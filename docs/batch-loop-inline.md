# セッション内バッチガイド（旧方式復旧・1セッション=複数チケット）

対話セッション内で、複数のactiveチケットを orchestrator が連続処理するための運用手順です。`/batch-loop-inline {ID-1} {ID-2} ...` を対話セッションで実行すると、事前承認テンプレートへの人間の承認を経て、orchestratorが通常の実装ループ（investigator→architect→implementer→tester→reviewer）をチケットごとに自律実行し、チケット境界で前進・停止を判定します。

> **対話セッション専用**: このコマンドはヘッドレス実行（`claude -p`）を想定しません。ヘッドレスでの連続実行が必要な場合は外部駆動版 `/batch-loop`（`scripts/batch_loop.py`）を使ってください。使い分けは `docs/batch-loop.md` 冒頭の比較表、または本ファイル「使い分け指針」を参照してください。

## 位置づけ（旧方式との関係）

本コマンドは、KLK-001（外部駆動バッチ導入）が非推奨化した旧方式（単一セッションへバッチ事前承認テンプレートを送り、orchestratorが同一セッション内で連続ループする方式）を、現行ポリシー（`docs/worktree-policy.md` のworktree分離・KLK-002のモデル割当）と整合させたうえで、外部駆動版とは別コマンドとして復旧したものです（KLK-007）。単純な過去バージョンの復元ではなく、次の互換性検証を経ています。

**互換性検証の結論と変更点**: 旧方式（8c10f84相当）は差し戻し（tester/reviewer）で**即停止**していました。この挙動を文字通り復元すると、KLK-001以降に明文化・hook強制された「実装ループ内の差し戻しはエージェント間で完結し人間は介在しない」という不変条件（CLAUDE.md 開発ループフロー、orchestrator.md Priorities）と衝突します。そのため本コマンドでは、差し戻し検知の粒度を「即停止」から外部駆動版 `/batch-loop` と同じ**チケット境界での停止**（チケットがdoneに到達した時点で `retry_counts` の増分を検査し、増分があれば次のチケットへ進まず停止・再承認を求める）へ変更しました。

- 実装ループ内の自律的な差し戻し処理（tester→implementer、reviewer→implementer）はバッチ実行有無に関わらず不変（人間非介在の原則を保つ）
- 「差し戻しが発生したバッチを人間の確認なしに進めない」という旧方式の意図は、チケット境界での停止として維持される
- 外部駆動版・セッション内版で境界判定の考え方が統一され、二重規範にならない

**worktree分離ポリシーとの整合**: worktreeの作成（design_done→implementer委譲直前）・削除（reviewer承認後）はチケット単位のイベントに紐づき、セッションが1チケットで終わるか複数チケットにまたがるかには依存しません。セッション内バッチはチケットを逐次処理する（並行しない）ため、ある時点でアクティブなworktreeは常に高々1つであり、並行worktree上限3件（`docs/worktree-policy.md`）にも抵触しません。対話セッションの `permissions.additionalDirectories`（`../{リポジトリ名}.wt/`）は worktree-policy.md で既に対話セッション向けに設定済みであり、追加の権限設定は不要です。

**KLK-002モデル割当との整合**: `model` frontmatterはサブエージェント起動（Task/Agentツール）のたびに解決される割当であり、呼び出し元セッションが外部駆動ヘッドレスか対話セッションかに関係なく同一に働きます。セッション内バッチは `/start-loop` と同じ委譲ロジック（orchestrator.md Agent Delegation Rules）をそのまま繰り返すだけなので、モデル割当について追加の調整は不要です。

> **パイロット運用の注意**: 旧方式＋worktree分離の組み合わせは、上記のとおり構造的には整合しますが、実運用（investigator〜reviewerのフルループ）での実績はまだありません。**初回の実運用バッチは人間監視下のパイロット実行**と位置づけてください（外部駆動版 `/batch-loop` のV-4実測と同じ考え方）。

## 使い方

対話セッション内で実行します（ターミナルでの別実行は不要）。

```
/batch-loop-inline APP-001 APP-002
```

実行フロー:

1. ID列の検証（`tickets/active/{ID}_*.md` に一意存在・cancelled/blocked/done でない・重複不可）
2. `/start-loop` 起動時チェックリスト（Autoモード確認・14日blockedトリアージ・in_progress上限・done/件数警告・残存worktree検出）を**バッチ開始前に1回だけ**実行
3. 事前承認テンプレート（下記）の提示と人間の承認
4. 承認後、対象チケットを先頭から順に処理（通常の実装ループ委譲ロジックにそのまま従う）
5. チケットが `done`/`blocked` になるたびに前進・停止を判定（下記「停止条件」）

## 事前承認テンプレート

このテンプレートへの人間の承認が「バッチ連続実行の事前承認」の実体です（`.claude/agents/orchestrator.md`「改善ループ（人間の判断後）」テーブル直下の注記が指す「代行」はこれを指します）。

```
【バッチ連続実行の事前承認（セッション内・/batch-loop-inline）】
対象チケット（実行順）: {ID-1} {ID-2} ...

このセッション内で、各チケットに対して通常の実装ループ（investigator→architect→
implementer→tester→reviewer）を自律的に実行します。

前進の扱い:
- チケットがdoneに到達し、かつそのチケットの処理中にretry_countsの増分が
  一切なかった場合 → 完了を要約報告し、人間の確認を待たずに次のチケットへ進みます
- チケットの処理中にretry_countsが増分した場合（差し戻しが発生した場合）→
  そのチケットがdoneに到達しても次のチケットへは進まず、要約を報告して停止します
  （改めて人間の確認・再承認を待ちます）
- チケットがblockedになった場合（リトライ上限超過を含む）→ 直ちに停止し、
  ブロッカー内容を報告します
- 最終チケットの処理が終わったら、結果によらず必ず停止し、通常の改善ループ判断
  （実装ループ継続/設計見直し/調査やり直し）を人間に確認します

この事前承認は、チケット間の前進判断（本来は改善ループ判断テーブルが扱う）をバッチ内に
限り代行するものであり、実装ループ内の自律的な差し戻し処理そのものは変更しません
（人間非介在の原則は維持されます）。

実行してよろしいですか？
```

## 停止条件（チケット境界）

| 条件 | 動作 |
|---|---|
| チケットが `blocked`（リトライ上限超過を含む） | 直ちに停止し、ブロッカー内容を報告する |
| チケットが `done` かつ `retry_counts` 増分あり（差し戻し発生） | doneに到達していても次へ進まず、要約報告して停止・再承認を待つ |
| チケットが `done` かつ増分なしかつ残りチケットあり | 要約報告して次のチケットへ進む（人間の確認は待たない） |
| チケットが `done` かつ残りチケットなし（最終チケット） | 要約報告して停止し、通常の改善ループ判断を人間に確認する |

## 使い分け指針

| 判断基準 | `/batch-loop`（外部駆動） | `/batch-loop-inline`（セッション内・本ガイド） |
|---|---|---|
| バッチ件数 | 制限なし。多数件でも安全（セッション使い捨てでトークン累積なし） | 少数（目安2〜3件）を推奨。件数が増えるほど同一セッションにレポートが蓄積しコスト増 |
| トークン累積 | なし（チケットごとに新規セッション） | あり（セッション内に全チケットのサブエージェントレポートが蓄積） |
| 人間監視の要否 | 不要（無人実行可能。ヘッドレスでは`ask`は自動deny、応答不能な場面はチケットをblocked化して停止） | 必要（対話セッションが前提）。AskUserQuestion等の人間判断が必要になりそうなチケットに強い |
| 実行環境 | ターミナルでのPythonスクリプト実行が必要 | Claude Codeの対話セッション内で完結（追加のターミナル操作不要） |
| 進捗の可視性 | ターミナル標準出力でリアルタイム表示（stream-json化・KLK-007） | セッションの通常の応答としてリアルタイムに見える |
| 差し戻し発生時の挙動 | チケット完了時に停止・報告。`--continue-on-rework`で緩和可 | チケット完了時に停止・報告し、再承認を待つ（対話でその場に確認できる） |
| 推奨用途 | 既定。多数件・長時間・無人実行したい場合 | 少数件をその場で見守りながら進めたい場合、対話的判断が挟まりそうな場合 |

## Never（本コマンドが遵守する制約）

- ヘッドレス実行を想定しない（ask hook等ヘッドレス固有の配慮は不要。ヘッドレス連続実行が必要な場合は `/batch-loop` を使う）
- 事前承認を得ずにチケット間を自動前進しない
- `retry_counts` 増分を検知したにもかかわらず人間の再承認なしに次のチケットへ進まない
- 大量件数・長時間の無人実行を目的として使わない（トークン累積のトレードオフを人間へ明示せずに実行しない）。多数件・無人実行が目的の場合は `/batch-loop` を案内する
