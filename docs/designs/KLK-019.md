# [KLK-019] シェル制御構文（for/while/if）の誤deny解消 設計

> このファイルはarchitectが生成・更新するチケット単位の設計書です。
> チケット KLK-019 に対応します。implementer・tester・reviewerが参照します。

## 1. 目的

`.claude/hooks/guard_bash_writes.py` の `head_of()` は `;` 区切りの1ステートメントの
先頭語を無条件に「コマンド名」とみなす。`for`/`while`/`until`/`if`/`elif`/`case`は
もちろん、`do`/`then`/`else`/`fi`/`done`/`esac`もすべて`ALLOWED_HEADS`に無いため、
これらが先頭語になっただけで保護対象パスに言及するステートメントが一律denyに
なる（本チケットに SPEC.md 上の REQ/SCR/IF は無い。要件の正はチケット KLK-019
の受け入れ条件）。本チケットは、制御構文キーワードを**単純にALLOWED_HEADSへ
追加せず**（investigator実測: `do rm $f`等4形が deny→allow に転じる穴を確認済み）、
先頭キーワードだけを再帰的に剥がして残余語を既存のALLOWED_HEADS判定へそのまま
回す機構を新設し、読み取り専用の制御構文をallowへ、書き込みを含む制御構文
（リテラルパス・ループ変数経由の両方）を引き続きdenyへ分類する。

## 2. 現状

**現在のフロー（`for f in tickets/active/*.md; do rm $f; done` の例）:**
```
lex() → 改行/`;`を統一的にstatement区切りとして split_statements()
  → 統計1 ["for","f","in","tickets/active/*.md"]
      head_of = "for" → ALLOWED_HEADS外 → gate_hit(literal mention)=True → deny
      （"rm $f" を含む統計2 は評価に到達すらしない）
  → 統計2 ["do","rm","$f"]
      head_of = "do" → ALLOWED_HEADS外（統計1で既にdeny済みのため到達しない）
```
制御構文の特別扱いはコード中に一切存在しない（investigation.md Finding1）。
`ALLOWED_HEADS`/`CWD_SAFE_HEADS`へ制御構文キーワードを単純追加する仮想パッチ
検証では、`for f in tickets/active/*.md; do rm $f; done`／`if rm ...; then echo done; fi`／
`case x in *) rm ...;; esac`／`while true; do rm ...; break; done`の4形すべてが
deny→**allow**に転じることを実測済み（investigation.md Finding3）。原因は
「`do`/`then`/`elif`/`else`の直後に続く実コマンド語がhead判定から一切見えない」
こと（ステートメント分割が`;`単位のみのため`do rm $f`は1ステートメントであり、
`head_of`は先頭語`do`だけを見て`rm`を判定対象にしない）。

**関連する既存ファイル:**
- `.claude/hooks/guard_bash_writes.py` `split_statements()`: `"""トークン列を \`;\` \`&&\` \`||\` \`&\` でステートメントへ分割する。"""` （`;`単位のみで分割し、制御構文の入れ子は一切考慮しない）
- 同ファイル `head_index()`: `"""語リスト中で「先頭コマンド名」に当たる語の位置を返す。無ければ -1。"""` （環境変数代入前置きと `(` グループ化しか読み飛ばさない）
- 同ファイル `statement_violation()`: `"""ステートメント単位の違反理由を返す。問題なければ None。"""` （`segments = pipe_segments(statement)` が変更対象の中心行）
- 同ファイル `redirect_violation()`: `"""出力リダイレクト先が保護対象・保護対象を代入された変数なら理由を返す。"""` （`guarded_vars` のみを見る。ループ変数の追跡機構が無い）
- 同ファイル `record_assignments()`: `"""\`NAME=保護対象パス\` の前置き代入を記録する（リダイレクト先の追跡用）。"""` （`for NAME in ...` の束縛は対象外）
- 同ファイル `find_violation()`: `for statement in split_statements(tokens):` （ステートメントごとの cwd 追跡・違反判定ループの本体）
- `tests/test_guard_bash_writes.py` `INVENTORY_CASES`: `("INV-SH-11", "パラメータ展開（値は不可視＝構造的限界・**未対応**）",` （ループ変数値追跡は既存でも「原理的に閉じられない」限界として明記済み。本チケットが変えるのは「値」ではなく「変数参照の構文的存在」の扱い）

## 3. 設計方針

**採用する方針:**

1. **`ALLOWED_HEADS`/`CWD_SAFE_HEADS`は一切変更しない。** 制御構文キーワード
   （`for`/`while`/`until`/`if`/`elif`/`do`/`then`/`else`/`case`）は「コマンド」
   ではなく構文上のマーカーである、という性質をそのまま表現する。モジュール
   docstring末尾の「ALLOWED_HEADSへコマンドを追加するときの手順」（4次元棚卸し）
   はコマンド名を新規収載するときの手続きであり、本設計はこれを一切トリガー
   しない（棚卸し表・5手順の適用対象外であることを明記する）。
2. **`strip_control_prefix(statement)`** を新設し、ステートメント（`(kind,value)`
   トークン列）の先頭に連なる制御構文キーワードを再帰的に剥がし、実行されうる
   「残余コマンド」のトークン列を返す。剥がすものが無い・構造を確定できない
   （C形式for・複数パターンcase等）場合は `None` を返し、呼び出し元は**元の
   statementでそのまま判定する**（＝現状の保守的なdeny挙動を変えない。P8）。
   - `if`/`elif`/`while`/`until` の直後は**実行される条件コマンド**なので、
     キーワード1語だけを剥がして残余をそのまま次のループへ回す。
   - `do`/`then`/`else` の直後は**実行される本文コマンド**なので、同様に
     1語だけ剥がす。
   - `for NAME in LIST` は**実行されるコマンドを一切含まない**（LISTは列挙
     されるだけ）。`NAME`が識別子の形（`[A-Za-z_][A-Za-z_0-9]*`）であることを
     確認できた場合に限り、残余を空リスト`[]`として返す（ALLOWED_HEADS判定を
     スキップ＝実質的に「常に許可」だが、これは「判定するコマンドが無い」
     ためであり、ALLOWED_HEADSへの追加とは異なる）。C形式（`for ((i=0;...))`）
     など`NAME`が識別子の形を取らない場合は`None`を返しフォールバックする。
   - `case SUBJECT in PATTERN) ...` は「ヘッダー＋最初の節の本体」が同一
     ステートメントに同居する。`PATTERN`が単一トークンで`)`終端の単純な形
     （`*.md)`・`*)` 等）だけを認識し、それ以外（複数パターンの`a|b)`・
     `(`/`)`が別トークンに分割される形・`in`欠落等）は`None`を返して
     フォールバックする（理由は§6リスクのR-CTRL2）。
3. **ゲート判定・cwd追跡はすべて既存の`statement_violation`/`find_violation`の
   仕組みを再利用する。** `strip_control_prefix`の出力は「`pipe_segments`へ渡す
   語列」を差し替えるためだけに使う。`redirect_violation`・ANSI引用チェック・
   heredocチェック・`mentions_guarded_expanded`によるゲート判定は**元の
   statement**に対して行う（変更しない）。これにより新設ロジックの影響範囲が
   「ALLOWED_HEADS判定に渡す語列の選択」1点に限定される。
4. **ループ変数経由の書き込み（AC3）は値を追跡せず、構文的な束縛の事実だけを
   証拠にする。** `for NAME in LIST`のLISTが（`mentions_guarded_expanded`で）
   保護対象パスに言及していた場合、`NAME`を新設の`guarded_loop_vars`集合へ
   登録する。以降の統計で`$NAME`/`${NAME}`という**参照が構文上どこかに現れる
   だけで**（読み取りコマンドの引数であっても）そのステートメントのゲートを
   開く。ゲートが開いた後の許可・不許可は既存のALLOWED_HEADS判定にすべて
   委ねる（`cat $f`は`cat`がALLOWED_HEADSにあるため許可のまま、`rm $f`は
   `rm`が無いため拒否）。値の追跡が原理的に不可能である以上、**「参照される
   だけでゲートを開く」が唯一の保守側に倒せる設計**である（詳細根拠は
   §6 R-CTRL1）。
5. **既存の`guarded_vars`（`NAME=value`前置き代入の追跡）とは完全に分離した
   別集合`guarded_loop_vars`を使う。** 両者を統合すると、既存の許容済みギャップ
   （INV-SH-11: `f=tickets/active/APP-001.md; rm $f` → 恒久的にallow）が本
   チケットの変更で新たにdenyへ転じてしまい、スコープ外の挙動変更（回帰）に
   なる。分離することでINV-SH-11の挙動は1バイトも変わらない。

**代替案と却下理由:**
| 案 | 却下理由 |
|---|---|
| 制御構文キーワードを`ALLOWED_HEADS`/`CWD_SAFE_HEADS`へ単純追加 | investigator実測で4形すべてがdeny→allowに転じる穴を確認済み（`do`/`if`等の直後の書き込みコマンドが一切判定されなくなる） |
| ループ変数の値そのものを解決しようとする（`for f in a b c`の列挙を辿るなど） | LISTがglob（`tickets/active/*.md`）の場合は実際のファイルシステムをstatしないと値が確定せず、本hookの「テキストのみで判定する」既存アーキテクチャ（ファイルI/Oを一切行わない）を逸脱する。原理的に閉じられない値追跡は既存INV-SH-11でも明示済みの限界であり本チケットで覆さない |
| 完全な shell 文法パーサへの刷新（`case`の`\|`パターン等も含め全構文を正しく解釈） | KLK-010が13ラウンド・10件の穴を経て確立した現行アーキテクチャ（ステートメント分割＋head判定＋追加規則のOR拡張）からの逸脱が大きく、長期的複雑性が増大する。本チケットのスコープ（AC1〜7）に対して過剰であり、既存機構の再利用で安全性を保ったまま閉じられる |
| ループ変数参照を「書き込み系コマンドの引数位置」だけに限定して検出（読み取りコマンドの引数では無視） | 「書き込み系コマンド」を独自に列挙するブラックリストが必要になり、新しい列挙漏れの次元を作る（KLK-010 P4が戒める形）。既存のALLOWED_HEADS判定へ委ねる「ゲートを開くだけ」の設計なら新しい列挙を増やさずに済む |

## 4. 実装詳細

**ファイル構成（変更のみ・追加ファイル無し）:**

**新設定数（`.claude/hooks/guard_bash_writes.py`。KLK-018のブレース展開節と
同じ位置づけで、既存定数の直後に独立したセクションとして追加する）:**
```python
# --- KLK-019: シェル制御構文（for/while/until/if/elif/do/then/else/case）の
#     本体再帰判定 -------------------------------------------------------------
CONTROL_CONDITION_KEYWORDS = frozenset({"if", "elif", "while", "until"})
CONTROL_BODY_KEYWORDS = frozenset({"do", "then", "else"})
# fi/done/esac は常に統計の末尾（bashの文法上、必ず区切り記号の後にしか
# 現れない）にしかならず、単独語のみの統計は言及ゲートが立たないため既存の
# ロジックのままで無害（§6 R-CTRL3）。特別扱いは不要だが可監査性のため列挙する。
CONTROL_CLOSING_KEYWORDS = frozenset({"fi", "done", "esac"})
BASH_NAME_RE = re.compile(r"[A-Za-z_][A-Za-z_0-9]*")
```

**新設関数（すべて既存関数のすぐ後、`statement_violation`の手前に配置）:**
```python
def _parse_for_header(words):
    """`for NAME in LIST` の古典形なら (NAME, LIST語のリスト) を返す。
    C形式（`for ((...))`）・`in`を伴わず余分な語がある不明な形は None。
    `for NAME; do ...`（`in`省略＝$@相当）は (NAME, []) を返す
    （LISTが無いためguarded_loop_varsには登録されない＝安全側）。
    """
    if len(words) < 2 or words[0] != "for":
        return None
    name = words[1]
    if not BASH_NAME_RE.fullmatch(name):
        return None
    rest = words[2:]
    if not rest:
        return name, []
    if rest[0] == "in":
        return name, rest[1:]
    return None  # `for NAME extra...`（in を伴わない不明な形）


def _strip_case_clause(tokens):
    """`case SUBJECT in PATTERN) ...` の先頭を剥がし、本体トークンを返す。

    単一トークンの単純パターン（`*.md)`・`*)` 等）だけを認識する。認識でき
    ない形（複数パターンの `|`・分割された `(`/`)`・`in` の欠落等）は None を
    返す（P8: 曖昧な位置は保守側。呼び出し元は元の statement で判定する）。
    """
    if (len(tokens) < 4 or tokens[1][0] != "w" or
            tokens[2] != ("w", "in") or tokens[3][0] != "w"):
        return None
    pattern = tokens[3][1]
    if not pattern.endswith(")") or pattern == ")":
        return None
    return tokens[4:]


def strip_control_prefix(statement):
    """先頭に連なる制御構文キーワードを再帰的に剥がし、残余トークンを返す。

    残余は「実行されうる本体コマンド」の (kind, value) トークン列（空リストも
    ありうる＝forヘッダーのように実行コマンドを含まない場合）。剥がすものが
    無い、または構造を確定できない場合は None を返す（呼び出し元は元の
    statement で判定する＝既存の deny 側の挙動を維持する。P8）。
    """
    tokens, changed = statement, False
    while tokens:
        if tokens[0][0] != "w":
            break
        head = tokens[0][1]
        if head == "case":
            residual = _strip_case_clause(tokens)
            if residual is None:
                return tokens if changed else None
            tokens, changed = residual, True
            continue
        if head == "for":
            plain = [v for k, v in tokens if k == "w"]
            parsed = _parse_for_header(plain)
            if parsed is not None:
                return []  # ヘッダーに実行コマンドは無い
            return tokens if changed else None  # C形式等、判定できない形
        if head in CONTROL_CONDITION_KEYWORDS or head in CONTROL_BODY_KEYWORDS:
            tokens, changed = tokens[1:], True
            continue
        break
    return tokens if changed else None


def control_stripped_segments(statement):
    """制御構文の先頭キーワードを剥がした残余からパイプ区間を得る。

    剥がせなかった場合（strip_control_prefix が None を返す場合）は元の
    statement からそのまま得る（安全側フォールバック。既存の全ステートメント
    に対して1バイトも挙動を変えない）。**この関数は ALLOWED_HEADS 判定
    （segment_violation 群）と cwd 追跡（next_cwd）の両方の呼び出し元から
    使うこと。** 片方だけに適用すると、`if cd tickets/active; then rm
    APP-001.md; fi` のように「if の条件で cd し、cwd 追跡だけが古い statement
    を見る」ことで cwd_is_guarded が発火しない穴になる（§6 R-CTRL4）。
    """
    stripped = strip_control_prefix(statement)
    return pipe_segments(stripped if stripped is not None else statement)


def mentions_guarded_var(words, names):
    """語のいずれかが names に含まれる変数を参照するか（`$NAME`/`${NAME}`）。

    読み取り・書き込みを問わず**参照が構文上に存在するだけ**で真になる
    （値の追跡は行わない＝AC3の保守的deny設計。実際に許可されるかどうかは
    このゲートの後段にある既存の ALLOWED_HEADS 判定に委ねる）。
    """
    if not names:
        return False
    for word in words:
        for ref in VAR_REF_RE.findall(word):
            if ref in names:
                return True
    return False


def record_loop_binding(statement, guarded_loop_vars, substs=()):
    """`for NAME in LIST` の LIST が保護対象に言及する場合、NAME を
    guarded_loop_vars へ登録する（KLK-019 AC3）。

    値そのもの（実行時に $NAME に束縛される個々の要素）は追跡できない
    （for の展開結果はコマンド文字列上に現れないため原理的に不可能。
    モジュール docstring「パラメータ展開」・INV-SH-11 と同型の限界）。
    ここでは「LIST全体が保護対象パスへ言及している」という構文的事実だけを
    証拠にし、`guarded_loop_vars` へ加える。既存の `guarded_vars`
    （NAME=value 前置き代入の追跡）とは完全に別集合であり、統合しない
    （INV-SH-11 の挙動を変えないため。§3 設計方針5）。
    """
    words = [v for k, v in statement if k == "w"]
    parsed = _parse_for_header(words)
    if parsed is None:
        return
    name, rest = parsed
    if not rest:
        return
    if mentions_guarded_expanded(expand_all(rest, substs)):
        guarded_loop_vars.add(name)
```

**既存関数の変更点:**

- `redirect_violation(statement, guarded_vars, substs=(), cwd="")` に
  `guarded_loop_vars=()` を追加し、リダイレクト先の変数参照チェックへ
  `guarded_vars` とのOR条件として組み込む:
  ```python
  any(n in guarded_vars or n in guarded_loop_vars
      for n in VAR_REF_RE.findall(resolved))
  ```
  （`for f in tickets/active/*.md; do echo x > $f; done` を検出するため）
- `statement_violation(statement, guarded_vars, substs=(), cwd="", guarded_loop_vars=())`
  - `segments = pipe_segments(statement)` を `segments =
    control_stripped_segments(statement)` へ差し替える（1行）
  - `redirect_violation(...)` の呼び出しへ `guarded_loop_vars` を追加で渡す
  - gate_hit の最終行へ `or mentions_guarded_var(expanded_words,
    guarded_loop_vars)` を追加する（`do rm $f`のような「読み取りに見えない
    参照」でゲートを開くため）
- `find_violation()`:
  - ループ変数の初期化を1行追加: `guarded_vars, guarded_loop_vars, seen =
    set(), set(), set()`
  - `record_assignments(...)` の直後に `record_loop_binding(statement,
    guarded_loop_vars, substs)` を追加
  - `statement_violation(...)` 呼び出しへ `guarded_loop_vars` を追加で渡す
  - cwd 追跡行 `segments = pipe_segments(statement)` /
    `cwd = next_cwd(segments[0] if segments else [], cwd)` を
    `segments = control_stripped_segments(statement)` に差し替える
    （**理由: R-CTRL4**。§6参照）

`degraded_violation`（字句解析に失敗した入力向けフォールバック）は変更しない
——制御構文の再帰的ストリッピングは正常経路（`lex()`が成功した入力）だけを
対象とし、degradedは従来どおり素朴な分割のまま維持する（degradedは元々
「旧版の判定要素の上位互換」であり、制御構文キーワードも旧版と同じく無条件
denyのまま。読み取り専用の制御構文がdegradedへ落ちた場合に誤denyのまま
残る既知の限界として§6に明記する。KLK-029のsed/awkゲート緩和が同様に
degradedへ及ばないのと同型の縮退）。

**処理フロー（`for f in tickets/active/*.md; do rm $f; done` を再入力した場合）:**
```
find_violation
 └ statement1=["for","f","in","tickets/active/*.md"]
    ├ record_loop_binding: _parse_for_header→("f",["tickets/active/*.md"])
    │   mentions_guarded_expanded(["tickets/active/*.md"])=True
    │   → guarded_loop_vars={"f"}
    ├ statement_violation: control_stripped_segments→strip_control_prefix
    │   → "for"はNAME形式(f)を確認→[] (残余なし)
    │   segments=[[]] → segment_violation([])→head無し→None
    │   gate_hit=True(literal mention)だがsegmentsに違反無し→None（allow継続）
    └ cwd追跡: control_stripped_segments→[] → next_cwd([],cwd)→cwd不変
 └ statement2=["do","rm","$f"]
    ├ redirect_violation: リダイレクト無し→None
    ├ control_stripped_segments→strip"do"→["rm","$f"]→segments=[["rm","$f"]]
    ├ gate_hit: 文字通りの言及は無いが mentions_guarded_var(["do","rm","$f"],
    │   {"f"})=True（$fの参照）→ gate_hit=True
    └ segment_violation(["rm","$f"])→head="rm"はALLOWED_HEADS外→
        "'rm' は許可されていません" → deny
```
（読み取り版 `... do echo $f; done` は同じ経路で `segment_violation(["echo","$f"])`
→ head="echo" は ALLOWED_HEADS内 → None → allow）

## 6. リスク

| リスク | 深刻度 | 軽減策 |
|---|---|---|
| **R-CTRL1（AC3の核心）**: ループ変数の値は原理的に追跡不能。`for f in tickets/active/*.md; do rm $f; done`で`$f`の実行時の値（`APP-001.md`等）はコマンド文字列上に現れないため、「値」を根拠にした判定は不可能 | high | 値ではなく「NAMEがガード対象パスへ束縛されるLISTを持つforの変数である」という**構文的事実**を証拠にし、`$NAME`という**参照の存在**だけでゲートを開く（`mentions_guarded_var`）。破れる形（否定形）: 本関数の呼び出し箇所が「ゲートを開く」以外の用途（例: 単独で許可判定に使う）に転用された場合。向き: 誤って強めても deny 方向にしか働かない（ゲートを開いた後の許可・不許可は既存のALLOWED_HEADS判定に委ねるため、over-denyにしかならない）。検出器: `tests/test_guard_bash_writes.py`のINV-CTRL-03〜05・`test_klk019_loop_var_*` |
| **R-CTRL2**: `case`の複数パターン（`a|b)`）は本hookの字句解析器が`\|`を「パイプ演算子」として無条件に扱うため（`OPERATOR_CHARS`に`\|`を含む）、case構文上の論理和と混同し、正しく解析できない | medium | 単一パターン（`)`で終端する単一トークン）だけを認識対象とし、それ以外は`_strip_case_clause`が`None`を返して既存の（保守的な）deny挙動へフォールバックする。将来この次元を閉じるには字句解析器自体にcase文脈を持たせる別チケットが必要（本チケットのスコープ外・§6既知の限界として明記） |
| **R-CTRL3**: `fi`/`done`/`esac`単独ステートメントは特別扱いをしていないため、万一これらが保護対象パスに言及する形で使われた場合（例: 変数名やコメントの巻き添えではなく、直接パスを引数のように置く不正な形）に誤denyや誤allowが起きないか | low | bashの文法上、これらは常に「区切り記号の直後」にしか現れず、単独語のみのステートメントとしてしか出現しない（本設計書§2で確認）。単独語ステートメントが保護対象パスへ言及することは構文的にありえない（引数を取らないため）。念のためINV-CTRL-XXで単独`done`/`fi`/`esac`のケースを固定する |
| **R-CTRL4（設計中に発見。investigation.mdには無い新規リスク）**: `strip_control_prefix`をALLOWED_HEADS判定にのみ適用し、`find_violation`のcwd追跡（`next_cwd`）には適用しない設計にすると、`if cd tickets/active; then rm APP-001.md; fi`のように「ifの条件節でcdする」形でcwd追跡が古いstatement（head="if"）を見て`next_cwd`が発火せず、後続の`then`節でcwd_is_guardedが偽のままrmが素通りするおそれがある（旧版はstatement1自体を"if"未許可でdenyしていたため、この経路は今まで到達しなかった＝本チケットの変更で新たに露出する） | high | `control_stripped_segments`をALLOWED_HEADS判定とcwd追跡の**両方**から呼ぶ単一のヘルパーとして共有し、片方だけに適用することを構造的に防ぐ（§4のコードコメントに明記）。検出器: `test_klk019_if_cd_then_rm_denies_via_cwd_tracking`（deny側）と`test_klk019_if_cd_then_cat_allows_via_cwd_tracking`（allow側）の対 |
| **R-CTRL5**: `guarded_loop_vars`は一度登録した変数名を統計全体で保持し続ける（forループの`done`を過ぎても保持）ため、同名変数を無関係な用途で再利用した場合に過剰denyが起きうる | low（安全側の誤り） | 意図的な設計判断（§3方針4）。値追跡が不可能な以上、スコープ終端の判定も不可能であり、より広く保持する方が安全側（over-denyのみで新規allowの穴にはならない）。§9 Open Questionsではなく設計確定事項として明記する |
| **R-CTRL6**: `degraded_violation`は本チケットの対象外のため、字句解析に失敗する入力（未閉じクォート等）に制御構文が混在した場合、読み取り専用の制御構文でも従来どおり誤denyのまま残る | low（既存の限界の継続） | 新規の穴ではない（degradedは常により保守的であることが既存の設計原則）。§4末尾・本設計書の「既知の限界」として明記し、別チケット候補とする |
