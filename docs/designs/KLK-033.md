# [KLK-033] 否定文字クラス[!]globがpathish分断で検出されずSPEC.md操作が誤allowされる 設計

> このファイルはarchitectが生成・更新するチケット単位の設計書です。
> チケット KLK-033 に対応します。implementer・tester・reviewerが参照します。

## 1. 目的

対応要件ID: 該当なし（本リポジトリはKit自身のツールであり `docs/SPEC.md` が存在しない
ことを確認済み。KLK-020・KLK-031・KLK-032の前例に同じ。要件の正はチケットKLK-033の
受け入れ条件と `docs/reports/KLK-033/investigation.md`）。

`.claude/hooks/guard_bash_writes.py` の候補抽出正規表現 `SHELL_EXPAND_PATHISH_RE` の
文字集合に `!` が無いため、bashの否定文字クラス `[!...]` を含む語が `!` の位置で分断され
（`docs/[!x]PEC.md` → `docs/[` ＋ `x]PEC.md`）、シェル実行時にはディスク上の
`docs/SPEC.md` に一致するにもかかわらず「保護対象パスへの言及なし」と判定され人間承認
ゲートをすり抜ける（誤allow）。文字集合へ `!` を追加してこの分断を閉じ、あわせて
`!` 追加により**到達可能になる** `_ticket_lib.is_spec_basename_fnmatch` の非単調性
（`.upper()` が `[!s]` を `[!S]` へ変える）を和集合形で是正する。
KLK-020（SPEC.md判定の一本化）→ KLK-031（`has_literal_char` ゲート）→ KLK-032（glob事前
フィルタの大小区別）に続く系譜の、候補抽出レイヤーの是正である。

## 3. 設計方針

**採用する方針: (1) `SHELL_EXPAND_PATHISH_RE` の文字集合へ `!` を1文字追加し、
(2) `_ticket_lib.is_spec_basename_fnmatch` を和集合形へ拡張する。両者は同一Phase・
同一コミットで適用する（結合必須。理由はD2末尾）。`GLOB_META_CHARS`・KLK-031ゲート・
`GUARDED_DIR_NAMES` 側比較・呼び出し階層はすべて無変更。**

### D1. `SHELL_EXPAND_PATHISH_RE` の文字集合拡張（`!` の追加位置と最終形）

最終形（`!` を既存集合の末尾＝`\]` の直後に追加する）:
```python
SHELL_EXPAND_PATHISH_RE = re.compile(r"[A-Za-z0-9_.\-/{},*?\[\]!]+")
```
- **追加位置の根拠:** Pythonの正規表現の文字クラス内では `!` は特殊文字ではなく位置に
  依存しない（POSIXブラケット式の `[!...]` と異なり、Python `re` の否定は `^` のみ）。
  それでも**末尾**に置くのは、先頭に置くと読み手が `^`（否定）と混同する余地を作らない
  ためであり、investigator が実測に用いた仮説形
  （`re.compile(r"[A-Za-z0-9_.\-/{},*?\[\]!]+")`、investigation.md §1 実測4）と
  バイト単位で同一にして「実測した形をそのまま実装する」ためである。
- **`GLOB_META_CHARS` を無変更とする根拠（3点。チケットAC4の評価の一部）:**
  1. `!` 単体はglobメタ文字ではない。bashで `[!...]` が否定クラスとして意味を持つのは
     ブラケット `[` の直後という文脈に限られ、その `[` は既に
     `GLOB_META_CHARS = frozenset("*?[")` に含まれる。したがって成分
     `[!x]PEC.md` は現状の `any(ch in component for ch in GLOB_META_CHARS)` を
     `[` で既に通過する（investigation.md §1 実測4で確認済み）。
  2. `!` を追加すると `has_literal_char`（KLK-031ゲート）が `!` を「リテラル文字では
     ない」と数えるようになり、ゲートの意味論（「構造的資格を持つ成分だけをSPEC.md照合
     の対象にする」）を `!` の分だけ変えてしまう。KLK-031の誤deny是正の前提を触るため
     不可。
  3. `!` を追加すると `any(ch in component ...)` のメタ文字ゲートが `foo!bar` のような
     **glob ではない語**に対しても真になり、glob分岐（fnmatch照合＋文字列再構成）が
     不要に走る。挙動は deny 方向へ広がる可能性があり、コストも増える。
  以上より、`GLOB_META_CHARS` は無変更が最小かつ意味論的に正しい。

### D2. `is_spec_basename_fnmatch` の非単調性への対処 —— **(a) 和集合形を採用する**

チケットが示した二択のうち **(a) 和集合形へ変更**を採る（(b) docstring但し書きのみは
却下。下表参照）。判定式:
```python
fnmatch.fnmatchcase("SPEC.md", pattern) or fnmatch.fnmatchcase("SPEC.MD", pattern.upper())
```
- **決定的な理由（(b) では誤allowが残る）:** D1の `!` 追加によって `[!...]` を含む成分は
  **初めて `is_spec_basename_fnmatch` に到達する**。現行実装（`.upper()` 単独）では
  `is_spec_basename_fnmatch("[!s]PEC.md")` = `fnmatchcase("SPEC.MD", "[!S]PEC.MD")` = False
  （investigation.md §2 実測）。一方 bash では `[!s]` が大文字 `S` を除外しないため
  `docs/[!s]PEC.md` は実ファイル `docs/SPEC.md` に一致する。よって(b)を採ると
  `rm docs/[!s]PEC.md` という誤allowが**新たに到達可能な穴として残る**。KLK-032レビュー
  Medium 3-1が「本番経路では回帰なし」と評価できたのは `!` が分断されていたためであり、
  その前提はD1で消滅する。非単調性の是正はD1と不可分である。
- **健全性の根拠（第1項が「正しい述語」そのもの）:** bashのglob照合は大小をそのまま比較
  するため、「パターン `pattern` が実ファイル `SPEC.md` に一致する」ことと
  `fnmatchcase("SPEC.md", pattern)` は同一の述語である。和集合の第1項はこの健全な述語
  そのものであり、第2項（`pattern.upper()` 側）はKLK-020／KLK-032が人間確定した
  「SPEC.md判定は大小を区別しない」方針による意図的な過大近似（deny方向＝安全側）である。
  したがって和集合形は「健全 ∪ 過大近似」であり、正規形 `docs/SPEC.md` に対する
  allow方向の取りこぼしを構造的に持たない。
- **単調性（deny面の縮小なし）:** 和集合形は旧実装（第1項のみ）とKLK-032実装（第2項のみ）
  の双方のTrueを保持する。investigation.md §2の11パターン比較表で実測確認済み。
  既存4テスト（`test_is_spec_basename_fnmatch_*`）の全入力に対する照合は§9の表で確定
  （全件が現行期待値と一致するため既存テストは**無変更**）。
- **KLK-031ゲートとの直交性:** ゲートは「GUARDED_FILENAMEを `literals` に加えるか」、
  本関数は「加えられたGUARDED_FILENAMEをどう照合するか」を決めるレイヤーであり、
  KLK-032 D3の直交性はそのまま成立する。`_guarded_paths_from_expanded('*') == []`
  （KLK-032の既存unitテスト）は本変更後も維持される。
- **公開インターフェース:** シグネチャ `is_spec_basename_fnmatch(pattern)` と
  非str→False の契約は無変更（呼び出し元は `_guarded_paths_from_expanded` のみ。
  investigation.md §3で確認）。`isinstance` チェックは両fnmatch呼び出しより前に置き、
  `None`／`123` に対する `.upper()` 例外を発生させない。
- **残余の限界（新規に作る限界ではなく、既存の限界を縮小した後の残り）:** 第2項は
  pattern全体を大文字化するため、ブラケット表現を含むパターンについては `SPEC.md`
  以外の大小変種（`Spec.md`・`sPEC.md` 等）を対象とする一致を取りこぼしうる
  （例: `[!s]pec.md` は False。正規形 `SPEC.md` には bash でも一致しないため本
  リポジトリでは実害なし）。完全閉包（`spec.md` の全大小変種に対する照合）は本
  チケットのスコープ外とし、§6にリスクとして記録する。和集合形は旧実装・KLK-032実装
  いずれよりもこの残余を**厳密に縮小する**（拡大はしない）。

### D3. 文字集合拡張の副作用評価（チケットAC4の評価本体）

- **語内限定:** `SHELL_EXPAND_PATHISH_RE` は `lex()`／`skeleton.split()` が既に分割した
  **1語の内部**にのみ適用される。`!` の追加は語と語の結合を変えないため、`!` が独立語
  として現れる形（`! grep foo bar.txt`・`find . ! -name '*.md'`・`[[ ! -f x ]]`・
  `[ ! -f x ]`）は候補集合が不変であり判定も不変（investigation.md §1 実測6・§3）。
- **影響が生じる形:** `!` が他のpathish文字と同一語内で連続する形のみ
  （`foo!bar`・`a!b/c.md`・`!important`・`!!`・`docs/[!x]PEC.md`）。これらは修正後
  1トークンとして候補に載るが、`_guarded_paths_from_expanded` が要求する構造
  （`tickets/active`／`tickets/done` の文字列隣接、または最終成分がSPEC.md相当）を
  偶然構成しないため結果は不変（investigation.md §1 実測6で `find_violation` が全て
  `None` のまま）。誤deny方向の予算は§9のテストでロックする。
- **履歴展開:** `!!`・`!$` は非対話シェルでは既定で無効という既存の設計前提
  （モジュールdocstring「既知の限界」に既記載）に変更なし。修正後は候補として1語で
  拾われるようになるだけで、保護対象構造を作らないため判定は変わらない。
- **ブレース展開のコスト会計（investigatorが挙げていない追加の副作用。本設計で評価）:**
  候補が `!` をまたいで結合されるため、1候補あたりの `{` 出現数とブレース直積の組合せ数が
  増えうる（例: `a{1,2}!b{3,4}.txt` は従来2候補×2通りだったものが1候補×4通りになる）。
  `MAX_BRACE_CHAR_COUNT`（50）・`MAX_BRACE_COMBINATIONS`（512）に到達した場合の分岐は
  KLK-018の既存フォールバック（候補全体を保護対象候補とみなす＝deny方向＝安全側）へ
  合流し、新しい判定パスは生まれない。現実のコマンド長では閾値から大きく離れており、
  向きも安全側であるため許容する（§6にリスク行として記録。§9で `rm a{1,2}!b{3,4}.txt`
  が allow のままであることを固定する）。
- **degraded経路:** 同一の `SHELL_EXPAND_PATHISH_RE` を共有するため、`!` 追加は
  `degraded_violation` の全ゲート（`skeleton.split()` 全体ゲート・パイプ区間ゲート・
  `LEGACY_REDIRECT_RE` 先の判定）へ自動的に一律波及する。コード変更は不要だが、
  波及したことの証跡としてdegraded経路のテストを§9に必須で置く（investigator Unknowns
  ③の決着。D4参照）。

### D4. investigator Unknowns 3点の決着

| # | Unknown | 決着 |
|---|---|---|
| ① | 実bashでの `rm docs/[!x]PEC.md` 実行検証を行うか | **行わない。** 理由3点: (i) 本チケットの受け入れ条件はhookが検出してdeny/askすることであり、bashの実削除挙動は検証対象ではない。(ii) 「bashが一致させるか」という述語は D2 のとおり `fnmatchcase("SPEC.md", pattern)` と同一であり、これは和集合形の第1項として**実装に内在**する。よってヘルパー単体テスト（`[!x]PEC.md`→True・`[!S]PEC.md`→False）が同じ述語を両側から固定し、実bash実行は同一述語の二重確認にすぎない。(iii) 保護対象の実ファイル `docs/SPEC.md` に一致しうる `rm` の実行は破壊的であり、hook自身が守る対象を壊すリスクを負う。さらに検証コマンドの文字列自体が本hookにdenyされる（§4-4）。**人間が実bash確認を要求する場合の手順**（参考・本設計では実施しない）: 使い捨てディレクトリで `d=$(mktemp -d)` → 空の `SPEC.md` を作成 → `rm` ではなく `echo`／`ls` でglob展開結果のみを確認 → `rm -rf "$d"`。この手順はインラインBashツール呼び出しでは実行できない（hookにdenyされる）ため、人間が自分の端末で実行するか、テストファイル内から `subprocess` 経由で起動すること |
| ② | 和集合形と `tests/test_ticket_lib.py` 既存4ケースの網羅照合の実施方法 | **設計時に全入力を照合済み**（§9の照合表。既存4メソッドの入力は合計11個であり、和集合形の期待値は全件現行の期待値と一致）。実施方法: implementerはPhase 1完了時に既存4メソッドを**1行も変更せず**実行してPASSを確認する（変更が必要になった場合は和集合形が既存契約を破っている証拠であり、実装を止めてorchestratorへ報告する）。testerは `tests/test_ticket_lib.py` 全件および `discover` 全件（baseline 805件）を再実行して回帰0を確認する |
| ③ | degraded経路の否定クラス回帰テストの具体ケース | **§9で必須ケースとして確定**: deny側 `rm docs/[!x]PEC.md # don't`（末尾の未閉じシングルクォートで `lex` を失敗させ `degraded_violation` へ落とすKLK-031／KLK-032と同一のイディオム）、誤deny予算側 `rm foo!bar # don't`（allow）。読み取り専用head（`cat ... # don't`）のdegraded対称性は**任意**とし、期待値を事前に断定しない（正常経路の `cat` allow はinvestigatorが実測済みだがdegraded側は未実測。追加する場合はtesterが実測値で固定し、実測結果が allow でなかった場合はレポートで報告する） |

**代替案と却下理由:**
| 案 | 却下理由 |
|---|---|
| (A) `is_spec_basename_fnmatch` はdocstring但し書きのみ（チケット二択の(b)）とし、pathish拡張だけ行う | D1適用後は `[!...]` が本関数に到達するため、`rm docs/[!s]PEC.md` が誤allowとして**残る**（bashでは `docs/SPEC.md` に一致する）。誤allow=危険方向の穴を意図的に残すことになり、チケットの期待動作「保護対象パスに一致しうるコマンドがdeny/askされる」を満たさない |
| (B) `SHELL_EXPAND_PATHISH_RE` を「空白以外の全文字」等へ大幅に広げる | 誤deny面が制御不能に広がり（クォート・演算子・`$` 等まで候補化）、KLK-018/031が積み上げた誤deny予算の前提を壊す。本チケットが必要とするのは `!` 1文字のみで、投機的拡張は行わない |

### 4-2. `_ticket_lib.py`: `is_spec_basename_fnmatch` の和集合形化

**変更対象（一意引用。関数末尾の2行）:**
```python
    return isinstance(pattern, str) and fnmatch.fnmatchcase(
        "SPEC.MD", pattern.upper())
```

**変更後（docstringも本関数内で全面差し替え。シグネチャは無変更）:**
```python
def is_spec_basename_fnmatch(pattern):
    """glob パターン pattern が 'SPEC.md' に fnmatch するか（大小の扱いは
    下記2項の和集合。KLK-032 で新設し KLK-033 で和集合形へ拡張した）。

    ① fnmatch.fnmatchcase("SPEC.md", pattern)
       bash が実ファイル docs/SPEC.md に対して行う照合と同一意味論
       （大小をそのまま比較する）。取りこぼすと「bash では一致するのに
       hook は検出しない」= allow 方向（危険）になるため、健全性の要。
    ② fnmatch.fnmatchcase("SPEC.MD", pattern.upper())
       KLK-020／KLK-032 が確定した「SPEC.md 判定は大小を区別しない」
       方針による意図的な過大近似（deny 方向=安全側）。

    ①を欠くと `.upper()` が `[!s]` を `[!S]` へ変える非単調な操作になり、
    `[!s]PEC.md` が False になる（KLK-032 レビュー Medium 3-1）。KLK-033 で
    SHELL_EXPAND_PATHISH_RE に `!` を追加したことでこの経路は到達可能に
    なったため、①②の和集合が必須である（docs/designs/KLK-033.md §3 D2）。

    残余の限界: ②は pattern 全体を大文字化するため、ブラケット表現を含む
    パターンについては 'SPEC.md' 以外の大小変種（'Spec.md' 等）を対象と
    する一致を取りこぼしうる（例: '[!s]pec.md' は False。正規形
    'SPEC.md' には bash でも一致しない）。全大小変種に対する完全閉包は
    スコープ外（docs/designs/KLK-033.md §3 D2・§6）。

    注意: リテラル文字を1文字も含まないパターン（'*'・'**' 等）にも True を
    返す。呼び出し側の KLK-031 ゲート（has_literal_char。リテラル文字0の
    成分では GUARDED_FILENAME を照合対象に加えない）が先に除外する前提で
    あり、本関数は孤立ワイルドカードの扱いに関知しない（レイヤーを分離）。
    """
    if not isinstance(pattern, str):
        return False
    return (fnmatch.fnmatchcase("SPEC.md", pattern)
            or fnmatch.fnmatchcase("SPEC.MD", pattern.upper()))
```
- `isinstance` を早期returnに変えることで、非str（`None`・`123`）に対する
  `.upper()` 呼び出しへ到達しない契約を維持する（既存テスト
  `test_is_spec_basename_fnmatch_non_str_returns_false` の契約）。
- コスト: 1成分あたり fnmatch 呼び出しが1→2回になる。`fnmatch.fnmatchcase` は
  translate結果をキャッシュするため実効コストは無視できる（呼び出しは
  glob成分ごとに最大1回）。
- 例外安全性: `pattern.upper()` が無効な範囲（`[Z-a]`→`[Z-A]`）を生む場合、
  Python 3.12 の fnmatch は例外を送出せず False を返す（KLK-032レビュー 3-3で
  実測確認済み）。和集合形では第1項が生きるため、この artifact による
  allow 方向の取りこぼしはむしろ縮小する。

### 4-4. 検証時の運用上の注意（hookの自己遮断。KLK-032 §4-4と同じ運用）

- 動作確認は `python3 -c "...docs/[!x]PEC.md..."` のようなインライン実行で行わず、

  一時ファイルが必要な場合はWriteツールで作成する。
- `git commit -m` のメッセージにも `[!...]` 形の文字列を入れない（同じ理由でdenyされうる）。

## 8. ロールバック戦略

git revert {Phase2コミットハッシュ} {Phase1コミットハッシュ}

注意点2つ:
- revertは誤allow（否定クラスglobによる人間承認ゲートのすり抜け）を意図的に再導入する
