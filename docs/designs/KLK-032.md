# [KLK-032] guarded_paths_after_shell_expansionのSPEC.md判定がglob下で大小区別を残し誤allowする 設計

> このファイルはarchitectが生成・更新するチケット単位の設計書です。
> チケット KLK-032 に対応します。implementer・tester・reviewerが参照します。

## 1. 目的

対応要件ID: 該当なし（本リポジトリはKit自身のツールであり `docs/SPEC.md` が存在しない。
KLK-020・KLK-031の前例に同じ。要件の正はチケットKLK-032の受け入れ条件と
`docs/reports/KLK-032/investigation.md`）。

`.claude/hooks/guard_bash_writes.py` の `_guarded_paths_from_expanded` 内の
glob事前フィルタ `fnmatch.fnmatchcase(literal, component)` が大小区別を残しており、
`docs/sp*.md`・`docs/Spec*.md` 等の小文字/大小混在glob難読化が「保護対象パスへの
言及なし」と誤判定され人間承認ゲートをすり抜ける（誤allow）。KLK-020が一本化した
SPEC.md判定の「5箇所目」の取り残し（`docs/reports/KLK-020/review.md`「High Risk」節で
発見）を是正し、SPEC.md（`GUARDED_FILENAME`）側の照合**のみ**をcase-insensitive化する。
`GUARDED_DIR_NAMES`（active/done）側はチケットのスコープ指定どおり現状維持とする。

## 3. 設計方針

**採用する方針: `literals` 構築（KLK-031ゲート含む）を無変更のまま、内側ループの
比較のみを literal の種別で分岐させ、SPEC.md側の照合を `_ticket_lib` の新ヘルパー
`is_spec_basename_fnmatch` 経由でcase-insensitive化する。**

- **比較のみを分岐（D1）:** `literals` に入りうる値は `"active"`・`"done"`・
  `GUARDED_FILENAME`（`"SPEC.md"`）の3つのみであり、`literal == GUARDED_FILENAME` で
  SPEC.md側を確実に識別できる。GUARDED_DIR_NAMES側は従来どおり
  `fnmatch.fnmatchcase(literal, component)`（大小区別あり）のまま残す。
  これによりKLK-031で追加されたゲート行（`has_literal_char = ...`／
  `if index == last_index and has_literal_char:`／`literals = literals + [GUARDED_FILENAME]`
  とその直前のKLK-031コメントブロック）は**バイト単位で無変更**となり、
  チケットAC4（KLK-031と同一関数内で衝突しない差分の明示）を構造的に満たす。
- **正規化ポイントの集約（D2）:** `_ticket_lib.is_spec_basename` は厳密等価判定であり
  パターン照合の意味論を持たないため直接は使えない（investigation.md §1）。代わりに
  同じ正規化方式（`.upper()`）を用いるパターン照合版
  `is_spec_basename_fnmatch(pattern)` を `is_spec_basename` の直後に新設し、
  「SPEC.md判定の正規化は `_ticket_lib` に集約する」というKLK-020 D1／README addendum
  （「共有できる判定は `_ticket_lib.py` へ集約する」）の原則を維持する。
  これは `is_project_spec` が採った「basename部分のみcase-insensitive・
  ディレクトリ部分は大小区別維持」という部分適用の前例（KLK-020 D1のスコープ限定）と
  構造的に同型であり、「SPEC.md側のみcase-insensitive・active/done側は現状維持」という
  本チケットの要求と整合する。
- **KLK-031ゲートとの相互作用（D3、AC4対応）:** ゲート（`has_literal_char`）は
  「GUARDED_FILENAMEを `literals` に**追加するか**」を決めるレイヤー、本修正は
  「追加されたGUARDED_FILENAMEを**どう照合するか**」を決めるレイヤーであり、両者は
  直交する。リテラル文字0の成分（`*`・`**`・`*?`・`?*` 等）はゲートが先に
  GUARDED_FILENAMEを `literals` から除外するため、新しい比較には**到達しない**
  （`is_spec_basename_fnmatch("*")` 自体はTrueを返すが unreachable。この前提は
  ヘルパーのdocstringに明記し、unitテスト `_guarded_paths_from_expanded('*') == []` で
  固定する）。よってKLK-031の誤deny是正（`rm *`・`rm build/*` 等のallow）は
  そのまま保たれる。実装順序: develop HEAD `5fe3c4f`（KLK-031コミット `4c99758` を
  祖先に含む）の上に本修正を適用する。逆順（本修正が先）は起こり得ない
  （KLK-031はマージ済み）。

**修正後の判定例（机上トレース）:**
- `docs/sp*.md`: 最終成分 `sp*.md` はリテラル文字を含む→ゲート通過→
  `is_spec_basename_fnmatch("sp*.md")` = `fnmatchcase("SPEC.MD", "SP*.MD")` → True →
  `SPEC.md` へ置換→ `_is_guarded_path("docs/SPEC.md")` → True → 検出（`['docs/SPEC.md']`）
- `docs/Spec*.md`: 同様に True → 検出
- `rm *`: 成分 `*` はリテラル文字0→ゲートがSPEC.mdを除外→検出なし（KLK-031維持）
- `rm tickets/*`: GUARDED_DIR_NAMES側 `fnmatchcase("active", "*")` → True →
  `tickets/active` へ置換→検出（従来どおりdeny。GUARDED_DIR_NAMES側は無変更）
- `tickets/ACTI*E/APP-001.md`: `fnmatchcase("active", "ACTI*E")` → False →
  検出なし（GUARDED_DIR_NAMES側の大小区別が維持されることの証跡）

**代替案と却下理由:**
| 案 | 却下理由 |
|---|---|
| (A) 内側ループの比較を一律 `fnmatch.fnmatchcase(literal.upper(), component.upper())` に置換 | GUARDED_DIR_NAMES（active/done）側もcase-insensitive化され、チケットが明示的にスコープ外と指定した挙動（`tickets/ACTI*E/…` 等の非検出）を変えてしまう。却下 |
| (B) `literals` を `(literal, case_insensitive)` のタプル列に再構築し、ゲート行ごと書き直す | 機能的には同等だが、KLK-031で追加されたゲート行・コメントブロックの書き換えを伴い、AC4「同一関数内で衝突しない差分の明示」の検証コストと退行リスクを不必要に増やす。採用案はゲート行をバイト単位無変更に保てる |
| (C) `guard_bash_writes` 内にインラインで `fnmatchcase(GUARDED_FILENAME.upper(), component.upper())` を書く（ヘルパーを作らない） | 正規化方式（upper）が `is_spec_basename` と別の場所に重複実装され、KLK-020が是正した「独立実装のドリフト」再発パターン（本チケット自体がその5箇所目）をまた作る。README addendum「共有できる判定は `_ticket_lib.py` へ集約」（KLK-020 D3）にも反する |
| (D) `is_spec_basename` 自体を拡張してパターン照合も受け付ける（引数追加等） | 厳密等価判定とパターン照合は意味論が異なる（investigation.md §1）。既存4箇所の呼び出しの意味論を変えるリスクを負ってまで1関数に統合する利益がない。別関数の並置が安全 |
| (E) glob事前フィルタを廃止し置換総当たり＋`_is_guarded_path` 再評価だけに頼る | fnmatch照合は「フィルタ」であると同時に「どのliteralへ置換するかの決定」そのものであり、廃止すると置換候補が定まらない。構造的に不可能 |

### 4-1. `_ticket_lib.py`: ヘルパー新設＋import追加

**新関数**（`is_spec_basename` の直後・`is_project_spec` の直前に配置。
一意引用アンカー: `return isinstance(name, str) and name.upper() == "SPEC.MD"`）:
```python
def is_spec_basename_fnmatch(pattern):
    """glob パターン pattern が大小を区別せず 'SPEC.md' に fnmatch するか
    （KLK-032: guard_bash_writes._guarded_paths_from_expanded の SPEC.md 側
    glob 事前フィルタが大小区別を残す「5箇所目」だったことの是正。
    is_spec_basename のパターン照合版であり、正規化方式（upper）を
    is_spec_basename と同一に保つ単一の正規化ポイント）。

    注意: リテラル文字を1文字も含まないパターン（'*'・'**' 等）にも True を
    返す。呼び出し側の KLK-031 ゲート（has_literal_char。リテラル文字0の
    成分では GUARDED_FILENAME を照合対象に加えない）が先に除外する前提で
    あり、本関数は孤立ワイルドカードの扱いに関知しない（レイヤーを分離）。
    """
    return isinstance(pattern, str) and fnmatch.fnmatchcase(
        "SPEC.MD", pattern.upper())
```

**`is_spec_basename` docstring末尾への相互参照追記**（一意引用アンカー:
`SPEC.md 判定を一本化する単一の正規化ポイント）。"""`）: 閉じ引用の直前に

## 8. ロールバック戦略

Phase 1（コード）とPhase 2（テスト）を別コミットにすることを推奨するが、
変更が小さいため単一コミットでもよい。revertで完全に旧挙動へ戻る
（サイドカー等の状態は持たないため後処理不要）。

```bash
git revert {Phase2コミットハッシュ} {Phase1コミットハッシュ}
# 単一コミットの場合
git revert {実装コミットハッシュ}
```

注意: revertは誤allow（セキュリティホール: glob難読化＋小文字化による
人間承認ゲートのすり抜け）を意図的に再導入する操作であり、KLK-031の誤deny是正の
revert（利便性の後退のみ）とは性質が異なる。実施は人間の明示判断による。
