## 1. 目的

REQ/SCR/IF-ID: 該当なし（Kit自身の運用改善。KLK-007 reviewerレビューの非ブロッキングMedium指摘2件のフォローアップ）。

1. `render_event()` でサブエージェント発話（`parent_tool_use_id` 同伴の `assistant`/`user` イベント）の
   tool_use/tool_result表示に `[subagent:{label}] ` 接頭辞を付け、メインエージェントの発話と区別可能にする（Medium(1)）
2. `run_session()` の子プロセスstdout pipeを `finally` で明示closeし、長時間バッチ運用でのfd管理を
   GC任せから防御的多層化へ改める（Medium(2)）

いずれも表示品質・リソース衛生の改善であり、境界判定・終了コード・`run_session()` の外部契約には触れない。

## 2. 現状

investigator調査（docs/reports/KLK-008/investigation.md）より:

**現在のフロー（表示側）:**
```
render_event(evt):
  1. etype == "system"                    → init / task_started / task_notification を処理してreturn
  2. etype == "stream_event"              → text_delta を処理してreturn
  3. etype in ("assistant", "user")       → message.content の tool_use/tool_result のみ処理して
                                            無条件return。parent_tool_use_id/subagent_type を一切見ない ← AC1の対象
  4. フォールバック分岐（トップレベルtype一致 or "parent_tool_use_id" in evt）
                                          → 実スキーマの assistant/user イベントは 3 で先取りされ到達しない
```
VS-2実測（docs/batch-loop.md「stream-json下の追加実測」節）で、サブエージェント自身の発言は
`type: "assistant"/"user"` に `parent_tool_use_id`・`subagent_type` を伴って届くと確認済み。
つまり本問題は仮説ではなく実測確認済みの表示欠落（サブエージェントのツール操作が
メインエージェントと同じ `[tool]`/`[result]` 表示になり区別できない）。

**現在のフロー（pipe管理側）:**
```
run_session(cmd, root, timeout_min):
  proc = subprocess.Popen(..., stdout=subprocess.PIPE, ...)   # 明示closeは関数内に一切ない（GC任せ）
  reader = threading.Thread(target=_reader_thread, ...)        # readerも finally で eof sentinel を put するのみ
  try:
    while: queue.get(timeout=残り時間) → eofでbreak / timeoutで _terminate(proc) → return "timeout"
    code = proc.wait()
  except KeyboardInterrupt: _terminate(proc); raise
  return code, elapsed
```
`_terminate(proc)` は terminate → wait(10) →（残存時）kill → wait(5) と必ず子プロセスの終了を
待ち切ってから返る。したがって timeout/SIGINT いずれの経路でも `_terminate` 復帰時点で子はreap済み
（＝OS側でpipeのwriter側は閉鎖済み）。この事実が本設計のclose順序保証の根拠。

## 3. 設計方針

**採用する方針:**

1. **AC1（サブエージェント接頭辞）**: assistant/user 分岐の**内部で**、tool_use/tool_result の行生成より
   **先に**サブエージェント判定を評価し、判定結果の接頭辞を各表示行に前置するヘルパー
   `_subagent_prefix(evt)` を新設する。分岐自体の並べ替え（フォールバック分岐をassistant/userより
   前へ移動）は行わない（下記代替案の却下理由参照）
2. **Unknown 1（JSON構造: トップレベルか `message` 内か）の設計判断 — 両対応ルックアップで解消し、
   実装前の実機プローブは行わない**。判定は `evt.get("parent_tool_use_id") or
   message内.get("parent_tool_use_id")` の順で行う。根拠: (a) 本機能は表示専用でフェイルセーフ
   （位置の推定が外れても接頭辞が付かない＝現状と同等に留まり、境界判定・終了コードへの影響はゼロ）、
   (b) 両候補を数行でカバーでき、外れた場合の再フォローアップチケットを予防できる、
   (c) 実機プローブはAPI消費と人間監視を要しコストに見合わない。実スキーマでの最終確認は、
   docs/batch-loop.mdが既に義務づけている「人間監視下のパイロット実行」（V-4）に相乗りする
3. **判定はキー存在ではなく実値（truthy）で行う**。`"parent_tool_use_id" in evt` のキー存在判定だと、
   CLIがメインエージェントのイベントに `parent_tool_use_id: null` を明示付与するスキーマだった場合に
   全イベントへ誤って接頭辞が付く。truthy判定なら null/欠落のどちらでも誤発火しない
   （既存TestRenderEventのイベントは同キー自体を持たないため、いずれの判定でも既存テストは無改修通過）
4. **Unknown 2（ラベル取得優先順位）の設計判断**: `evt.get("subagent_type")` →
   message内 `subagent_type` → `evt.get("name")` → `"subagent"` の連鎖で確定する。
   第一候補 `subagent_type` はVS-2実測済みの `system`/`task_started` 分岐が既に同名フィールドを
   トップレベルで使用している実績に合わせる。`name` は既存フォールバック分岐との一貫性のために残す
   防御（実スキーマでの裏付けなしと調査で判明済みだが、害もない）。種別間の命名一貫性は未検証のまま
   だが、どのフォールバックに落ちても表示が壊れない連鎖なので設計上のブロッカーではない
5. **AC2（pipe close）/ Unknown 3（実装順序）の設計判断**: `run_session()` 全体を try/finally で包み、
   **「(i) 子プロセスreap保証 →(ii) リーダースレッドのEOF観測待ち（有限join）→ (iii) メインスレッドから
   `proc.stdout.close()`」の順序を finally 内で保証する**。(i) は正常経路では `proc.wait()`、
   timeout/SIGINT経路では既存の `_terminate()` が既に保証しており、finally冒頭の
   `if proc.poll() is None: _terminate(proc)` は想定外例外経路のための防御（多層化）。
   子がreapされればwriter側はOSレベルで閉じ、readerの `readline()` はEOFで自然終了するため、
   `reader.join(timeout=5)` は通常ミリ秒で返る。join後のcloseは「読んでいるスレッドがいない状態での
   close」となり、移植性の懸念（別スレッドがブロッキングread中のfdをcloseする挙動のOS依存性）を
   構造的に回避する。join(5) 超過という病的ケースでのみ最終手段としてclose（本環境では実測で無害と
   調査済み。fdリーク放置よりも安全側）
6. **`run_session()` の外部契約（引数・戻り値 `(exit_status, elapsed_sec)`）は不変**（AC3・CHANGELOG.md
   既存合意の維持）。elapsed は return 式評価時（finally実行前）に確定するため、join追加による
   計測値への影響もない。`_reader_thread`・`handle_stream_line`・境界判定は一切変更しない

**代替案と却下理由:**
| 案 | 却下理由 |
|---|---|
| フォールバック分岐（`"parent_tool_use_id" in evt` の分岐）をassistant/user分岐より前へ移動 | 実スキーマのassistant/userイベントでは `evt.get("message")` がdictでtruthyのため、同分岐の `text = evt.get("text") or evt.get("message")` がdictを `_brief` した無意味な表示になり、tool_use/tool_result のレンダリングも失われる。既存フォールバックテスト3件の意味も変質する |
| `with subprocess.Popen(...) as proc:` によるclose | `__exit__` が無条件・無同期に `self.stdout.close()` を呼ぶ（Python 3.12.3ソースで調査済み）ため、リーダースレッドがread中でもcloseされうる。さらにKeyboardInterrupt時は `self.wait()` をスキップする特殊分岐があり、close順序（reap後）を制御できない |
| `_reader_thread` 自身が finally でpipeをcloseする | closeがreaderスレッドの都合で非同期に起きるため、`run_session()` 復帰時点でのclose完了を保証できず、テストで決定的に検証できない（timeout経路ではrun_session復帰後にcloseされる競合窓が残る） |
| 実装前にVS的軽量プローブでassistant/userイベントの生JSON構造を実測 | 表示専用・フェイルセーフな機能に対しAPI消費と人間監視のコストが見合わない。両対応ルックアップで両候補を包含し、実機確認は義務づけ済みのパイロット実行（docs/batch-loop.md V-4）へ相乗りする方が総コストが低い |
| キー存在判定（`"parent_tool_use_id" in evt`）での発火 | メインエージェントのイベントに `parent_tool_use_id: null` が明示されるスキーマだった場合に全行へ誤接頭辞。truthy判定は null/欠落の両方で安全（方針3参照） |

**(1) `_subagent_prefix()` の新設と assistant/user 分岐の変更**

`render_event()` の直前（`_brief()` と `render_event()` の間）にヘルパーを追加する:

```python
def _subagent_prefix(evt):
    """assistant/userイベントがサブエージェント発話なら "[subagent:{label}] " を返す。
    そうでなければ空文字。判定は parent_tool_use_id の実値（truthy）で行う
    （メインエージェント側に parent_tool_use_id: null が明示されても誤発火しない）。
    フィールド位置はトップレベルを第一候補、message内を防御的な第二候補として両対応する
    （VS-2実測はprose記録のみで生JSONLがrepoに残っていないため。表示専用・フェイルセーフ）。"""
    msg = evt.get("message")
    msg = msg if isinstance(msg, dict) else {}
    if not (evt.get("parent_tool_use_id") or msg.get("parent_tool_use_id")):
        return ""
    label = (evt.get("subagent_type") or msg.get("subagent_type")
             or evt.get("name") or "subagent")
    return "[subagent:%s] " % label
```

assistant/user 分岐（アンカー: `if etype in ("assistant", "user"):`）を次のとおり変更する。
接頭辞の評価は行生成より先に行い、**各表示行**へ前置する（複数ブロック時も1行ごとに区別可能）:

```python
    if etype in ("assistant", "user"):
        prefix = _subagent_prefix(evt)  # tool_use/tool_result表示より先に評価（KLK-008 AC1）
        content = ((evt.get("message") or {}).get("content")) or []
        if not isinstance(content, list):
            return None
        lines = []
        for block in content:
            if not isinstance(block, dict):
                continue
            btype = block.get("type")
            if btype == "tool_use":
                lines.append(prefix + "[tool] %s(%s)" % (
                    block.get("name", "?"), _brief(block.get("input", {}))))
            elif btype == "tool_result":
                lines.append(prefix + "[result] %s" % _brief(block.get("content", "")))
        return "\n".join(lines) if lines else None
```

スコープ注意: text-only content（tool_use/tool_result なし）は従来どおり `None` を返す（表示対象を
拡大しない）。フォールバック分岐（アンカー: `if etype in ("task_started", "task_notification") or
"parent_tool_use_id" in evt:`）は将来スキーマ変化への防御として**無変更**で残す。
`render_event()` のdocstringへ「サブエージェント発話（parent_tool_use_id同伴のassistant/user）は
接頭辞で区別する（KLK-008）」の1〜2行を追記する。

**(2) `run_session()` の try/finally 再構成（変更後の全体像）**

```python
def run_session(cmd, root, timeout_min):
    """claude セッションを1つ実行し (exit_status, elapsed_sec) を返す。
    stdoutはパイプで受けてリアルタイムに進捗表示する（stderrは継承のまま）。
    exit_status はプロセス終了コード、タイムアウト時は文字列 "timeout"。
    stdout pipeは finally で必ず明示closeする（fd管理の多層防御。KLK-008 AC2）。
    close順序は「子プロセスreap → リーダースレッドのEOF観測待ち（有限） →
    メインスレッドからclose」を保証する（read中fdへの別スレッドcloseを構造的に回避）。"""
    start = time.monotonic()
    proc = subprocess.Popen(
        cmd, cwd=str(root), stdin=subprocess.DEVNULL,
        stdout=subprocess.PIPE, text=True, bufsize=1, errors="replace",
    )
    out_queue = queue.Queue()
    reader = threading.Thread(target=_reader_thread,
                              args=(proc.stdout, out_queue), daemon=True)
    reader.start()
    state = {"mid_line": False}
    deadline = start + timeout_min * 60 if timeout_min else None
    try:
        while True:
            if deadline is not None:
                remaining = deadline - time.monotonic()
                if remaining <= 0:
                    _terminate(proc)
                    return "timeout", time.monotonic() - start
            else:
                remaining = None
            try:
                kind, payload = out_queue.get(timeout=remaining)
            except queue.Empty:
                continue
            if kind == "eof":
                break
            handle_stream_line(payload, state)
        if state["mid_line"]:
            sys.stdout.write("\n")
            sys.stdout.flush()
        code = proc.wait()
        return code, time.monotonic() - start
    except KeyboardInterrupt:
        _terminate(proc)
        raise
    finally:
        # fd多層防御（KLK-008 AC2）: closeは必ず子プロセスreap後に行う。
        # 正常経路は proc.wait()、timeout/SIGINT経路は _terminate() がreapを保証済み。
        # 下のpoll判定は想定外例外で子が残った場合の防御（従来は子が残置されえた）。
        if proc.poll() is None:
            _terminate(proc)
        # 子reap済 → writer側閉鎖 → readline がEOFで自然終了するため通常は即返る。
        # join超過（病的ケース）でも最終手段としてcloseする（fdリーク放置より安全側）。
        reader.join(timeout=5)
        proc.stdout.close()
```

既存コードからの差分は「`return code, ...` を try 内へ移動（従来はexceptの後・関数末尾）」と
「finally 節の追加」のみ。while ループ本体・except 節は無変更。timeout経路の `return "timeout", ...`
も finally を通ってからreturnするため、全経路でcloseが保証される。elapsed の値は return 式の評価時点
（finally 実行前）で確定するため計測値は不変。

**処理フロー（変更後・pipe close順序）:**
```
1. 子プロセス終了の確定（proc.wait() 完了 / _terminate() 完了 / finallyの防御_terminate）

3. reader.join(timeout=5) でスレッド終了を確認（通常は即時）
4. proc.stdout.close() をメインスレッドから実行（読んでいるスレッドは存在しない）
```

変更は `scripts/batch_loop.py` と `tests/test_batch_loop.py` の2ファイルに閉じ、Phase単位のコミットで
独立にrevert可能（Phase 1=表示、Phase 2=pipe closeは相互依存なし）。

```bash
# 問題のあったPhaseのコミットのみを打ち消す（表示不具合ならPhase 1、fd/ハング系ならPhase 2）
git revert {該当Phaseのコミットハッシュ}
# developへのマージ後に全体を戻す場合
git revert -m 1 {マージコミットハッシュ}
```

表示側の不具合はバッチの安全性（境界判定・終了コード）に影響しないため緊急性は低い。
pipe close側で万一ハング・例外が出た場合はPhase 2のrevertで従来のGC任せ（実害未確認）へ即時復帰できる。
