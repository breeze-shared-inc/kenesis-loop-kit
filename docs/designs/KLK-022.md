## 1. 目的

本チケットはKit自身の内部改善でありSPEC.mdは不在（KLK-003・KLK-021等の前例に従う）。要件の正は
チケットKLK-022の受け入れ条件（上記AC1〜AC6）とする。

KLK-003が `start-loop.md` に適用した「全件フルリード→一覧CLI＋対象のみフル読み取り」への改訂
（`docs/designs/KLK-003.md`）が、直後に委譲される `.claude/commands/triage.md` の手順1には
未適用のまま残っている。本設計は、triage.md手順1を「CLI検出（候補ID抽出）→候補のみフル読み取り」
の2段階へ分割し、あわせてstart-loopからの委譲時に検出が二重に行われない導線を文面上に明示する。

## 2. 現状

**現在のフロー（`/triage` 単体実行・start-loop委譲のいずれの経路でも同一）:**
```
1. tickets/active/ の全チケットをフル読み取り（全チケットの本文・ログを含む）
2. 読み取った内容からLLMがstatus=blocked かつ 経過日数/ID一致 の条件でフィルタし一覧表示
3. 対象を人間に提示し三択確認 → 実行 → 結果報告
```
start-loop.md「14日超blockedチケットの検出」は既にKLK-003で一覧CLI化済みで候補IDを検出しているが、
その直後に「`.claude/commands/triage.md` の手順でトリアージしてからループへ進む」という表現で
triage.md手順1〜5全体に委譲しており、triage.md手順1が独自に全件フルリードを再度行う構造になって
いる（二重検出）。

## 3. 設計方針

**採用する方針:**

1. **triage.md手順1を「候補ID特定」の1手順のまま維持しつつ、内容をCLI検出（2経路分岐）に置き換え、
   候補のみのフル読み取りを新規の独立した手順として挿入する。** `scripts/list_tickets.py` の出力列に
   タイトル・ブロッカー内容が無いため、単純な「手順1をCLI呼び出しに置換するだけ」ではAC1が要求する
   一覧表示（ID・タイトル・ブロッカー内容・経過日数）を満たせない。したがって手順を6段階に再構成する:
   - 手順1: 候補チケットのIDを特定する（**起動経路に応じて2分岐**。詳細は§4）
   - 手順2: 候補が0件なら終了する（既存手順2と同じ判断だが、フル読み取り前に行う。CLI出力のみで
     判定可能なため、不要なフル読み取りを避けられる）
   - 手順3（新規）: 候補IDのみをReadツールでフル読み取りし一覧表示する（AC3の粒度明記そのもの）
   - 手順4〜6: 既存手順3〜5（三択確認・実行・結果報告）をそのまま踏襲（内容不変・番号のみ繰り下げ）

2. **start-loop.mdの委譲文言に「triage.md手順1をスキップし、検出済みの候補ID一覧を引き継ぐ」ことを
   明示する。** 現状「`.claude/commands/triage.md` の手順でトリアージしてから」という表現が
   手順1〜5全体を指しており、手順1（検出）の要否が曖昧だった（investigator指摘の核心）。
   triage.md側の新手順1が「start-loopから委譲された場合」の分岐を持つため、start-loop.md側にも
   対応する「手順1はスキップ」という明示的な参照を追加し、両ファイルの文言が相互に整合するようにする
   （AC2）。

3. **CLIへの絞り込み引数（`--status=blocked`等）は新設しない。** investigatorが特定した通り、
   `scripts/list_tickets.py` は `guard_bash_writes.py` の `mentions_guarded()` 非干渉のため
   パスを表す引数を一切持たない設計であり（KLK-003設計§3・KLK-021のT4固定テスト）、これは
   触れてはならない制約である。経過日数計算・ID一致判定は、start-loop.mdの現行運用と同様に
   引き続きLLM側推論（CLI出力の`updated`列を読んで計算）で行う。

4. **triage.mdに「メインworktreeで実行する」旨の注記を追加する。** triage.md手順1の単体実行経路が
   `scripts/list_tickets.py` を直接呼び出す設計になる以上、KLK-021がorchestrator.md/start-loop.mdに
   追加したのと同じcwd依存リスク（worktree内実行による対象取り違え）がtriage.mdにも生じる。
   単体`/triage`実行はorchestratorのメインworktree内で行われるのが通常の運用だが、明文化されて
   いないため、start-loop.md/orchestrator.mdと同じ注記を追加し一貫性を保つ（KLK-021完了後の着手を
   前提としたチケット本文の申し送り§関連 に対応）。

5. **機械検証テストは新規ファイル `tests/test_klk022_doc_wiring.py` を追加する。**
   `tests/test_klk003_doc_wiring.py` を拡張する案（KLK-021が採った前例）も検討したが、現時点の
   支配的な慣行は「1チケット=1新規doc-wiringテストファイル」であり（`test_klk004`・`test_klk017`・
   `test_klk025`・`test_klk026`・`test_klk027`の5ファイルが直近の前例、いずれも「既存ファイルは
   編集しない」と明記）、KLK-021が`test_klk003_doc_wiring.py`を拡張したのは「KLK-003が導入した
   *同じファイル・同じセクション*（policy-registry.mdの表）への検証観点の追加」という限定的な
   ケースだった。KLK-022は`triage.md`という*KLK-003が一度も触れていない別ファイル*を新たに検証
   対象にするため、拡張ではなく新規ファイルを切るほうが「1チケット=1ファイル」という支配的な
   慣行・スコープの明確な境界（Clear boundaries）に整合する（AC4）。

6. **`docs/policy-registry.md` の該当行（§2引用）へtriage.mdを追記する。** 同行の「実行責任者」列
   （現状「orchestrator / start-loop」）へ `/triage` を追加し、「転記先・強制」列へ
   `.claude/commands/triage.md 手順1` と新規テスト `tests/test_klk022_doc_wiring.py` を追加する。
   理由: triage.md手順1が本設計により`scripts/list_tickets.py`の新たな実行者・ドキュメント上の
   反映先になるため、既存原則（「実行責任者となるファイルに正を定義し、下表へ1行追加」）に照らして
   この行の実態を最新化するのが妥当（AC6）。なお同行の「転記先・強制」列が
   `tests/test_klk003_doc_wiring.py`・`tests/test_guard_bash_writes.py`（KLK-021追加分）を
   欠いているという既存の不備（investigator§6指摘）は、本チケットの変更と直接関係しない過去の
   ギャップであり、本チケットのスコープでは遡って追記しない（不要な書き換えを避ける・KLK-003の
   代替案却下理由と同じ判断基準）。

**代替案と却下理由:**

| 案 | 却下理由 |
|---|---|
| triage.md手順1を単純にCLI呼び出し1行へ置換する（分割しない） | `scripts/list_tickets.py`の出力列にタイトル・ブロッカー内容が無く、AC1が要求する一覧表示（ID・タイトル・ブロッカー内容・経過日数）を満たせない。分割が必須（investigator指摘の中核） |
| CLIへ`--status=blocked`等の絞り込み引数を新設する | `guard_bash_writes.py`の`mentions_guarded()`非干渉のため、CLIはパスを表す引数を一切持たない設計が必須制約（KLK-003設計§3・KLK-021 T4固定テスト）。新設は不採用 |
| `tests/test_klk003_doc_wiring.py`を拡張する | 同ファイルはKLK-003が導入したorchestrator.md/start-loop.md/policy-registry.mdの検証を主目的とし、KLK-021の拡張も同一ファイル・同一セクションへの観点追加という限定ケースだった。triage.mdは別ファイル・別スコープであり、直近5チケット分の支配的な慣行（1チケット=1新規ファイル）に従うほうが境界が明確 |
| start-loop.mdの委譲文言を変更せず、triage.md側だけで二重検出を回避する（例: triage.md手順1が「start-loopから委譲されたかどうか」を独力で判定する） | start-loop.md側が「手順（三択を人間に確認）でトリアージ」という手順1〜5全体を指す表現のままだと、triage.md単体で読んだ第三者（人間・将来のLLMセッション）が「手順1は省略可能」と判断する根拠がstart-loop.md側に残らない。AC2は「文面上で確認」を求めており、両ファイルの相互参照が必要 |
| triage.mdへの「メインworktree」注記を追加しない | 単体`/triage`実行経路がCLIを直接呼び出す設計になる以上、orchestrator.md/start-loop.mdと同型のcwd依存リスクが構造的に同一であり、注記なしでは一貫性を欠く（KLK-021が指摘したリスクと同型） |

def extract_section(text, heading):
    """`## {heading}` から次の `## ` 見出し（または末尾）までを抜き出す。
    tests/test_klk003_doc_wiring.py の実装を移植する。"""

    end = len(lines)
    for i in range(start, len(lines)):
        if lines[i].startswith("## "):
            end = i
            break
    return "\n".join(lines[start:end])
