# [KLK-031] guarded_paths_after_shell_expansionの孤立*グロブによるSPEC.md誤判定(誤deny) 設計

> このファイルはarchitectが生成・更新するチケット単位の設計書です。
> チケット KLK-031 に対応します。implementer・tester・reviewerが参照します。

## 1. 目的

`.claude/hooks/guard_bash_writes.py` の `_guarded_paths_from_expanded`（KLK-018で新設）は、
`/` 区切り成分が `GLOB_META_CHARS`（`*`／`?`／`[`）のみで構成される場合（孤立 `*`・
`dir/*` の末尾 `*`・`**`・`*?`・`?*` 等）、`fnmatch.fnmatchcase("SPEC.md", component)` が
成分の構造に関わらず常に（または長さ一致のみで）真になり、`tickets/`・`docs/SPEC.md` と
一切関係のない日常コマンド（`rm *`・`rm build/*`・`chmod 755 *` 等）を誤denyする
（本チケットに SPEC.md 上の REQ/SCR/IF は無い。要件の正はチケット KLK-031 の受け入れ
条件）。人間裁定により、この誤denyは KLK-018 §9 AC4(N2) の想定漏れとして是正対象と
確定している。

## 2. 現状

**現在のフロー（`_guarded_paths_from_expanded` 内、`index == last_index` の分岐）:**
```
guarded_paths_after_shell_expansion(text)
  → SHELL_EXPAND_PATHISH_RE.findall(text) で候補抽出
  → expand_braces(candidate) でブレース展開
  → _guarded_paths_from_expanded(expanded) で分断glob判定
      → path.split("/") の各成分に GLOB_META_CHARS が含まれるか判定
      → 含まれる場合、GUARDED_DIR_NAMES=("active","done") に対して
        fnmatch.fnmatchcase(literal, component) を試す
      → 成分が「最後の区切り成分」なら GUARDED_FILENAME="SPEC.md" も追加で試す
      → 成分が "*"（GLOB_META_CHARS のみで構成＝リテラル文字を1文字も含まない）
        の場合、fnmatchcase("active","*")／fnmatchcase("done","*")／
        fnmatchcase("SPEC.md","*") は**いずれも真**になる

        basename=="SPEC.md" で真になる（前段のディレクトリ文脈を問わない）

        偽のまま（この分岐は誤denyの原因になっていない。§3で実証）
  → is_guarded_token_expanded → mentions_guarded_expanded
  → statement_violation の gate_hit を True にする
  → head（rm/chmod/tar/cp/mkdir 等 ALLOWED_HEADS 外）だと segment_violation が deny
```

## 3. 設計方針

**採用する方針（精密な原因切り分けに基づく最小修正）:**

机上検証の結果、本バグの原因は `_guarded_paths_from_expanded` の **2つの分岐のうち
GUARDED_FILENAME（"SPEC.md"）側にのみ**あることを特定した。

- **GUARDED_DIR_NAMES（"active"/"done"）側は誤denyの原因ではない。** この分岐が
  `_is_guarded_path` を真にするには、置換後の文字列が文字通り `"tickets/active"`
  または `"tickets/done"` という部分文字列を含む必要がある。これは「置換対象の
  成分の直前に、既に候補中に literal `"tickets"` セグメントが存在する」ことを
  要求するため、`rm build/*` → 置換後 `"build/active"` は `"tickets/active"` を
  含まず _is_guarded_path は偽のまま（机上トレース済み・§6 Risksに再掲）。
  したがって `rm tickets/*` のように**既に "tickets/" という文脈を含む語**は
  この分岐で引き続き正しく deny される（これは誤denyではなく、`tickets/active`・
  `tickets/done` へ実際に展開されうる語への正当な言及検出であり、既存の
  安全性主張が保護すべき対象そのものである）。
- **GUARDED_FILENAME（"SPEC.md"）側が誤denyの唯一の原因である。** `_is_guarded_path`
  の SPEC.md 判定は `os.path.basename(path) == "SPEC.md"` という**ディレクトリ
  文脈を問わないbasename一致**であるため、成分が `"*"` のようにリテラル文字を
  1文字も含まない場合、fnmatch は「構造的に SPEC.md へ似ている」ことを一切
  検証せずに常に（または長さ一致のみで）真になり、`"build/SPEC.md"` のような
  無関係な組み合わせを誤って保護対象と判定する。investigator実測
  （`guarded_paths_after_shell_expansion("*")` → `["SPEC.md"]`）はこの分岐単独で
  再現しており、GUARDED_DIR_NAMES側の関与は無い。

このため、**修正はGUARDED_FILENAME（"SPEC.md"）を判定候補へ追加する条件にのみ
「成分がGLOB_META_CHARS以外の文字（リテラル文字）を最低1文字含むこと」を追加する**。
GUARDED_DIR_NAMES側は無変更のまま維持する（`fnmatch.fnmatchcase`自体や
`GLOB_META_CHARS`・`GUARDED_DIR_NAMES`・`GUARDED_FILENAME`・`_is_guarded_path`は
一切変更しない＝KLK-018が確立した「基盤シンボルは変更しない」文化を踏襲）。

**代替案と却下理由:**
| 案 | 却下理由 |
|---|---|
| (A) GLOB_META_CHARSのみで構成される成分は、GUARDED_DIR_NAMES・GUARDED_FILENAMEの両方から一律除外する（判定を成分ごとに単純化） | **却下。** GUARDED_DIR_NAMES側は本来誤denyの原因ではなく（上記トレース参照）、両方除外すると `rm tickets/*`・`rm -rf tickets/*` のように**既に"tickets/"という文脈を含む**危険なコマンドまで allow 化してしまう。ticket AC1が求めるのは「保護対象パスと**無関係な**コマンド」の誤denyの是正であり、"tickets/"文脈を持つ語の検出弱体化は求められていない。既存の安全性主張（false negative回避）を不必要に壊すため却下する |
| (B) `_is_guarded_path` のSPEC.md判定自体を「docs/直下のみ」等へ狭める | **却下。** `_is_guarded_path` は13箇所超から共有される基盤シンボルであり、KLK-018が「専用関数の新設＋OR追加」で回避した全呼び出し経路への波及を再度招く。またSPEC.mdをどこでも保護する現行仕様が意図的か否かは本チケットの調査範囲外であり、変更するなら別途の影響調査・チケットが必要 |
| (C) `_guarded_paths_from_expanded` 全体を「候補全体に"tickets/"または"SPEC"という部分文字列が含まれる場合のみ処理する」ように前置ガードする（成分単位ではなく候補単位のガード） | **却下（過剰かつ不正確）。** ブレース展開直後の文字列は既に`_is_guarded_path`の①判定（文字通り一致）で拾われており、②へ進む時点で候補は「①では一致しなかった」もの。候補単位で"tickets"/"SPEC"の部分文字列有無を見るガードを追加すると、"SPEC"というリテラルの有無だけで足りるはずの判定に対し、成分単位では意味を持たない候補全体の粗い事前フィルタを重ねることになり、可読性・保守性が(A)(採用案)より悪化する。成分単位のガード（採用案）の方が`_guarded_paths_from_expanded`の既存ループ構造にそのまま馴染む |

## 4. 実装詳細

### 4-1. コード修正（`.claude/hooks/guard_bash_writes.py`、`_guarded_paths_from_expanded` 内）

**変更対象（一意な引用文字列。`grep -cF` で1件のみ現存確認済み）:**
```python
        literals = list(GUARDED_DIR_NAMES)
        if index == last_index:
            literals = literals + [GUARDED_FILENAME]
```

**変更後:**
```python
        literals = list(GUARDED_DIR_NAMES)
        # KLK-031: 成分が GLOB_META_CHARS（*／?／[）のみで構成される場合
        # （孤立 `*`・`**`・`*?`・`?*` 等。リテラル文字を1文字も含まない）、
        # fnmatch は成分の構造的資格を一切問わず SPEC.md に常に（または長さ
        # 一致のみで）真になり得る。_is_guarded_path の SPEC.md 判定は
        # basename 一致でディレクトリ文脈を問わないため、これを許すと
        # `rm build/*`・`rm *` のような無関係な語まで「SPEC.md への言及」と
        # 誤判定してしまう（誤deny）。SPEC.md 側の判定対象に加えるのは、
        # 成分が GLOB_META_CHARS 以外の文字（リテラル文字）を最低1文字含む
        # 場合のみに限定する（"acti*e"・"SPEC*.md" 等の部分アンカー付き
        # パターンは従来どおり判定対象のまま）。GUARDED_DIR_NAMES
        # （active/done）側は変更しない — こちらは _is_guarded_path が
        # "tickets/active"／"tickets/done" という文字列そのものの隣接を
        # 要求するため、候補中に既に "tickets/" という文脈が無い限り誤って
        # 一致しない（詳細は docs/designs/KLK-031.md §3）。
        has_literal_char = any(ch not in GLOB_META_CHARS for ch in component)
        if index == last_index and has_literal_char:
            literals = literals + [GUARDED_FILENAME]
```

このパッチは `_guarded_paths_from_expanded` という単一関数内の1箇所のみを変更する。
`guarded_paths_after_shell_expansion` → `is_guarded_token_expanded` /
`mentions_guarded_expanded` の呼び出し階層はこの関数を経由する唯一の経路
（architect確認済み。`_guarded_paths_from_expanded` の呼び出し元は
`guarded_paths_after_shell_expansion` の1箇所のみ）であるため、
`is_guarded_token_expanded`／`mentions_guarded_expanded` の**現存する全呼び出し
箇所**（architect確認時点で `guarded_write_target`・`redirect_violation`・
KLK-019の`for`ループ変数追跡（guarded_loop_vars登録箇所）・`statement_violation`
（gate_hit算出の2分岐）・`degraded_violation`（関数レベルゲート・リテラル
リダイレクト判定・ステートメント単位ゲートの3箇所）・`subst_violation`の
計8箇所）に自動的に・一貫して波及する（受け入れ条件AC5）。呼び出し箇所自体
への変更は不要。implementerは実装後に
`grep -n "is_guarded_token_expanded\|mentions_guarded_expanded" .claude/hooks/guard_bash_writes.py`
で現存する全呼び出し箇所を再確認し、本節の列挙から漏れがないことを確認する
こと（将来別チケットで呼び出し箇所が増減してもこの構造的主張は自動的に
成り立つため、列挙自体は参考情報であり正ではない）。
