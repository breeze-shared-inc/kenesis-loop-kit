# [KLK-034] 否定文字クラス [^...] とPOSIX文字クラス [[:class:]] がpathish分断で検出されずSPEC.md操作が誤allowされる 設計

> このファイルはarchitectが生成・更新するチケット単位の設計書です。
> チケット KLK-034 に対応します。implementer・tester・reviewerが参照します。

## 1. 目的

対応要件ID: 該当なし（本リポジトリはKit自身のツールであり `docs/SPEC.md` が存在しない
ことを確認済み。KLK-020・KLK-031・KLK-032・KLK-033の前例に同じ。要件の正はチケット
KLK-034の受け入れ条件8件と `docs/reports/KLK-034/investigation.md`）。

bashのブラケット式は `[!...]` と **`[^...]`** の双方を否定として解釈し、さらにPOSIX文字
クラス `[[:upper:]]` 等を解釈する。`.claude/hooks/guard_bash_writes.py` の候補抽出正規表現
`SHELL_EXPAND_PATHISH_RE` の文字集合に `^`／`:` が無いため、これらを含む語は候補抽出の
段階で分断され、シェル実行時にはディスク上の `docs/SPEC.md` に一致するにもかかわらず
「保護対象パスへの言及なし」と判定されて人間承認ゲートをすり抜ける（誤allow=危険）。
本チケットは (1) 文字集合へ `^`／`:` を追加して分断を閉じ、(2) fnmatchへ渡す直前に
bashのブラケット式方言を吸収する正規化を新設して意味論の乖離を閉じる。あわせて
(3) KLK-033のreviewerレビューが指摘した記述の不正確（設計書§5/§7の不変条件・§8の
revert対象・docstringの重複）を是正する。KLK-020（SPEC.md判定の一本化）→ KLK-031
（`has_literal_char` ゲート）→ KLK-032（glob事前フィルタの大小区別）→ KLK-033
（`[!...]` の候補抽出）に続く系譜の、**同一ファミリの残存ベクタの一括閉塞**である。

## 3. 設計方針

**採用する方針: (1) `SHELL_EXPAND_PATHISH_RE` の文字集合へ `^` と `:` を追加し、
(2) fnmatch照合へ渡す成分だけを `_bash_bracket_to_fnmatch` で正規化する新関数を
`guard_bash_writes.py` に新設して `_guarded_paths_from_expanded` の照合2箇所へ配線する。
(1)(2)は同一Phase・同一コミットで適用する（結合必須。理由は代替案(F)）。
`GLOB_META_CHARS`・KLK-031ゲート・`PATHISH_RE`・`is_spec_basename_fnmatch` の判定式・
呼び出し階層はすべて無変更。**

### D1. `SHELL_EXPAND_PATHISH_RE` の文字集合拡張（`^`／`:` の追加と `GLOB_META_CHARS` 無変更）

最終形（既存集合の末尾＝`!` の直後に `^:` を追加する。investigator が実測に用いた
仮説形〔investigation.md §2-3〕とバイト単位で同一）:
```python
SHELL_EXPAND_PATHISH_RE = re.compile(r"[A-Za-z0-9_.\-/{},*?\[\]!^:]+")
```
- **追加位置の根拠:** Python `re` の文字クラス内で `^` が否定になるのは**クラスの先頭**の
  ときだけである。末尾（既存文字の後ろ）に置けば否定にならず、読み手が否定と誤読する
  余地も作らない。KLK-033が `!` を末尾に置いた判断と同じ理由づけ。
- **`:` も追加する根拠（追加しない案の却下）:** `:` はPOSIXクラスの閉塞には不足だが
  （D3）、**ブラケット式のメンバーとして `:` を含む合法なglob**（`docs/[:S]PEC.md`＝
  「`:` または `S`」の肯定クラス。bashは `docs/SPEC.md` に一致させる／
  `tickets/[:a]ctive/APP-001.md`。後者はinvestigation.md §4で実bash展開を実測済み）を
  閉じるために必要である。これらは `:` を足さない限り候補分断で永久に非検出のまま残る
  真の誤allowであり、`^` と同じファミリに属する。誤deny方向の副作用は§5・§9で固定する。
- **`GLOB_META_CHARS` は無変更（`^`／`:` を含めない）。根拠3点** — KLK-033 D1と同型:
  1. `^`／`:` 単体はglobメタ文字ではない。`^` が否定マーカーとして意味を持つのは
     ブラケット `[` の直後という文脈に限られ、その `[` は既に
     `GLOB_META_CHARS = frozenset("*?[")` に含まれる。成分 `[^x]PEC.md`・
     `[[:upper:]]PEC.md` は現状の `any(ch in component for ch in GLOB_META_CHARS)` を
     `[` で既に通過する。
  2. `^`／`:` を追加すると `has_literal_char`（KLK-031ゲート）がこれらを「リテラル文字
     ではない」と数えるようになり、ゲートの意味論（「構造的資格を持つ成分だけをSPEC.md
     照合の対象にする」）を変えてしまう（例: 成分 `[^` は現在 `has_literal_char=True`
     だが `^` をメタ扱いにすると `False` へ転じる）。KLK-031の誤deny是正の前提を触るため
     不可。
  3. `foo^bar`・`a:b` のような**globではない語**に対してもメタ文字ゲートが真になり、
     glob分岐（fnmatch照合＋文字列再構成）が不要に走る。挙動はdeny方向へ広がる可能性が
     あり、コストも増える。
- **`PATHISH_RE` は無変更。** `PATHISH_RE`（`is_guarded_token`／`guarded_paths` が使う
  リテラルパス抽出）を広げてはならない。理由2点: ① 13箇所超の呼び出し元の意味論を変える
  ② **候補分断規則の変更による非単調性を「glob成分を含む語」に閉じ込めている仕組みが
  `PATHISH_RE`（`^`／`:`／`!` を含まない）とのORそのものである**（KLK-033 reviewer
  レビュー §3-3）。ここを広げるとリテラル形の保護も分断規則の変更に巻き込まれる。

### D2. `[^` → `[!` 正規化の適用粒度と位置制約 —— **構造走査による位置依存置換／成分単位／`guard_bash_writes.py` 側**

**(a) 適用レイヤ = `/` 区切り成分ごと、照合に渡す値のみ。**
`_guarded_paths_from_expanded` のループ内で、`has_literal_char` ゲートを通過した**後**に
`match_component = _bash_bracket_to_fnmatch(component)` を1回計算し、
`lib.is_spec_basename_fnmatch(match_component)` と
`fnmatch.fnmatchcase(literal, match_component)` の**両方**へ渡す。
- 候補全体（ブレース展開前）やブレース展開後の文字列全体に適用しない理由: ブラケット式は
  パス区切り `/` をまたがない（filename globbingで `/` はブラケット式に一致しない）ため、
  成分単位が意味論的に正しい最小の適用単位である。全体適用にすると `/` をまたぐ
  ブラケット走査の妥当性という新しい未検証の前提を持ち込む。
- 再構成（`rebuilt`）は**正規化前の `components`** に `literal` を差し替える現行実装のまま
  （正規化は照合専用であり、検出結果として返るパスは従来どおり正規形 `docs/SPEC.md`）。
- `GLOB_META_CHARS` 事前フィルタと `has_literal_char` ゲートは**正規化前の成分**で行う
  （KLK-031の判定行をバイト単位で無変更に保つ。`^`／`:`／`!` はいずれもメタ文字集合に
  含まれないため、正規化の有無でゲートの結果は変わらない）。

**(b) 位置条件 = 「真にブラケット式の開始直後にある `^`」のみ。単純な部分文字列置換は使わない。**
investigation.md §3-2 の実測反例（`[a[^]one` は `[` をリテラルメンバーに含む合法な肯定
クラスであり、素朴な `re.sub(r"\[\^", "[!")` は `^one` に一致していたパターンを `!one` に
一致するパターンへ**意味反転**させる）を無効化するため、ブラケット式の構造を走査して
開始位置を確定させる。走査規則（bash／POSIX／Python `re` に共通の規則）:
1. ブラケット式の外側で `[` を見つけたら開始候補とする。
2. 直後の1文字が `!` または `^` なら否定マーカー（この位置の `^` だけを `!` へ置換する）。
3. 否定マーカーの直後の `]` はクラスの終端ではなく**リテラルメンバー**（Python `re` も
   同じ規則を持つ。investigation.md §3-1 で実測確認済み）。
4. 以降、最初の `]` が終端。**対応する `]` が見つからなければブラケット式ではない**
   （`[` はリテラル。bashも未閉塞ブラケットをglobとして展開しない。D4）。
5. ブラケット式の内部にある `[` は（`[:`／`[.`／`[=` の形を除き）単なるメンバーであり
   新しいブラケット式を開始しない → これが反例 `[a[^]one` を無効化する条件。

**(c) 置き場所 = `guard_bash_writes.py`（`is_spec_basename_fnmatch` 側には寄せない）。根拠4点:**
1. 正規化が必要なのは**SPEC.md側とactive/done側の両方**である（チケットの期待動作は
   「SPEC.md・tickets/active・tickets/done に一致しうるコマンド」を対象とし、
   investigation.md §5-3 は `rm tickets/[^x]ctive/APP-001.md` のdenyを要件に含む）。
   active/done側の照合は `guard_bash_writes.py` の `fnmatch.fnmatchcase` であり、
   `is_spec_basename_fnmatch` の内側に置くと**片側にしか効かない**。両側に効かせるには
   同じ正規化を2箇所で呼ぶことになり、KLK-020／KLK-032が是正した「独立実装のドリフト」
   を再生産する。呼び出し元で1回だけ正規化するのが最小かつ唯一の集約点である。
2. 本正規化は「SPEC.md判定の正規化」ではなく「**bash glob → Python fnmatch の方言変換**」
   であり、`_ticket_lib` が持つSPEC.md判定の正規化ポイント（`is_spec_basename`／
   `is_spec_basename_fnmatch`）とは関心が直交する。`_ticket_lib` は他hook
   （`validate_ticket_state.py` 等）からも使われる共通ライブラリであり、bash方言の知識を
   持ち込むべきレイヤーではない。
3. `is_spec_basename_fnmatch` の**判定式を無変更に保てる**（KLK-033の和集合形がそのまま
   正しく機能する: 正規化後の `[!x]PEC.md` は第1項でTrue、`[!S]PEC.md` は両項でFalse）。
   結果として `tests/test_ticket_lib.py` の既存6件は無変更でPASSし、AC4の回帰リスクを
   構造的に下げられる。
4. 正規化は `GLOB_META_CHARS`／`has_literal_char` と同じ「glob成分の扱い」の層にあり、
   その定数群と同じファイルに置くのが凝集度が高い。
   ただし `is_spec_basename_fnmatch` のdocstringには**呼び出し側契約**（正規化は呼び出し側
   が行い本関数は行わない）を1段落追記する（§4-4-4。記述の不正確を残さないため）。

### D3. POSIX文字クラス `[[:class:]]` の閉塞範囲 —— **本チケットで閉塞する（過大近似方式）**

**決定: 対応する。** チケットの受け入れ条件1（AC1）が `rm docs/[[:upper:]]PEC.md` の
検出・deny/askを明示的に要求しているため、別チケットへ送る選択は受け入れ条件を弱める
ことになり採れない（KLK-033 §3 代替案(E)＝別チケット起票型の運用は、そこでの残余が
「bashでも保護対象に一致しない形」＝実害のない残余だったから成立した。本件の残余は
**実在する誤allow経路**であり性質が異なる）。受け入れ条件3（AC3）が求める「閉塞範囲の
明示」は下記の対応表で満たす。

**閉塞方式: POSIXクラス／照合要素／等価クラスを含むブラケット式全体を `?` へ置換する
（過大近似＝deny方向）。**
- 健全性の根拠（provableな性質）: bashのブラケット式も fnmatch の `?` も「**任意の1文字**に
  対する述語」であり、`?` の一致集合は任意のブラケット式の一致集合の**上位集合**である。
  したがって `?` への置換で一致を失うこと（allow方向の劣化）は構造的に起こらず、誤りの
  向きはdeny＝安全側にのみ倒れる。
- 副次的な利点: bashの文字カテゴリがロケール依存であること・照合要素のサポート詳細が
  bashのバージョンに依存することに**依存しない**（未文書の挙動を「安全」と仮定せず、
  どちらに転んでもdeny方向になる方式を選ぶ）。
- 適用対象の構文: ブラケット式の内部に `[:name:]`（POSIX文字クラス）・`[.sym.]`
  （照合要素）・`[=c=]`（等価クラス）のいずれかが現れる場合。**先頭の `[` を伴わない
  `[:space:]` は POSIXクラスではなく「`:`・`s`・`p`・`a`・`c`・`e` の肯定クラス」であり
  （bashと同じ解釈）、置換の対象にしない**（`tr -d '[:space:]'` 型のイディオムを
  巻き込まないため。investigation.md §4の「ブラケット+コロンの合成」に対応）。
- 到達可能性の注記: `:` と `.` は文字集合に含まれるため `[[:class:]]`・`[[.sym.]]` は
  候補として到達するが、`=` は文字集合に含まれないため `[[=c=]]` は候補抽出の段階で
  分断され到達しない。走査規則の一貫性のため実装には含めるが（`":.="` の1文字集合として
  扱う）、テストで固定するのは到達可能な `[:` と `[.` のみとする。

**閉塞範囲の対応表（AC3の「どこまで対応しどこを既知の限界として残すか」の明示）:**

| ブラケット式の形 | bashの意味 | 本チケット後の扱い | 根拠 |
|---|---|---|---|
| `[abc]`・`[a-z]` | 肯定クラス・範囲 | 従来どおりfnmatchが解釈（無変更） | `-` は既に文字集合にある |
| `[!abc]` | 否定 | 閉塞済み（KLK-033） | fnmatchがPOSIX準拠で解釈 |
| `[^abc]` | 否定 | **閉塞（`[!` へ正規化）** | D2 |

| `[a[^]…` | 肯定クラス（`[`・`^` をメンバーに含む） | 意味を変えない（非置換） | D2(b) 規則5・investigation.md §3-2 |

### D4. 未閉塞ブラケットへの適用ポリシー —— **正規化・照合とも現行踏襲（挙動不変）**

**決定: 未閉塞ブラケット（対応する `]` が無い `[`）には正規化を適用しない。**
D2(b) の走査規則4がそのまま実現する（走査が終端を見つけられない場合は `[` をリテラルと
して出力し、変換しない）。理由3点:
1. bashは未閉塞ブラケットを含む語をglobとして展開せず語をそのままリテラルとして扱う
   （investigation.md §3-4）。正規化して否定クラスとして照合すると、bashが一切glob解釈
   しない語に対してhookだけが否定クラスの意味論を適用することになり、**bashより広い
   意味論**を持ち込む（誤deny方向の新しいクラス）。
2. Python `fnmatch.translate` も未閉塞の `[` をリテラルとして扱う（`\[`）。したがって
   非置換のまま照合すればhookとbashの解釈が一致する。
3. 現行実装は未閉塞ブラケット成分も `GLOB_META_CHARS` 事前フィルタを `[` で通過させて
   fnmatch照合に入れる。この点は**無変更**とする（`[` がリテラル扱いされるためfnmatchは
   ほぼ確実に不一致となり、挙動が変わらない）。フィルタ側に閉塞判定を持ち込むと
   KLK-031ゲートと同じ層に新しい条件が増え、既存の誤deny予算の前提を触る。

**挙動不変であることをテストで固定する**（§9④）。ただし現行挙動は本設計時点で
未実測（investigation.md §3-4 のUnknown）であるため、期待値はimplementerが実測して
固定する。設計の予測はallow（`rm docs/[^x`・`rm docs/[^xPEC.md` はbashでも保護対象に
一致しないためallowが正しい）。**実測がdenyだった場合は実測値どおりdenyで固定し
レポートに記載する**（向きは安全側であり設計変更は不要）。

### 4-2. `guard_bash_writes.py`: 正規化関数の新設

```python
# --- KLK-034: bash のブラケット式と Python fnmatch の方言差の吸収 -------------
#
# bash のブラケット式は `[!...]` と **`[^...]`** の双方を否定として解釈し、
# さらに POSIX の文字クラス `[[:upper:]]`／照合要素 `[[.sym.]]`／等価クラス
# `[[=c=]]` を解釈する。一方 Python の fnmatch（が生成する re）はクラス内
# 先頭の `^` を**リテラル**としてエスケープし（`[^x]` → `[\^x]` ＝「`^` または
# `x` のいずれか1文字」）、POSIX クラス構文を一切特別扱いしない
# （`[:upper:` を字面どおりの6文字集合として読む）。この乖離があるため、
# 候補抽出の文字集合へ `^`／`:` を足して分断を解消しただけでは
# `[^x]PEC.md` も `[[:upper:]]PEC.md` も検出できない
# （docs/reports/KLK-034/investigation.md §2）。fnmatch へ渡す**直前**に
# 方言を吸収する。変換規則は2つだけである:
#   ① 真にブラケット式の開始直後にある `^` を `!` へ置換する（fnmatch は
#      `[!...]` を POSIX どおり否定として解釈する）。**「開始直後」は
#      ブラケット式の構造走査で判定し、単純な部分文字列置換は使わない** —
#      `[a[^]one`（`[` をリテラルメンバーに含む合法な肯定クラス）で意味が
#      反転するため（investigation.md §3-2 の実測反例）。
#   ② POSIX クラス／照合要素／等価クラスを含むブラケット式は fnmatch では
#      等価に表現できないため、**ブラケット式全体を `?` へ置換する**。
#      ブラケット式も `?` も「任意の1文字」に対する述語であり、`?` の一致
#      集合は任意のブラケット式の一致集合の上位集合である。したがって置換で
#      一致を失うこと（allow 方向の劣化）は構造的に起こらず、誤りの向きは
#      deny=安全側にのみ倒れる。bash 側の文字カテゴリがロケール依存である
#      ことにも依存しない。
# 未閉塞のブラケット（`[^x` のように対応する `]` が無い形）は bash も glob と
# して展開せずリテラル扱いするため**変換しない**（挙動不変。§3 D4）。
# 本関数は照合に渡す値だけを書き換える。GLOB_META_CHARS の事前フィルタと
# KLK-031 の has_literal_char ゲートは**正規化前の成分**で行い（ゲートの
# 意味論を変えないため）、検出結果として返すパスも正規化前の成分から
# 再構成する。詳細は docs/designs/KLK-034.md §3 D2・D3。
BRACKET_CLASS_LEADERS = ":.="   # [: POSIXクラス ／ [. 照合要素 ／ [= 等価クラス


def _scan_bracket_expression(pattern, open_index):
    """pattern[open_index] == "[" として、ブラケット式の構造を走査する。

    戻り値は (終端 `]` の位置, 否定マーカーの位置 or None,
    POSIX クラス／照合要素／等価クラスを含むか) のタプル。対応する `]` が
    見つからない（＝ブラケット式ではない。bash もリテラル扱いする）場合は
    None を返す。走査規則は docs/designs/KLK-034.md §3 D2(b) を正とする。
    """
    n = len(pattern)
    i = open_index + 1
    negation_index = None
    if i < n and pattern[i] in "!^":
        negation_index = i
        i += 1
    if i < n and pattern[i] == "]":
        i += 1          # 否定マーカー直後の `]` はリテラルメンバー（規則3）
    has_class_element = False
    while i < n:
        if (pattern[i] == "[" and i + 1 < n
                and pattern[i + 1] in BRACKET_CLASS_LEADERS):
            leader = pattern[i + 1]
            end = pattern.find(leader + "]", i + 2)
            if end != -1:
                has_class_element = True
                i = end + 2
                continue
            # 閉じない `[:` 等は単なるメンバーとして読み進める（bash でも
            # 未定義動作。ここで打ち切らないことで終端 `]` の探索を続ける）
            i += 1
            continue
        if pattern[i] == "]":
            return i, negation_index, has_class_element
        i += 1          # 内部の `[` は新しいブラケット式を開始しない（規則5）
    return None


def _bash_bracket_to_fnmatch(pattern):
    """bash のブラケット式を Python fnmatch が同じ意味で解釈できる形へ
    書き換える（KLK-034）。`[` を含まない文字列はそのまま返す。

    ① 真にブラケット式の開始直後にある `^` を `!` へ（`[!` は変換不要＝冪等）
    ② POSIX クラス／照合要素／等価クラスを含むブラケット式全体を `?` へ
       （過大近似＝deny 方向。一致を失わない）
    未閉塞ブラケットは変換しない（挙動不変）。
    """
    if "[" not in pattern:
        return pattern
    out = []
    i, n = 0, len(pattern)
    while i < n:
        if pattern[i] != "[":
            out.append(pattern[i])
            i += 1
            continue
        scanned = _scan_bracket_expression(pattern, i)
        if scanned is None:
            out.append(pattern[i])      # 未閉塞 → リテラルの `[`（bash と同じ）
            i += 1
            continue
        close_index, negation_index, has_class_element = scanned
        if has_class_element:
            out.append("?")
        else:
            span = pattern[i:close_index + 1]
            if negation_index is not None:
                offset = negation_index - i
                span = span[:offset] + "!" + span[offset + 1:]
            out.append(span)
        i = close_index + 1
    return "".join(out)
```

## 7. マイグレーション戦略

移行手順は**なし**（定数名・関数シグネチャ・呼び出し階層はすべて無変更で、状態・データ・
設定ファイルを持たない）。ただし**判定の変化は単調ではない**ため、変化の両方向を明示する。

**(1) deny方向へ拡大する変化（意図した是正）**
- `[^...]` 否定クラスを含む語（`rm docs/[^x]PEC.md`・`rm tickets/[^x]ctive/APP-001.md`）
- POSIX文字クラス／照合要素を含む語（`rm docs/[[:upper:]]PEC.md`・`rm docs/[[.S.]]PEC.md`）
- ブラケットメンバーに `:` を含む語（`rm docs/[:S]PEC.md`・`rm tickets/[:a]ctive/…`）
- POSIXクラスの過大近似に起因する一部の誤deny（`rm docs/[[:digit:]]PEC.md` 等。§6）

**(2) allow方向へ転じる変化（非単調。「発生しない」とは書けない）**
`^`／`:` が glob メタ文字を含むrunに隣接して候補が結合される形では、以前は独立候補
だった glob 断片が構造条件を満たさなくなり **deny から allow へ転じる**
（`rm docs/SP*.md:1`・`rm docs/SP*.md^y`・`rm docs/:SP*.md`・`rm docs/^SP*.md`・
`rm tickets/acti*e:x/APP-001.md`・`rm tickets/acti*e^x/APP-001.md`）。これらは bash でも
保護対象に一致しない形であり、旧denyが誤denyだったことの是正である（KLK-033 で `!` を
追加したときに reviewer が実測した4形と同型。`docs/reports/KLK-033/review.md` §3-3）。
**変化の向きが是正であることと、「denyがallowへ転じない」という不変条件が成立しない
ことは別の主張である。後者は成立しない。**

**(3) allow方向へ転じる変化（正規化による精度向上）**
`^` の追加のみを行った中間状態では `[^S]PEC.md` が `is_spec_basename_fnmatch` 第2項の
偶然一致でdenyされるが、正規化を入れると `[!S]PEC.md` として評価され allow になる
（bashも `SPEC.md` に一致させないため正しい）。文字集合拡張と正規化を同一コミットで
入れるため、develop との比較では allow→allow（不変）である。

**(4) 非単調性が glob 成分を含む語に限定される仕組み**
`is_guarded_token_expanded(text) = is_guarded_token(text) OR
guarded_paths_after_shell_expansion(text)` であり、`is_guarded_token` が使う
`PATHISH_RE` は `^`／`:`／`!` を含まない。したがってリテラルの保護対象パスを含む語
（`rm docs/SPEC.md:1`・`rm tickets/active/APP-001.md:1`）は分断規則の変更に関わらず
検出される。影響を受けるのは `PATHISH_RE` では拾えない glob 成分側（`SP*.md`・
`acti*e` 等）だけである。**この仕組みを壊さないため `PATHISH_RE` は無変更とする。**

**(5) 確認方針**
§9⑥の差分挙動の実測（新旧対照）で (2) の転換形を網羅的に洗い出し、代表形を
根拠コメント付きでテストに固定する。(4) が保たれることもリテラル形のテストで固定する。
既存818件の全件PASS（回帰0）を Phase 1・Phase 2 の両方で確認する。

## 8. ロールバック戦略

**方針: Phase単位コミットを維持し（既存規約 `.claude/agents/implementer.md`「Git Rules」）、
revert時は「develop..HEAD の全コミットを列挙して逆時系列でrevertする（Phase 3 のみ除外）」
とする。** KLK-033 §8 が tester 追加コミットを列挙し忘れて revert 手順が壊れた
（`docs/reports/KLK-033/review.md` §3-4）ことの再発防止として、**testerが追加する
コミットも必ず revert 対象に含める**。テストコミットのハッシュは設計時に未定なので、
ハッシュを固定せず「列挙して全件」という手順で規定する。

```bash
# 1) 対象コミットを列挙する（マージ前は作業ブランチ、マージ後は develop で）
git log --oneline develop..HEAD          # マージ前
# git log --oneline --first-parent -n 20 # マージ後（マージコミットから遡る）

# 2) Phase 3（docs/designs/KLK-033.md の記述訂正）のコミットを除外し、
#    残り全部（Phase 1・Phase 2・tester が追加した全テストコミット）を
#    逆時系列（新しい順）でrevertする
git revert {testerコミット（複数あれば新しい順に全件）} \
           {Phase2コミット} {Phase1コミット}

# 3) revert後に必ず全件テストを実行し、旧挙動と旧テストの整合を確認する
python3 -m unittest discover -s tests -p "test_*.py"
```

注意点4つ:
- **testerコミットを必ず含める。** 本チケットのテストは修正後の挙動（`[^...]`・
  `[[:class:]]` のdeny）を固定するため、実装だけをrevertすると当該テストが失敗する。
  実施前に `docs/reports/KLK-034/implementation.md`・`test-report.md`・`review.md` に
  記録されたコミット一覧と `git log` を突き合わせ、漏れがないことを確認する。
- **Phase 3 は revert 対象に含めない。** `docs/designs/KLK-033.md` §5/§7/§8 の訂正は
  KLK-034 の実装とは独立に成立する事実訂正であり、戻すと「既存のdenyがallowへ転じる
  変化は構造的に発生しない」という**誤った不変条件の記述が復活する**（将来の文字集合
  変更時に真のdenyを黙って失う経路を作る）。
- **部分ロールバックは禁止。** Phase 1内の3変更（文字集合拡張・正規化関数の新設・
  照合への配線）はどれか一方だけを戻してはならない。文字集合拡張のみを残すと
  `[^s]PEC.md` が第2項の偶然一致でのみdenyされる非原理的な状態になり、正規化のみを
  残すと候補分断のため到達不能な死んだコードになる（§3 D2・代替案(I)）。
- revertは誤allow（否定文字クラス／POSIX文字クラスglobによる人間承認ゲートのすり抜け）を
  意図的に再導入する操作であり、実施は**人間の明示判断**による（KLK-032・KLK-033の
  ロールバックと同性質）。

サイドカー・状態ファイル・データ移行を持たないため、revert以外の後処理は不要。
