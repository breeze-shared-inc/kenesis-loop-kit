## 3. 設計方針

### 3-1. 採用する方針: 「強制主体の保存」を唯一の削除可否基準にする

削除対象を「冗長かどうか」ではなく「削除後もそのルールを強制する主体が残るか」で判定する。基準は次の3つ。

| 基準 | 内容 | 判定 |
|---|---|---|
| **K1** | hook（`.claude/hooks/*.py`）が機械強制している | 削除可 |
| **K2** | 同一ファイル内の別の節、または CLAUDE.md ポリシー管理表が「定義（正）」として指定する箇所に同内容がある | 削除可 |
| **K3** | K1・K2のいずれにも当たらず、削除するとそのルールの記述主体が消える | **残す**（特に失敗が不可逆・検出困難な場合） |

この基準は、CLAUDE.md「ポリシー管理の原則」の「ポリシーは、それを実行する責任者の定義ファイルに必ず記載する。『どこかに書いた』だけでは実行されない」と整合する。削除は**転記の削除**に限り、**正の削除は行わない**。

### 3-2. 変更の形式: Editツールのold_string完全一致による1項目1編集

行番号指定の一括削除（`sed -i` / Pythonワンライナー / 複数行まとめたEdit）は**禁止**する。理由は §2 の非連続削除7箇所で誤削除が起きること。Editツールは文字列一致で動作するため行番号のずれに影響されず、対象行が1文字でも違えばエラーになる（= 誤削除の構造的な予防になる）。§4に**全項目の変更前テキストを一字一句**記載し、implementerはそれをold_stringにコピーする。

### 3-3. AC1の圧縮形式: 括弧内の列挙のみをhookポインタへ差し替える（最小diff）

5ファイルの該当行は、6ベクトルの列挙が**同一の括弧内文字列**として現れる。この括弧だけを置換対象にすることで、ファイルごとに異なる文脈（orchestratorの「読み取り・mvは可」、implementer/testerの「report to orchestrator instead」、investigator/reviewerの「read-only」）を無変更で保存できる。禁止ルールの本体（`any write vector`）はNeverに残るため、CLAUDE.md 170行の転記先「各agents/*.md Never」は維持される。

### 3-5. その他の設計判断（D2・D4）

**D2: tester.md 36行 `- Do not change architecture or design` は「削除」する。**
AC4の「（Do not modify production codeに包含）を整理する」という括弧書きに従い、包含関係を根拠に削除と解釈する。根拠はK2で、(i) 35行 `- Do not modify production code` が architecture/design を変更する唯一の手段（プロダクションコードの改変）を既に禁止している、(ii) 同ファイル Ticket Integration 51行「testerのWrite/Editはテストコード専用である」が設計書・チケットへの書き込みを封じている。よって独立した禁止として保持する必要がない。代替案「`Do not modify production code or design documents` へ統合（文言整理のみ）」は、行数が減らず(ii)と二重記載になるため却下。**なおこれはAC4の一義的でない部分の解釈であり、1行・可逆の差分である**（人間が「文言整理のみ」を意図していた場合は1行の復元で足りる）。AC4を弱めるものではない（削除も「整理」の一形態であり、禁止内容は35行で維持される）。

**D4: CLAUDE.md 162行への対処は「(a) 許容して残置し申し送り」。ただし前提の見直しを含む。**

**編集方法（全項目共通・必須）:**
1. **Editツールのみを使う。** `sed -i`・Pythonワンライナー・行番号指定の一括置換は使わない（§3-2）
2. **削除は1行1Edit。** `old_string` に「対象行のテキスト＋末尾の改行」、`new_string` に空文字列を指定する。連続行でも1行ずつ行う（誤削除の早期検出のため）
3. `new_string` を空にできない場合の代替: 直前の**残す行**と対象行の2行を `old_string` に、直前の残す行のみを `new_string` に指定する（隣接行のテキストは本節の「変更後の節（全文）」から取得する）
4. 各Edit後、その節の「変更後の節（全文）」と一致するかを目視確認する
5. **1つでもEditが権限拒否された場合は、そのファイル以降の作業を中止し、直ちにorchestratorへ報告する**（R1）。本節の全文言は人間が手で適用できる形式で記載されている

### 4-0. AC1: Bash書き換えベクトル列挙の圧縮（5ファイル・一字一句）

置換は**括弧内のみ**。全5ファイルで `old_string` は同一文字列（各ファイル内で1回だけ出現）。

```
old_string: (redirect, `sed -i`, `tee`, interpreter one-liners like `python3 -c`, `find -exec`, heredoc)
new_string: (denied by .claude/hooks/guard_bash_writes.py)
```

圧縮後の行全体（ファイルごと・行頭の `- ` を含む一字一句）:

**`.claude/agents/orchestrator.md` 163行目**

## 7. マイグレーション戦略

データベース・API・外部インターフェースの移行対象は**なし**（Markdownドキュメントのみの変更）。ただし次の2点を運用上のマイグレーションとして明記する。

1. **有効化タイミング:** worktree内の変更はdevelopへマージされるまで実行時のエージェント定義に影響しない。マージ後、**次回のサブエージェント起動時**から新しい定義が読み込まれる。本チケットを処理している実行中のセッション（orchestrator・implementer自身）のコンテキストには旧版が残る。削除した29行はすべて転記であり正とhookが残るため、旧版セッションと新版セッションで**行動規範に差は生じない**（K1/K2基準を採ったことの副次効果＝後方互換が自動的に保たれる）。
2. **段階的移行:** 最大の削減候補である Priorities節（35行相当）は本チケットで手を付けず、適用後の差し戻し率・リトライ消費を `/metrics` で観測してから別チケットで再評価する。参照2箇所（`docs/designs/KLK-007.md:159`・`docs/batch-loop-inline.md:11`）の差し替えを含む作業になるため、スコープを分ける（§3-4 D1#1・§3-5 D5）。

## 8. ロールバック戦略

**Phase単位コミットのため、Phase粒度で戻せる。**

```bash
# 個別Phaseの取り消し（worktree内。{hash} は該当Phaseのコミット）
cd ../kenesis-loop-kit.wt/KLK-009 && git revert --no-edit {hash}

# 未マージ段階での全体破棄（orchestratorが実施。develop は無傷）
git worktree remove ../kenesis-loop-kit.wt/KLK-009
git branch -D feature/KLK-009-{slug}

# develop へマージ後の取り消し
git revert -m 1 {マージコミットのhash}
# done化後に問題が発覚した場合は /rollback KLK-009（done → implementation_done）
```

**部分適用の安全性（R1で途中停止した場合）:** 6ファイルは相互に独立で、削除は転記の削除のみ。**1ファイルだけ適用された中間状態でも運用上の不整合は生じない**（強制主体は各正とhookに残る）。したがってPhase 1のみ適用・コミット済みの状態を「そのまま残して再開を待つ」判断も可能で、ロールバックは必須ではない。

**人間が §4 の文言を手で適用した場合:** `git diff` の結果を §4 の「変更後の節（全文）」と照合すれば正当性を検証できる（V-5〜V-9をそのまま適用可能）。
