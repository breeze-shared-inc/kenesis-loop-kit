# [KLK-002] エージェント定義へのモデル指定追加 設計

> このファイルはarchitectが生成・更新するチケット単位の設計書です。
> チケット KLK-002 に対応します。implementer・tester・reviewerが参照します。
> spec_version は「n/a」: 本チケットは docs/SPEC.md を持たないKit自身の改善であり
> （KLK-001と同様の前例）、REQ/SCR/IF-ID の参照は該当なし。要件の正はチケット本文の
> 受け入れ条件そのもの。

## 1. 目的

REQ/SCR/IF-ID: 該当なし（docs/SPEC.mdを持たないKit自身のトークン最適化改善）。
全エージェント定義（`.claude/agents/*.md`）の `model` frontmatterが未指定（inherit）のため、
機械的作業を担うtester・investigatorを軽量モデル（`sonnet`）へ明示的に割り当ててループ1周あたりの
コストを削減する。一方、判断品質がリトライ回数を左右するarchitect・reviewer・implementerは現状維持
（未指定=inherit）とし、その判断根拠と、モデル割当方針全体（誰にどれを割り当て、いつ見直すか）を
各エージェント定義ファイルから読み取れる形で明記する。

## 2. 現状

**現在のフロー:**
```
6エージェント定義ファイル（.claude/agents/*.md）は全てfrontmatterに model 未指定
  → 全サブエージェントがメインセッションと同じモデルで起動（inherit）
  → 役割ごとの判断負荷（機械的検証 vs 設計/レビュー判断）を反映した割当が存在しない
```

**関連する既存ファイル（investigator調査メモより）:**
- `.claude/agents/tester.md` / `investigator.md` / `architect.md` / `reviewer.md` / `implementer.md`:
  frontmatterは `name` / `description` / `tools`（+investigatorのみ `skills`）のみ。`model` キー無し。
  `tools` は文字列スカラー、`skills` はYAMLリストという混在書式が既に存在するため、`model` 行の追加
  はYAML構造上安全（investigator実パース確認済み）。
- `.claude/agents/orchestrator.md`: 本チケットの対象外（サブエージェントとしてではなくメインスレッド
  として起動する運用のため、`model` frontmatterの意味が他5ファイルと異なる。変更しない）。
- 公式ドキュメント（code.claude.com/docs/en/sub-agents、investigator 2026-07-19取得）: `model` の
  許容値は `sonnet` / `opus` / `haiku` / `fable` / フルモデルID / `inherit`。省略時は `inherit`。
  解決優先順位は `CLAUDE_CODE_SUBAGENT_MODEL` 環境変数 > 呼び出し時引数 > frontmatter > メイン
  セッションモデル。許可リスト外の値は無音で `inherit` にフォールバックしうる（起動失敗するかはUnknown、
  ただし今回は文書化済みの値 `sonnet` のみを使うため非該当）。
- `orchestrator.md`「リトライカウンタ管理」: tester起因の差し戻し上限が3回で最も高く「機械的な検証」
  という根拠記述が既にある。reviewer→investigator上限は1回で全経路中最低。investigator自身には
  「判断負荷が低い」根拠記述が無く、確信度判定・矛盾処理・breaking-change検出という非機械的判断要素
  を含む（investigatorが明示的に申し送った非対称性）。
- CLAUDE.md「ポリシー管理の原則」: 新規ポリシーは「定義ファイルに正を書き、CLAUDE.mdの表へ1行追記
  する」という自己統治ルールを持つ。本チケットが導入する「モデル割当の方針」はこの意味での新規ポリシー
  に該当すると判断する（3節参照）。

## 3. 設計方針

**採用する方針:**

1. **`model: sonnet` はtester.md / investigator.mdのfrontmatterにのみ追加し、他4ファイル
   （architect / reviewer / implementer / orchestrator）のfrontmatterは変更しない**
   - `sonnet` はチケットAC1が例示する値をそのまま採用する（human承認済みの前提。haiku等への
     変更は本設計では提案しない）
   - architect/reviewer/implementerは「未指定=inherit」を維持するとAC2が明示しており、
     `model: inherit` を明示的に書き込むのではなく、キー自体を追加しない（現状のバイト単位の
     挙動を完全に保持する）

2. **判断根拠と見直しトリガーは、frontmatterではなく本文の新設セクション「## Model Assignment」
   に1〜2文で記述する。位置はH1タイトル直後・`## Goal` の直前に、6ファイル中5ファイル
   （orchestrator.mdを除く）へ統一的に追加する**
   - frontmatterはキー:値の宣言のみに留め、説明文はYAML構造に混ぜない（既存の混在書式を壊さない）
   - AC2は architect/reviewer/implementerの根拠明記のみを要求するが、investigatorが申し送った
     「investigator軽量化の非対称性」に対応するため、tester/investigatorにも同形式の根拠＋見直し
     トリガーを対称的に記載する（ACを弱めず、ACが要求する開示レベルを6ファイルへ拡張する追加対応。
     テスト観点はAC2の3ファイルに絞って良い）
   - 各ファイルの文面は4節「実装詳細」に確定文面として記載する

3. **モデル割当の「全体方針」は各エージェント定義ファイルに分散配置し、単一の新規ドキュメントは
   作らない。CLAUDE.md「ポリシー管理の原則」表へは1行のみ追記し、定義の正が各agents/*.mdである
   ことを示すポインタとする**
   - CLAUDE.mdの自己統治ルール（本文セクションを増やさず表1行のみ追記）にそのまま従う
   - AC3「モデル割当の方針が定義ファイルから読み取れる」は、各ファイルの「## Model Assignment」
     節を横断して読めば充足する。新規の中央ドキュメント（例: docs/model-assignment-policy.md）
     を作るのは「新しい抽象化の導入」に当たり、既存の役割分担（各エージェントファイルが自分の
     ルールを持つ）から逸脱するため採用しない

4. **frontmatterの健全性（AC4）は、目視確認に加えて自動テストで継続的に担保する
   （`tests/test_agent_frontmatter.py` を新設）**
   - 単純な1行追加のdiffであっても、YAML破損の検出を人手だけに委ねない（プロジェクトの既存慣行:
     `tests/` にstdlibのみのunittestを揃え、CIに自動で乗る）
   - 将来モデル割当を見直す際の回帰防止ガードにもなる（見直しトリガー発火時の安全網）

**代替案と却下理由:**
| 案 | 却下理由 |
|---|---|
| architect/reviewer/implementerのfrontmatterに `model: inherit` を明示追加する | AC2の「未指定=inherit」という文言に反する。明示追加は将来の解決順位変更時に挙動が変わるリスクをわずかに増やすだけで得るものがない |
| 判断根拠・見直しトリガーをfrontmatterのコメント（YAMLには存在しないコメント構文の代用）に書く | frontmatterはツールがパースする構造化データであり、説明文を混ぜると将来のパーサ変更で壊れるリスクがある。本文セクションの方が安全かつ可読 |
| 新規ドキュメント docs/model-assignment-policy.md を作り全体方針を集約する | 「新しい抽象化を導入しない」制約に反する。AC3は各定義ファイルから読み取れれば足り、既存の1エージェント=1ファイルの役割分担とも整合しない |
| tester/investigatorには根拠note を追加しない（AC2の3ファイルのみ） | investigatorが明示的に指摘した非対称性（非機械的判断要素・reviewer→investigator上限1回という低耐性）への対応が設計に残らない。将来の見直し判断が属人化する |
| frontmatterの健全性確認を目視のみで済ませる | 1行追加でも将来の再編集（見直しトリガー発火時）で壊れる可能性があり、既存のテスト整備慣行（tests/配下のstdlib unittest）からも外れる |
