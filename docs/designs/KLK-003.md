# [KLK-003] orchestratorチケット読み取りのfrontmatterスキャン化 設計

> このファイルはarchitectが生成・更新するチケット単位の設計書です。
> チケット KLK-003 に対応します。implementer・tester・reviewerが参照します。

## 1. 目的

本チケットはKit自身の内部改善であり `docs/SPEC.md` は不使用（先行チケットKLK-001投稿時に人間承認済み）。要件の正はチケットKLK-003の受け入れ条件（AC1〜AC5、下記§9に転記）である。

orchestratorは作業開始時に `tickets/active/` を全件フル読みする（`.claude/agents/orchestrator.md` Ticket Integration「作業開始時: tickets/active/ を全件読み取り、priority順に処理対象を選択」）。これはチケット数×ログ長に比例する固定トークン費が毎ループ発生する構造的な非効率である。本設計は、frontmatter（id / status / priority / retry_counts / updated）のみをコンパクトな一覧として出力するCLI `scripts/list_tickets.py` を新設し、「一覧CLIで処理対象を選択 → 対象1件だけReadツールでフル読み取り」という二段階のフローへ改める。

## 2. 現状

**現在のフロー（orchestrator 作業開始時）:**
```
1. tickets/active/*.md を全件 Read ツールでフル読み取り（frontmatter + 本文 + ログ全文）
2. 読み取った全チケットの status / priority を人手（LLM推論）で比較
3. 処理対象を1件選び、次エージェントへ委譲
```
チケット数が増える・ログが伸びるほど、手順1の固定コストが線形に増加する。start-loop.md の起動時チェックリスト（14日超blocked検出・in_progress上限チェック）も同様に「tickets/active/ の全チケットを読み取り」という同じ全件フルリードを行っている。

**関連する既存ファイル:**
- `.claude/hooks/_ticket_lib.py`（`def split_frontmatter(text):` / `def parse_frontmatter(text):` / `def is_ticket(path):` と定数 `VALID_STATUS`/`RETRY_CAPS`/`IN_PROGRESS_STATUSES`/`IN_PROGRESS_LIMIT`）— 純粋なライブラリでCLI/argparse/`__main__`を持たない。5つのhookスクリプトから直接importされる共有基盤であり、本設計ではこのファイル自体は変更しない（§3参照）
- `.claude/agents/orchestrator.md`（見出し `## Responsibilities` の `- Read tickets/active/ and determine next action`、見出し `## Ticket Integration` の `- 作業開始時: tickets/active/ を全件読み取り、priority順に処理対象を選択`）
- `.claude/commands/start-loop.md`（見出し `## 起動時チェックリスト（必須・スキップ禁止）`、見出し `## ループ実行手順`）
- `scripts/batch_loop.py`（`_ticket_lib`を`sys.path.insert`でimportするCLIの前例。`main(argv=None, root=None)`のシグネチャ、引数はチケットIDのみでパスを引数化しない設計 — 本設計が踏襲する直接の前例）
- `.claude/metrics/aggregate.py`（同じく`_ticket_lib`をimportする別ファイルCLIの前例。日本語の人間可読テキスト出力）
- `.claude/hooks/guard_bash_writes.py`（定数 `ALLOWED_HEADS = {` / `READONLY_SCRIPTS = (`、関数 `def is_guarded_token(token):` / `def mentions_guarded(command):`）— Bashコマンド文字列が `tickets/active` または `tickets/done` という部分文字列を含むトークンを持つ場合のみ発動する。新CLIの呼び出し方次第でこのhookとの相互作用が生じる（§3で設計判断）
- `tests/test_batch_loop.py` / `tests/_util.py` / `tests/test_ticket_lib.py`（テストの前例）

## 3. 設計方針

**採用する方針:**

1. **新規スクリプト `scripts/list_tickets.py` を追加する**（`_ticket_lib.py` へのサブコマンド追加ではない）。`_ticket_lib.py` は5つのhookスクリプトが直接importする純粋な検証ライブラリであり、CLI/argparseを持ち込むとこの共有基盤の責務が肥大化し、テスト・レビューの負担を増やす。既存の2前例（`scripts/batch_loop.py`、`.claude/metrics/aggregate.py`）はいずれも「別ファイルから`_ticket_lib`をimportするCLI」という形を取っており、これに倣う。`scripts/`配下を選ぶ理由: `.claude/hooks/`はsettings.jsonに登録された PreToolUse/PostToolUse/Stop hook専用ディレクトリであり（`.claude/hooks/README.md`表に厳密に対応）、一覧CLIはそのいずれのイベントにも該当しない一般ユーティリティである。`.claude/metrics/`はメトリクス集計専用であり、本CLIはメトリクスではなくチケット一覧なので用途が異なる。`scripts/`は`batch_loop.py`と同様「人間またはorchestratorが直接Bash実行する運用スクリプト」の置き場として適切。

2. **CLIはパスを表す引数を一切持たない。** `python3 scripts/list_tickets.py`（引数なし）で常に `<リポジトリルート>/tickets/active/` を対象にする。リポジトリルートは `scripts/batch_loop.py` と同じ手法（`Path(__file__).resolve().parents[1]`）で自己解決する。テスト用に `main(root=None)` というPython関数引数（CLI引数ではない）でルートを注入できるようにする（`batch_loop.py`の`main(argv=None, root=None)`と同じ設計）。

   **理由（guard_bash_writes.pyとの相互作用の解消）:** `.claude/hooks/guard_bash_writes.py` の `mentions_guarded()` は、Bashコマンド文字列のいずれかのトークンが部分文字列として `tickets/active` または `tickets/done` を含む場合にのみ以降の検証（`ALLOWED_HEADS`/`READONLY_SCRIPTS`）を発動させる。CLIをパス引数なしで呼び出す設計にすれば、Bashコマンド文字列 `python3 scripts/list_tickets.py` はどのトークンにも `tickets/active`/`tickets/done` という部分文字列を含まない（スクリプトパス自体は `list_tickets.py` であり `tickets/active` という連続した文字列を含まない）。したがって `mentions_guarded()` は False を返し、hookは即座に allow する。**この設計を採ることで `guard_bash_writes.py` の変更（`READONLY_SCRIPTS` へのスクリプト登録）は一切不要になる**（investigatorが指摘した重要リスクの解消策）。将来この制約を破ってパスを引数化する変更を行う場合は、`guard_bash_writes.py` の `READONLY_SCRIPTS` にスクリプトパスを追加する変更が必須になることをスクリプト冒頭のdocstringに明記する（`batch_loop.py`が同じ理由を明文化している前例に倣う）。

3. **出力はJSONではなく整形済みプレーンテキスト。** リポジトリ内にJSON出力CLIの前例はなく（`aggregate.py`は日本語テキスト出力）、消費者はLLM（orchestrator）でありJSONの構文オーバーヘッド（クォート・括弧）はトークン削減という本チケットの目的に反する。列固定幅のテーブル1行＝1チケットとし、`retry_counts`は`lib.RETRY_CAPS`のキー順（`tester_to_implementer`→`tti`、`reviewer_to_implementer`→`rti`、`reviewer_to_investigator`→`rtv`）で3列に展開する。冒頭に凡例行 `tti=tester→implementer rti=reviewer→implementer rtv=reviewer→investigator` を1行出力し、略称の対応を明示する。

4. **priority順ソートはCLIが担わない。** `priority`（high/medium/low）の列挙・順序を表す定数はコード上どこにも存在しない（`.claude/commands/plan-tickets.md` 見出し `### 3. 分割案の作成` 内の `- **priority** はMoSCoWからマッピングする` という文書上の慣習のみ）。ここで新たに順序定数を導入するのは「新しい抽象化の追加」であり、AC1の文言（一覧を出力する）を満たすために必須ではない。CLIは`id`（≒ファイル名）の昇順という機械的で決定的な順序でのみソートし、priorityに基づく処理対象の選択はorchestrator（LLM）が一覧を読んだ上で行う（investigatorのUnknown③の判断: 単純一覧＋LLM側ソートを採用）。

5. **malformed frontmatterは黙ってスキップしない。** 1ファイル＝必ず1行を出力する（データ行またはERROR行のいずれか）。`validate_ticket_state.py` の `def count_other_in_progress(path):`（frontmatterのparse失敗を `except Exception:` で握りつぶして `continue` する）ではなく、`batch_loop.py`の`read_entry_at`（エラー理由を明示的に返す）の流儀を踏襲する。理由: 本CLIは「orchestratorがどのチケットを処理するか選ぶための唯一の一覧」であり、破損チケットが一覧から静かに消えると、orchestratorがそのチケットの存在自体を見落とすリスク（Operational safetyへの影響）がある。ERROR行として可視化し、orchestratorに当該チケットの個別フル読み取り（原因調査）を促す。CLI自体の終了コードは0のまま（ERROR行があってもツール全体は失敗させない。tickets/active/ディレクトリが存在しない場合のみ終了コード1の致命的エラーとする）。

**代替案と却下理由:**

| 案 | 却下理由 |
|---|---|
| `_ticket_lib.py` へサブコマンド追加（argparse組み込み） | 5つのhookが直接importする共有ライブラリにCLI関心を混ぜ込むと責務が肥大化し、テスト・レビューの負荷が増す。既存2前例（batch_loop.py, aggregate.py）はいずれも別ファイル形式 |
| CLIに `--dir`/`--path` 等でtickets/activeのパスを引数化 | Bashコマンド文字列に `tickets/active` というリテラルが混入し、`guard_bash_writes.py` の `mentions_guarded()` を発動させる。発動した場合 `READONLY_SCRIPTS` への登録が必須になり、hookの変更範囲・レビュー負荷が増える。テスト用のルート注入は `main(root=None)` というPython関数引数で十分に代替できる |
| JSON出力 | リポジトリ内に前例がなく、構文オーバーヘッド（クォート・括弧）がトークン削減という目的に反する。消費者はLLMでありプレーンテキストで十分パース可能 |
| CLIがpriority順（high>medium>low）にソートして出力 | priorityの順序を表す定数がコード上どこにも存在せず、新規導入は「強い正当化のない新しい抽象化」に当たる。AC1は「一覧を出力する」ことのみを要求しており、優先度に基づく選択はLLMの推論で代替可能 |
| malformedなチケットを一覧から静かに除外 | 一覧がorchestratorの唯一の判断材料になるため、チケットの存在自体を見落とすリスクが生じる（Operational safety） |
| `validate_ticket_state.py`/`check_loop_integrity.py`の「tickets/active全件glob+parse」ロジックを`_ticket_lib.py`へ共通ヘルパとして切り出し、3箇所で共有する | investigatorが「必須ではない」と明記した任意改善。テスト済みのPreToolUse/Stop hookのコードパスに手を入れるリスクが、本チケットのACとは無関係な範囲まで変更を広げる。`batch_loop.py`も同種の重複した独自globロジックを持っており、重複の許容は既存の慣習と整合する。「不要な書き換えを避ける」というarchitect制約に基づき却下 |

**主要なインターフェース（`scripts/list_tickets.py`、Python）:**
```python
# stdlib のみ。sys.path.insert で .claude/hooks から _ticket_lib を import する
# （scripts/batch_loop.py と同じ手法）。CLI引数は一切持たない。

REQUIRED_LIST_FIELDS = ("id", "status", "priority", "updated")

def build_row(path: Path) -> tuple[dict | None, str | None]:
    """1チケットファイルを読み、(row, None) または (None, error_message) を返す。
    row のキー: id, status, priority, updated, tti, rti, rtv（すべて文字列。
    tti/rti/rtvは int）。row と error_message は排他（必ずどちらか一方が None
    でない）。frontmatter が無い/必須フィールド欠落/retry_countsが不正な
    場合は row=None かつ error_message に理由を入れる（黙ってスキップしない）。"""

def collect(active_dir: Path) -> tuple[list[dict], list[str]]:
    """active_dir 配下を `lib.is_ticket()` でフィルタしつつファイル名昇順で走査し、
    (rows, errors) を返す。rows は build_row が成功した行のみ、errors は
    "<filename>: <理由>" 形式の文字列リスト。"""

def format_header() -> str: ...
def format_row(row: dict) -> str: ...

def main(root: str | Path | None = None) -> int:
    """root（省略時は Path(__file__).resolve().parents[1]）配下の
    tickets/active/ を一覧表示する。tickets/active/ が存在しなければ
    stderr にエラーを書き 1 を返す（致命的エラー）。存在すれば凡例行・
    ヘッダ行・データ行・ERROR行・件数サマリを stdout に出力し 0 を返す
    （ERROR行があっても0のまま。ツール自体はinformationalであり、
    個別チケットの不整合はorchestrator/testerが後続で対処する）。"""

if __name__ == "__main__":
    import sys
    sys.exit(main())
```

**出力フォーマット例:**
```
凡例: tti=tester→implementer rti=reviewer→implementer rtv=reviewer→investigator
id          status                priority  tti  rti  rtv  updated
KLK-002     done                  medium    0    0    0    2026-07-18 09:00
KLK-003     investigation_done    medium    0    0    0    2026-07-19 17:28
ERROR APP-999_broken.md: frontmatter を解析できません
計 2 件（エラー 1 件）
```
列幅は固定値でよい（id:10, status:20, priority:8, tti/rti/rtv:4, updated:16 を目安とする。実データがはみ出す場合は素直に右へずれてよく、厳密な整列はACの対象ではない）。

**処理フロー:**
```
1. main(root) 呼び出し
2. root/tickets/active が存在するか確認 → 無ければ stderr にエラーを書き exit 1
3. collect(active_dir):
   a. sorted(active_dir.glob("*.md")) をファイル名昇順で走査
   b. lib.is_ticket(str(path)) が False のもの（_index.md 等）はスキップ
   c. 各ファイルで build_row(path) を呼び、成功なら rows へ、失敗なら
      "filename: reason" を errors へ追加
4. 凡例行 → ヘッダ行 → rows を id 順に整形して出力 → errors を ERROR行として出力
   → "計 N 件（エラー M 件）" を出力
5. exit 0
```

```bash
# developへマージ済みの場合（orchestratorのworktreeライフサイクル管理の手順に従いマージされたコミット）
git revert <developへのマージコミットハッシュ>
```
