## 1. 目的

`.claude/hooks/guard_bash_writes.py`の`_take_backtick`は、バッククォート置換の内側テキストを`substs`へ格納する際、bashのバッククォート内容確定規則（`` \` ``→`` ` ``・`\$`→`$`・`\\`→`\`の1段階アンエスケープ）を一切適用していない。このため再帰評価（`find_violation`→`subst_violation`→`lex()`再呼び出し）時に、エスケープされたネストのバッククォート（`` `echo \`rm docs/SPEC.md\`` ``）内側の書き込みコマンドが新規`substs`エントリとして分離されず、headチェックの対象にならずallowになる（investigator調査・`docs/reports/KLK-024/investigation.md`）。本設計は`_take_backtick`にのみ1段階アンエスケープを実装し（investigator提示の案(a)）、多段ネスト（2〜3階層・`MAX_SUBST_DEPTH`境界）へ一般化しつつ、KLK-014の`_extract_degraded_substs`との関係（AC6）を整理する。対応する受け入れ条件はAC1〜AC6（本書冒頭表）。SPEC.md非依存のKit内部改善のためSPEC由来のIDは無い。

## 2. 現状

**現在のフロー（バグの所在）:**
```
lex() 通常状態ループ（quote == ""）:
  分岐3: if c == "\\" and i+1 < n: → buf へ2文字そのまま積む（汎用エスケープ）
  分岐8: if c == "`": → _take_backtick(command, i+1, buf, substs)

  分岐3 が分岐8 より「先」にあるため、`\`` は常に分岐3で消費され、
  分岐8（_take_backtick）へは到達しない。

_take_backtick(command, start, buf, substs):
  end = _skip_backtick(command, start)       # 境界探索（正しい。変更不要）
  substs.append(command[start:end-1])        # ← 生スライスをそのまま格納（バグ）
  buf.append(SUBST_PLACEHOLDER % ...)

再帰評価:
  find_violation(top, depth=0)
    → lex() が外側の bare backtick を _take_backtick で抽出
       substs[0] = "echo \`rm docs/SPEC.md\`"（`\``が生のまま残る）
    → subst_violation(substs, 0, depth=0, cwd)
       → find_violation(substs[0], depth=1)
          → normalize_line_continuations（置換内側は素通し）
          → lex(substs[0]) が再度分岐3で `\`` を消費 → 新規substsが作られない
          → tokens=[('w','echo'),('w','`rm'),('w','docs/SPEC.md`')]
          → head='echo'（ALLOWED_HEADS）→ allow
```

## 3. 設計方針

**採用する方針: (a) `_take_backtick`の抽出結果にのみ1段階アンエスケープを実装する（investigator案(a)・最小修正）**

投機的な保守的全体deny（案(b)）は採らない。理由: ネストしているが内側が読み取り専用の良性パターン（`` `echo \`date\`` ``等）まで一律denyになり、AC3の誤deny予算（「日常読み取り相当のdeny件数が増えないこと」）に抵触するリスクがある。案(a)は実機bash仕様と厳密に一致する（investigator実機確認・3階層まで）ため、判定の正確性と誤deny予算の両方を満たす。

**`_skip_balanced`（`$(...)`用）は変更しない。** 実機bashで`$(...)`内側の`` \` ``はアンエスケープされずリテラルのまま解釈されることが確認されており（investigation.md詳細4）、ここへアンエスケープを追加すると`$(...)`内の良性`` \` ``パターンを誤ってネスト開始とみなし新規の誤deny源になる。

**AC6（`_extract_degraded_substs`との関係）の設計判断: 追加の共通化作業は不要。理由は「既に構造的に共通化されている」ため。**

`_extract_degraded_substs`のバッククォート分岐（`.claude/hooks/guard_bash_writes.py`内、一意な引用文字列で確認済み）:
```python
        if c == "`":
            try:
                i = _take_backtick(command, i + 1, buf, substs)
            except ValueError:
                buf.append(command[i:])
                break
            continue
```
これは`lex()`の分岐8（`i = _take_backtick(command, i + 1, buf, substs)`）と**同一の`_take_backtick`関数を呼んでいる**（別実装のコピーではない）。したがって`_take_backtick`を修正すれば、`lex()`経由（正常経路）・`_extract_degraded_substs`経由（degraded経路）の両方が同時に、かつ1箇所の修正で正しくなる。`_extract_degraded_substs`自体には一切手を入れない。この結論はコード直接確認（Read）により一次情報で判断したものであり、investigatorのUnknown「`_extract_degraded_substs`が同型バグを持つか」への回答でもある: **持つが、`_take_backtick`と共有しているため独立に修正する必要がない。** §9でこの主張を検証するための回帰テスト（degraded経路がKLK-024の修正を自動的に継承することを実機的に固定するテスト）を規定する。

**代替案と却下理由:**
| 案 | 却下理由 |
|---|---|
| (b) 判定不能とみなし保守的に全体deny | ネストしている良性パターン（内側が読み取り専用）まで一律denyになり、AC3の誤deny予算に抵触するリスクがある |
| `_skip_balanced`にもアンエスケープを追加する | 実機bashの仕様（`$(...)`内`` \` ``はリテラル）に反し、良性パターンの新規誤denyを生む |
| `_extract_degraded_substs`を独立に修正する（コード複製またはヘルパ関数の新規呼び出し追加） | 既に`_take_backtick`を共有呼び出ししており、`_take_backtick`側の修正だけで両経路が同時に直る。不要な重複コード・二重メンテナンスコストを避ける |

置き換え後（ヘルパ新設＋`_take_backtick`修正）:
```python
# --- KLK-024: バッククォート内容確定時の1段階アンエスケープ ------------------
#
# bash はバッククォート置換の内容を確定する際、`` \` ``→`` ` ``・`\$`→`$`・
# `\\`→`\` の3種のみを1段階アンエスケープし、他の文字へのバックスラッシュ
# （`\;`・`\ ` 等）はバックスラッシュ自体を含めてそのまま残す（実機bashで
# 確認済み。investigation.md詳細4）。`_take_backtick`はこれまでこの
# アンエスケープを行っておらず、抽出した生スライスをそのまま substs へ
# 格納していたため、再帰評価（subst_violation → find_violation → lex()
# 再呼び出し）時に `lex()` の汎用エスケープ分岐が `` \` `` を先に消費して
# しまい、内側の書き込みコマンドが新規 substs エントリにならず allow に
# なっていた（KLK-024）。
#
# 走査は `_skip_backtick` と同じ「`\`+次の1文字を対として消費する」規則に
# 従う（re.sub は左から右へ非重複でマッチを消費するため同じ挙動になる）。
# re.DOTALL は行継続の生テキスト（`\`+改行）がこの位置に残っている場合に
# 1組として正しく消費するために必要——対象外の組（改行を含む）は
# match.group(0) をそのまま返すため出力は1バイトも変わらない。
#
# `_skip_balanced`（$(...)/<(...)/>(...)用）には適用しない——$(...) の内側の
# `` \` `` は実機bashでリテラルのまま解釈されるため（investigation.md詳細4・
# `_skip_balanced`のdocstring参照）。
BACKTICK_UNESCAPE_RE = re.compile(r"\\(.)", re.DOTALL)


def _unescape_backtick_body(text):
    r"""bash のバッククォート内容確定規則（1段階アンエスケープ）を適用する。

    対象は `` \` ``→`` ` ``・`\$`→`$`・`\\`→`\` の3種のみ。他の文字への
    バックスラッシュはそのまま残す。証拠（保護対象パスの文字集合）を
    1文字も減らさない（アンエスケープ対象はいずれもパス文字集合
    `PATHISH_RE` に含まれない記号のため）。
    """
    if "\\" not in text:
        return text

    def replace(match):
        c = match.group(1)
        return c if c in "`$\\" else match.group(0)

    return BACKTICK_UNESCAPE_RE.sub(replace, text)


def _take_backtick(command, start, buf, substs):
    """バッククォート置換の内側を取り込み、終端の次の位置を返す。

    格納前に `_unescape_backtick_body` でバッククォート内容確定規則の
    1段階アンエスケープを適用する（KLK-024）。境界探索（`_skip_backtick`）
    自体は変更しない。`lex()`（正常経路）・`_extract_degraded_substs`
    （degraded経路）の双方が本関数を共有して呼ぶため、この修正1箇所で
    両経路に適用される。
    """
    end = _skip_backtick(command, start)
    if end < 0:
        raise ValueError("no closing backquote")
    substs.append(_unescape_backtick_body(command[start:end - 1]))
    buf.append(SUBST_PLACEHOLDER % (len(substs) - 1))
    return end
```

**多段ネストへの一般化の根拠:** `_unescape_backtick_body`は「1段階分だけ」アンエスケープする一般規則であり、ネスト階層数に応じた特別分岐を持たない。多段ネスト（`` `echo \`echo \\\`rm ...\\\`\`` ``のような3階層以上）では、`find_violation`の再帰呼び出し1回ごとに`_take_backtick`が1回呼ばれ、その都度ちょうど1段階分のアンエスケープが適用される。この「再帰の各段で1段階だけ剥がす」構造が、bash自身の「ネスト階層が1つ増えるごとにバックスラッシュを倍加する」規則（investigator実機確認・3階層まで）と数学的に対応する（§9のテスト観点で構成を示す）。したがって階層数に依存する条件分岐を実装に追加する必要はない。

**テスト専用ヘルパ（クラス定義より前、`payload`関数の近傍に追加）:**

```python
def _escape_once_for_backtick(text):
    r"""次の外側のバッククォートへ埋め込むために、text 中の `` ` ``・`$`・`\`
    をそれぞれ1段階分エスケープする（guard_bash_writes._unescape_backtick_body
    の逆演算。KLK-024のテスト専用ヘルパ）。"""
    return (text.replace("\\", "\\\\")
                .replace("`", "\\`")
                .replace("$", "\\$"))


def _nested_backtick_command(depth, inner="rm docs/SPEC.md"):
    r"""バッククォートを `depth` 階層ネストしたコマンド文字列を機械的に構築
    する（各階層は `echo` でラップする）。depth=1 は `` `inner` ``、depth=2 は
    チケット KLK-024 の再現手順1と同型（`_escape_once_for_backtick` を1回
    適用した形が完全に一致することを設計時に手計算で確認済み。
    docs/designs/KLK-024.md §3参照）。"""
    command = "`%s`" % inner
    for _ in range(depth - 1):
        command = "`echo %s`" % _escape_once_for_backtick(command)
    return command
```
