# [KLK-026] docs/reports運用の実効化 設計

> このファイルはarchitectが生成・更新するチケット単位の設計書です。
> チケット KLK-026 に対応します。implementer・tester・reviewerが参照します。

## 1. 目的

KLK-004が導入した「サブエージェントレポートの詳細を`docs/reports/{ID}/{phase}.md`へ外部化する」規約は、**規約自体は正しいが運用手順（誰が・いつ・どこでコミットするか）が欠けているため意図どおりに機能しない**（investigator確認済み）。本設計は、AC1〜AC6に対応する運用手順を確定し、投資家が発見した2件の矛盾（review.md作成場所の設計/実運用差異、worktree-policy.md境界表のreviewer二重登場）を解消する。AC5（`.gitignore.public`へのdocs/reports/追加可否）は、2026-08-17に人間が選択肢(b)（`.gitignore.public`にのみ`docs/reports/`除外パターンを追加し、`.gitignore.private`は変更しない）を決定したことを受け、本改訂（2026-08-17）でPhaseを追加し設計を確定した（§10 Open Questions「決定済み」参照）。

## 2. 現状

**現在のフロー（バグ）:**
```
1. investigator調査完了 → orchestratorがdocs/reports/{ID}/investigation.mdへ代筆で書き出す
   → コミットされないままメインツリーに放置される（design_done後、architectの設計中も未コミット）
2. worktree作成（design_done→implementer委譲直前）→ docs/designs/{ID}.mdのみコミットされる
   → investigation.mdは未コミットのままなので、worktree内のimplementer/tester/reviewerから読めない
3. implementer/tester自筆分（implementation.md/test-report.md）は「してよい」という許可規定のみで
   コミットが義務化されていない
4. reviewer完了 → orchestratorがメインツリーでdocs/reports/{ID}/review.mdへ代筆で書き出す
   → コミット規定が無いため、マージが起きない限りメインツリーが恒常的にdirtyになる
5. docs/worktree-policy.md「作業場所の境界」表はdocs/reports/に触れておらず、
   tester/implementerがworktree内で自筆する運用も反映されていない
```

**関連する既存ファイル（節見出し＋一意な引用文字列）:**

  — このコミット手順が`docs/reports/{ID}/investigation.md`・`review.md`には存在しない

## 3. 設計方針

**採用する方針:**

1. **review.mdは「メインツリーで直接作成しその場でdevelopへコミットする」方式を正規手順として確定し、KLK-012実運用（featureブランチ側へコミットしてマージで取り込む、コミット`979c062`）は正規手順として採用しない。** KLK-004設計§3方針5は既に作成場所を「メインworktree」と定義しており矛盾はないが、コミットする手順が欠落していたことが本バグの根本原因（investigator確認済み）。したがって設計書側の訂正は不要で、欠落していたコミット手順を補うことがAC6の答えになる。KLK-012方式を採用しない理由: reviewer差し戻し時はマージが発生しないため、featureブランチ側にコミットする方式では変更内容がメインツリーへ永久に届かないケースが生じ、KLK-004設計が明言する「マージのタイミングに依存せず即座に参照可能」というゴールに反する。承認・差し戻し双方でメインツリーへ直接コミットすれば、この非対称は生じない。
2. **investigation.mdは、AC1(a)が指示するとおりworktree作成手順（design_done→implementer委譲直前）でdocs/designs/{ID}.mdと同じタイミング・同種の手順でdevelopへコミットする。** investigation完了時点（todo→investigation_done）ではまだworktreeが存在せず即時コミットの必要性がないため、既存の「必要になる直前にコミットする」という設計書コミットのjust-in-timeパターンをそのまま踏襲し、新しい概念を持ち込まない。
3. **docs/worktree-policy.mdの境界表は、既存2行の「扱うもの」列にdocs/reports/の行き先を追記する形に留め、「エージェント」列にreviewerを二重登録しない。** 表の「エージェント」列は「どこで作業するか」を表すものであり「誰の報告が外部化されるか」ではない、と明示することで、investigatorが指摘した矛盾（reviewerがworktree行とメインツリー行の両方に現れる）を構造的に解消する。review.mdの書き手は常にorchestrator（メインツリー行に既存）であり、reviewer自身がその行に追加登録される必要はない。
4. **implementer/tester自筆分のコミットを「してよい」から「次工程への引き継ぎ前に必ず行う」義務へ引き上げる。** 既存文言の「自ら作成し」は維持しつつ（KLK-004回帰テストが検証する文言のため）、コミットの部分のみ許可→義務に改める。
5. **implementation.md/test-report.mdのポインタ未解決期間（マージ前・差し戻し滞留中）は、docs/reports/README.mdに明記するに留め、解決する運用（例: メインツリーへの都度複製コミット）は導入しない。** 複製コミットは「コードはworktree、チケット・メトリクスはメインツリー一本化」というworktree-policy.mdの原則に反し、二重管理・コンフリクトリスクを生む。KLK-004設計§6リスク表が既にこの制約を「実装コード自体も同じ制約を持つ」と評価し許容済みであり、本チケットではこれを明文化するだけで足りる。
6. **AC5（`.gitignore.public`への`docs/reports/`追加可否）は、人間が選択肢(b)「`.gitignore.public`にのみ`docs/reports/`除外パターン（`docs/reports/*/`）を追加し、`.gitignore.private`は変更しない」を決定（2026-08-17）したことを受け、本改訂で設計を確定する。** 決定根拠（人間へ伝えた推奨根拠）: `docs/reports/{ID}/{phase}.md`は「本来チケット本文に書かれるはずだった詳細（investigation/reviewの生ログ）」の外部化であり、公開リポジトリで既に除外している`tickets/active|done/*.md`と同じ性質（生の作業ログ・プロセス記録）を持つ。一方`docs/designs/`は正式に整えられたアーキテクチャ成果物のため常に追跡を維持する、という区分で一貫性を取る。具体的な変更内容は§4 Phase2として追加する。
7. **docs/designs/KLK-004.md §5「影響範囲」表の訂正を本改訂で実施する。** AC5が(b)で決定したことにより、同表の`.gitignore.public` / `.gitignore.private`を1行にまとめた現行記述（「変更なし」「docs/reports/はGit追跡対象とする」）はもはや事実と一致しない。実際には`.gitignore.public`のみ変更（除外パターン追加）、`.gitignore.private`は変更なし（引き続き追跡）という非対称が生じるため、implementerが§4 Phase2で当該行を2行に分割し訂正する。これによりAC6（KLK-004設計書との矛盾がないこと）を満たす。

**代替案と却下理由:**

| 案 | 却下理由 |
|---|---|
| review.mdをチケット専用worktree側のfeatureブランチへコミットし、マージで取り込む（KLK-012実運用を正規手順化） | 差し戻し時はマージが発生しないため、変更内容がメインツリーへ永久に届かないケースが生じる。KLK-004設計の「マージのタイミングに依存せず即座に参照可能」というゴールに反する |
| implementation.md/test-report.mdも都度メインツリーへ複製コミットし、ポインタ未解決期間を解消する | 「コードはworktree、チケットはメインツリー一本化」という既存原則に反し、二重管理・コンフリクトリスクを生む。KLK-004設計が既に許容判断済みの制約を明文化すれば足りる |
| docs/worktree-policy.mdの境界表にreviewerを含む3つ目の行（「メインツリー・reviewer分の代筆」）を新設する | 「エージェント」列の意味が「作業拠点」から「報告の帰属」に変質し、表の一貫性を損なう。既存2行の「扱うもの」列への追記と注記1文で同じ情報を矛盾なく表現できる |
| AC5をarchitectが選択肢の中から決定する | チケットが明示的に人間判断事項と指定しており、architectの権限外（Open Question化が適切） |
| investigation.mdを調査完了直後（todo→investigation_done遷移時）に即時コミットする | worktreeがまだ存在せず即時性の必要がない。docs/designs/{ID}.mdの既存コミットパターン（必要になる直前にコミット）と統一した方が新しい概念を持ち込まずに済む |

## 8. ロールバック戦略

全ての変更が追加的（文言追加・新規節追加）またはテキスト置換のみで、状態機械・hookロジックには一切触れない。問題発生時はコミット単位でrevertする。

```bash
# developへマージ済みの場合（orchestratorのworktreeライフサイクル管理の手順に従いマージされたコミット）
git revert <developへのマージコミットハッシュ>
```

Phase2（回帰テスト追加）のみを個別にrevertすると、Phase1の文言変更を検証する対象が失われるため、Phase1とセットでrevertすることを推奨する（KLK-004ロールバック戦略と同型）。
