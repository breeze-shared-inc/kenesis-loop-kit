## 1. 目的

`guard_bash_writes.py`の`mentions_guarded`（`is_guarded_token`→`guarded_paths`→`PATHISH_RE`の鎖）は、sed/awkのプログラム本文中でバックスラッシュエスケープされた保護対象パス（`docs\/SPEC.md`・`tickets\/active\/APP-001.md`等）を検出できず、SED-7（KLK-015）・AW-7（KLK-010）の安全性検査そのものへゲートが到達しない（investigator実機実証済み・AC1〜AC3）。本設計は、`PATHISH_RE`／`guarded_paths`という**全15呼び出し元が共有するグローバルな鎖には一切手を入れず**（AC4を構造的に満たす）、sed/awk専用の狭いエスケープ正規化を**言及ゲートにのみ**追加することで、SED-7・AW-7の判定本体（KLK-015／KLK-010で確立済み・無変更で正しく機能する）へ確実に到達させる。対応するチケット受け入れ条件はAC1〜AC5（本書冒頭表）。

## 2. 現状

**現在のフロー（正常経路。字句解析に成功した入力のみ。degraded経路は本設計の対象外＝§3「対象外の明示」参照）:**
```
find_violation(command)
  └─ lex() 成功
       └─ statement_violation(statement, ...)                 ← 文単位の言及ゲート①
            ├─ redirect_violation(...)                          （無条件・本バグの対象外）
            ├─ if not (cwd_is_guarded(cwd) or
            │          mentions_guarded(expand_all(words, substs))):
            │       return None                                 ← ① ここが偽になると
            │                                                      segment_violation へ
            │                                                      到達しない
            └─ for segment_words in pipe_segments(statement):
                 segment_violation(segment_words, substs, cwd)
                    ├─ head == "sed":
                    │    elif strict or mentions_guarded(flat):  ← ② sed専用ゲート
                    │        sed_program_violation(text)  ★SED-7本体（無変更で正しい）
                    └─ head == "awk":
                         awk_violation(words, cwd, degraded)
                            ├─ AW-1: is_guarded_token(t) ...     ← ③ awk専用ゲート(a)
                            ├─ AW-2: is_guarded_token(v) ...     ← ④ awk専用ゲート(b)
                            ├─ if not (mentions_guarded(words)
                            │          or cwd_is_guarded(cwd)):
                            │       return None                  ← ⑤ awk専用ゲート(c)
                            └─ awk_program_violation(text)     ★AW-7本体（無変更で正しい）
```
①〜⑤はすべて`mentions_guarded`／`is_guarded_token`（根は`PATHISH_RE`）を経由する。`PATHISH_RE = re.compile(r"[A-Za-z0-9_.\-/]+")`は`\`を含まないため、`docs\/SPEC.md`は`docs`と`/SPEC.md/e`等に分断され、①〜⑤のいずれの箇所でも「言及あり」と判定できず、SED-7／AW-7本体（★印。既に正しく`w`/`e`/`system(`等を検出できることをKLK-015・KLK-010で確立済み）へ到達しない。

**重要な事実（investigation.md §「詳細調査ログ」1・3から導かれる。本設計の中核前提）:** SED-7・AW-7の判定本体は、いったん**到達しさえすれば**、本チケットの再現手順（`s/.*/rm docs\/SPEC.md/e`・`system("rm tickets\/active\/APP-001.md")`・`print > "tickets\/active\/APP-001.md"`）をエスケープの有無に関わらず正しくdenyする。理由:
- sedの`sed_strip_literals`は`s///`の置換文字列スパンを**除去して捨てる**（中身は判定に使わない）。除去後に残る`/e`の`e`は`SED_SAFE_PROGRAM_CHARS`に無いため、置換文字列の中身が何であってもdenyになる。
- awkの`awk_strip_literals`は文字列リテラルを丸ごと`""`へ置換する。`system("…")`の`system(`は文字列の**外側**にあるため、文字列の中身（エスケープの有無）に関わらず`AWK_SAFE_CALLS`に無い呼び出しとして検出される。`print > "…"`も同様に`AWK_STRING_RE.sub('""', word)`後の`AWK_OUTPUT_RE`が文字列の中身と無関係に一致する。
- したがって**本バグは検出対象抽出（言及ゲート）だけの問題であり、SED-7／AW-7の判定本体は無変更のままでよい**。これによりブラスト半径は「ゲート5箇所への追加条件」に限定でき、investigatorが懸念した「新しいstrip関数・新しい終端条件」（investigation.md §8 候補3の懸念）は不要になる。

- `docs/designs/KLK-015.md`: SED-7ホワイトリスト設計・§6 R1誤deny予算の列挙形式（本書§6 R1が踏襲する）

## 3. 設計方針

**採用する方針: 「ゲート限定エスケープ正規化」（investigation.md §8 候補3の絞り込み版）**

investigatorが提示した3候補を再検討し、§2で確認した「SED-7／AW-7本体は無変更で正しい」という事実に基づき、**候補3をゲート（①〜⑤）だけに限定する形**へ絞り込んだものを採用する。

1. 新規ヘルパー（`unescape_program_backslashes`・`_is_guarded_path_component`・`guarded_paths_in_program`・`is_guarded_token_in_program`・集合版`mentions_guarded_in_program`。計5関数）を`is_guarded_token`／`mentions_guarded`の直後に追加する。**既存の`is_guarded_token`／`mentions_guarded`／`guarded_paths`／`_is_guarded_path`／`PATHISH_RE`は1文字も変更しない。**
2. `unescape_program_backslashes(text)`は`re.sub(r"\\(.)", r"\1", text)`——**任意の`\X`を`X`へ畳み込む**。sed/awkともに「未知のエスケープシーケンス`\X`は警告つきで`X`（バックスラッシュを外した1文字）として扱う」という実機挙動（investigation.md §詳細調査ログ4）をそのまま模す。デリミタが`/`か`|`かに依存せず、**バックスラッシュの直後の文字を問わず一様に畳み込む**ため、Unknown②（デリミタが`.`・`-`等の場合の一般化）がゲート層に関しては**理論上の懸念を要さない**（後述R-U3）。
3. **単純な畳み込みだけでは`docs/SPEC.md`型（スラッシュ1箇所）を救済できない（設計初期案の誤り。実際に手計算で検証し判明）。** `s/.*/rm docs\/SPEC.md/e`を畳み込むと`s/.*/rm docs/SPEC.md/e`になるが、`PATHISH_RE.findall`はこれを`['s/.', '/rm', 'docs/SPEC.md/e']`と抽出し、**sedの`/e`フラグ（区切り文字＋フラグ。空白を挟まず直後に連続する）が候補の末尾へ融合する**ため、`os.path.normpath("docs/SPEC.md/e")`のbasenameは`e`のままになる（`_is_guarded_path`のbasename**完全一致**判定はこの融合に対して脆弱——バックスラッシュの有無に関わらず、末尾に空白を挟まず続くsed自身の構文がPATHISH候補へ巻き込まれると常に壊れる）。tickets/active・tickets/done型（部分文字列判定）はこの融合があっても`"tickets/active" in path`が成立するため元々頑健だが、SPEC.md型（完全一致）だけがこの融合に弱い。**したがって新設する`_is_guarded_path_component`は、SPEC.md型の判定を「basenameの完全一致」から「`/`区切り成分のいずれかにSPEC.mdが一致するか」へ緩める**（tickets/active・tickets/doneの部分文字列判定は変更しない）。`os.path.normpath(candidate).split("/")`に`"SPEC.md"`という要素が1つでもあれば真とする——これにより`["docs","SPEC.md","e"]`のように末尾へ余計な成分が融合していても正しく検出できる。**この関数は`_is_guarded_path`のコピーではなく`_is_guarded_path`自体は無変更のまま**、sed/awk専用ゲートだけが使う並行した緩い判定として新設する（AC4を満たすため）。
4. `guarded_paths_in_program(text)`は`unescape_program_backslashes(text)`した結果に対して`PATHISH_RE.findall`→`_is_guarded_path_component`を適用する（`guarded_paths`と同型だが、対象テキストがエスケープ畳み込み後・判定基準が成分緩和版という2点が異なる）。`is_guarded_token_in_program(text)`は`is_guarded_token(text) or bool(guarded_paths_in_program(text))`——**OR追加のみ**。既存の`is_guarded_token(text)`がTrueならこの関数も必ずTrue（False→Trueの方向にしか広がらない。KLK-015 P8と同型の「安全な拡張」の証明可能な形）。
5. この一連の関数を**sed／awk専用のゲート呼び出し箇所（①〜⑤）にだけ**適用する。①（`statement_violation`）は本来head非依存の共有ゲートのため、**その文にsed／awkのパイプ区間が含まれる場合に限り**適用する（`pipe_segments(statement)`から`head_of`で判定。他headだけの文は従来の`mentions_guarded`のまま＝AC4を構造的に満たす）。

**代替案と却下理由:**

| 案 | 却下理由 |
|---|---|
| 候補1: `PATHISH_RE`に`\`を追加するのみ | investigator実測で`tickets/active`型（スラッシュ2箇所）を救済できないことを確認済み（investigation.md §8）。かつ全15呼び出し元に影響し、AC4の限定列挙が困難になる |
| 候補2: `guarded_paths`／`PATHISH_RE`をエスケープ対応にグローバル改修 | 両型を救済できるが、全15呼び出し元（リダイレクト先判定・`cd`追跡・変数代入追跡・degraded全般）に影響する。これらの呼び出し元が扱うテキストは**bashの引用解除を経た最終値**であり、sed/awkのように「その後さらに自分の文法でエスケープを再解釈する」処理系ではない（§3-1「対象がsed/awkに限られる理由」参照）。グローバル改修はAC4（他headへの悪影響なし）の証明・列挙コストが本チケットの候補3限定版より高く、却下する |
| 候補3（investigator提示の原案）: sed/awk専用に**新しい**strip関数を作り新しい「strict」分岐を追加 | §2で確認したとおりSED-7／AW-7本体は無変更で足りるため、新しいstrip関数・新しい終端条件は不要（過剰実装）。本設計は候補3を「ゲートのみ」へ絞り込むことでinvestigatorが懸念した実装コスト（終端条件の精緻化）を回避する |
| degraded経路（sed:1974／awk全般／`degraded_violation`関数レベル・文レベルゲート）にも同じ緩和を適用する | §3-1「対象外の明示」参照。degradedはSED-7／AW-7本体を使わない（KLK-015 R6・KLK-010で確立済みの縮退）ため、ゲートだけ緩めても本体側の防御（ブラックリスト）は変わらず一貫した安全性向上にならない。かつ`degraded_violation`は独自の文処理ループを持ち`statement_violation`を経由しないため、①の修正はdegradedに影響しない（構造的に無関係）。範囲を広げず、Unknownとして明記のうえ将来チケットへ委ねる |

**対象がsed/awkに限られる理由（§6 R-U1の判断根拠）:** sed/awkは「プログラム本文」という**独自の小言語**を持ち、その小言語自身が`\`によるデリミタ／文字列終端のエスケープ規約を持つ。bashが引用解除した後の文字列（sed/awkから見れば「自分のプログラムのソーステキスト」）を**sed/awk自身がもう一段解釈する**ため、hookが見る字面（bashレベルで引用解除済みだが`\`はシングルクォート内で保持される）と実行時の意味（sedの`s///`区切り文字解釈・awkの未知エスケープ警告つき正規化）が乖離する。一方、リダイレクト先・変数代入・`sort -o`等はbashが引用解除した値が**そのまま最終値**であり、追加の再解釈層を持たない。したがって同種の乖離は原理的に生じない（investigation.md Assumptionsと整合）。

**対象外の明示（degraded経路）:** `sed`のdegradedブランチ（`SED_WRITE_RE`使用）・`awk_violation`内の`if degraded:`（AW-5／AW-6）自体は変更しない。ただしAW-1（③）・AW-2（④）・ゲート⑤は`awk_violation`冒頭の**degraded非依存の共通コード**であるため、実装上は`degraded`の値に関わらず`is_guarded_token_in_program`／`mentions_guarded_in_program`を使う（分岐を増やさない方が実装がシンプルであり、deny方向にしか作用しないため安全）。ただし`degraded_violation`自身の関数レベルゲート（`mentions_guarded(skeleton.split())`）と文レベルゲート（`mentions_guarded(w) for w in words_list`）は`statement_violation`を経由しない独立コードパスであり、**本設計では変更しない**——このため、字句解析に失敗する形（未閉じクォート等）へ意図的に落とし込んだうえでのエスケープ回避は、本チケットの対象外の残存リスクとして§6 R-U1相当に明記する。

置き換え後（`mentions_guarded`の定義と`# --- L1`見出しの間に以下を挿入する。既存の2行はそのまま残す）:
```python
def mentions_guarded(values):
    """語の集合のいずれかが保護対象に言及するか。"""
    return any(is_guarded_token(v) for v in values)


# --- KLK-029: sed/awk 専用の言及ゲート緩和 -----------------------------------
#
# sed/awk は「プログラム本文」という独自の小言語を持ち、その小言語自身が `\`
# によるデリミタ／文字列終端のエスケープ規約を持つ。bash が引用解除した後の
# 文字列（シングルクォート内では `\` がそのまま残る）を sed/awk 自身がもう
# 一段解釈するため、is_guarded_token が見る字面（`docs\/SPEC.md`）と実行時の
# 意味（sed の `s///` 区切り文字解釈・awk の未知エスケープ警告つき正規化）が
# 乖離する（実機 GNU sed 4.9・GNU Awk 5.2.1 で確認済み。
# docs/reports/KLK-029/investigation.md 参照）。
#
# **この乖離は sed/awk に固有**である。リダイレクト先・変数代入・`sort -o`
# 等はbashが引用解除した値がそのまま最終値であり、追加の再解釈層を持たない
# ため、下記の一連の関数は sed/awk 専用のゲート（segment_violation の sed
# 分岐・awk_violation・head に sed/awk を含む文の statement_violation）でのみ
# 呼び出すこと。**PATHISH_RE／guarded_paths／_is_guarded_path／
# is_guarded_token／mentions_guarded 自体は変更しない**（他 13 箇所の
# 呼び出し元・他 head の判定に一切影響しない＝ AC4）。
#
# P8 型の安全性主張:
#   - 主張: is_guarded_token_in_program(t) は is_guarded_token(t) が真ならば
#     必ず真（OR 追加のみ）。したがって既存の deny が allow に転じることは
#     構造的に起こらない。
#   - 破れる形（否定形）: 本関数の呼び出し箇所を「素の is_guarded_token を
#     置き換える」形で使った場合（OR ではなく置換にした場合）。本設計は
#     すべての呼び出し箇所で OR 追加の形を取ることを§4-2〜4-4で明記する。
#   - 向き: 誤りの向きは常に allow 方向（危険）。SPEC.md 型の判定を
#     basename 完全一致から「/ 区切り成分のいずれかに一致」へ緩めたことで
#     ゲートの発火条件は広がる方向にのみ動く（判定基準を狭める変更は無い）。
#   - 検出器: tests/test_guard_bash_writes.py の INV-SED-27〜31・
#     INV-AWK-21〜25（本設計§4-5）。

def unescape_program_backslashes(text):
    r"""sed/awk が実行時に解釈するとおり `\X` → `X` へ畳み込む（証拠収集専用）。

    デリミタが `/` か `|` か、あるいはそれ以外かに関わらず一様に適用する
    （バックスラッシュの直後の1文字を問わず畳み込むため、特定のデリミタ
    文字集合に依存しない）。判定を広げる方向（ゲートを発火させる方向）にのみ
    使うこと。sed_program_violation／awk_program_violation の安全性判定
    そのもの（sed_strip_literals／awk_strip_literals）は経由しない——両関数は
    KLK-015／KLK-010で確立済みの独自のデリミタ／文字列除去を引き続き使う。
    """
    if "\\" not in text:
        return text
    return re.sub(r"\\(.)", r"\1", text)


def _is_guarded_path_component(path):
    """sed/awk 専用ゲート: _is_guarded_path の SPEC.md 判定（basename の
    **完全一致**）を「`/` 区切り成分のいずれかに一致」へ緩めた判定。

    sed の `s/.*/rm docs\/SPEC.md/e` を畳み込むと候補 `docs/SPEC.md/e` に
    なる（`/e` はsed自身の区切り文字＋フラグで、空白を挟まず直後に連続する
    ため PATHISH 候補へ融合する）。この候補の basename は `e` であり、
    _is_guarded_path の完全一致では検出できない。成分単位（`split("/")`に
    `"SPEC.md"` が含まれるか）で見ることでこの融合に頑健になる。
    tickets/active・tickets/done は元の部分文字列判定のまま（既に融合に
    頑健なため変更しない）。**_is_guarded_path 自体は無変更**——本関数は
    sed/awk 専用ゲートだけが使う並行した緩い判定として新設する（AC4）。
    """
    if ".claude" in path.split("/"):
        return False
    if "tickets/active" in path or "tickets/done" in path:
        return "/Templates/" not in path and not path.endswith("_index.md")
    return "SPEC.md" in path.split("/")


def guarded_paths_in_program(text):
    """sed/awk 専用: guarded_paths のエスケープ畳み込み・成分緩和版。

    バックスラッシュを畳み込んだ字面から PATHISH 候補を再抽出し、
    _is_guarded_path_component で判定する。guarded_paths（無変更）と
    _is_guarded_path（無変更）は経由しない。
    """
```
