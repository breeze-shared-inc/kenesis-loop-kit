# [KLK-016] docs/SPEC.mdのドリフト検知バックストップ追加 設計

> このファイルはarchitectが生成・更新するチケット単位の設計書です。
> チケット KLK-016 に対応します。implementer・tester・reviewerが参照します。

**受け入れ条件の番号付け:** チケット本文のチェックボックスを出現順に **AC1〜AC6** と呼ぶ。

| AC | 要旨 |
|---|---|
| AC1 | docs/SPEC.md がBash経由（LLMのWrite/Editを通さず）に変更された場合、Stop hookが検出して報告する |
| AC2 | 正規の変更経路（guard_spec_writes.py の人間承認を経たWrite/Edit）では誤検出しない |
| AC3 | docs/SPEC.md が存在しないプロジェクトでもhookがエラーにならない（fail-open） |
| AC4 | 検出方式の選択理由を設計書に記載する。状態の保存場所はhookが自動生成し、LLM・エージェントは直接編集しない方式にする |
| AC5 | `.claude/hooks/README.md` のhook一覧と「強制する不変条件」へ追記する |
| AC6 | tests/に回帰テストを追加し、既存テストと合わせて全件パスする |

## 1. 目的

`check_loop_integrity.py`（Stop hookのドリフト検知）は `tickets/active|done/*.md` のみを検査対象とし、`docs/SPEC.md` は対象外である。`guard_spec_writes.py` 自身のdocstringが「SPEC.mdには観測サイドカーが存在しないためStop hookのドリフト検知が無い」と明記しており（investigation.md §2）、チケット側に存在する「PreToolUseをすり抜けてもStop hookが最後の砦として捕捉する」という2段防御がSPEC.mdには無い非対称を解消する。本チケットはKit自体（メタ開発）のインフラ改善であり、docs/SPEC.md自体は本リポジトリに存在しない前提で設計する（AC3が正面から要求する状態）。

## 2. 現状

**現在のフロー:**
```
Write/Edit(docs/SPEC.md)
  └─ guard_spec_writes.py（PreToolUse）: is_spec(path) が真なら ask（人間承認）
       └─ 承認後: 実際の書き込み実行
            └─ record_metrics.py（PostToolUse）: is_ticket(path) が偽 → 即 return（SPEC.mdは無視される）

Bash経由の書き換え（sed -i / リダイレクト等）
  └─ guard_bash_writes.py（PreToolUse・Bash）: ベストエフォートで遮断（すり抜けうる）
       └─ すり抜けた場合、検出する仕組みが存在しない
            （check_loop_integrity.py は tickets/active|done/*.md のみ走査）
```

## 3. 設計方針

**採用する方針:**

**D1（検出方式）: sha256ハッシュ監視を採用する。** `docs/SPEC.md`の内容（バイト列）のsha256をサイドカーに保存し、Stop hookで再計算して比較する。理由:
1. 内容が実際に変化した場合のみ検知する（`touch`・`git checkout`等の無害な操作、あるいは将来ファイルシステム間でmtime精度が異なる環境でも、内容が同じなら誤検知しない＝AC2「正規経路では誤検出しない」を安全側に満たしやすい）
2. `record_metrics.py`は既にWrite/Edit直後にファイルを開いて中身を読む処理（チケットのfrontmatterパース）を実装済みであり、同じ処理点にハッシュ計算を追加するだけで実装コストは小さい
3. `check_state_drift`（既存のticket用ドリフト検知）と同じ「サイドカーに保存した値」対「現在値」の単純な等価比較モデルに載せられ、既存パターンとの親和性が高い

**D2（サイドカー配置）: `tickets/.metrics_state.json`には相乗りさせず、`docs/.spec_state.json`として分離する。** 理由:
1. 概念的独立性 — SPEC.mdのドリフト検知はticketのライフサイクルと無関係であり、`{ticket_id: {status, retry_counts, ts}}`前提のスキーマに`{hash, ts}`という異なるレコード種別を混在させると将来の読み手を混乱させる
2. `tickets/`ディレクトリの有無から疎結合にできる（AC3の「fail-open」をticket機構と独立に保証しやすい）
3. `docs/SPEC.md`と同じ`docs/`配下に置くことで「何のための状態ファイルか」が直感的
4. 既存の「hookが自動生成・LLM非編集・`.gitignore`対象」という運用パターン自体は`tickets/.metrics_state.json`と共通のまま踏襲する（AC4後半）

**D3（判定基準）: `guard_spec_writes.is_spec`とは統一せず、`_ticket_lib.py`に専用の`is_project_spec(path, cwd)`を新設し、対象を「プロジェクト直下の`docs/SPEC.md`1件のみ」に限定する。** ネストしたSPEC.md（`docs/foo/SPEC.md`等）はドリフト検知の対象外とする。理由:
1. チケットのAC文言が「`docs/SPEC.md`」と明記しており、basename一致による広い判定（ネスト許容）へ拡張することはACの範囲を超える
2. `is_ticket`と`guard_bash_writes.py`内の保護対象判定が意図的に基準を分けている前例（KLK-010 D2）と同型の判断であり、「目的が異なる判定は統一しない」というKit全体の既存方針と整合する
3. ネストしたSPEC.mdの監視が将来必要になった場合は、単一サイドカーではキー設計から見直しが必要になるため、別チケットで判断すべき事項である

**D4（README.md「強制する不変条件」の解釈）: CLAUDE.md「hook一覧・強制する不変条件」は、README.md内に同名の見出しが存在しないため、①hook一覧表の役割列（`check_loop_integrity.py`行・`record_metrics.py`行）と②「メトリクスの運用」節、の2箇所への追記と解釈する。** investigatorの調査（investigation.md §4）で提示された解釈を採用する。表の役割列と運用節はいずれも「何を・なぜ強制するか」を記述する既存の構造であり、新規見出しを追加すると既存の文書構造（README.mdの節構成）を不必要に増やすことになるため、既存節への追記で足りると判断する。

**D5（fail-openの境界）: サイドカーに記録が無い期間（SPEC.md作成直後で一度も正規のWrite/Editを経ていない等）はドリフト照合をスキップする。** 既存の`check_state_drift`（サイドカーに記録が無いチケットは照合しない）と同じ設計を踏襲する。`/spec-interview`によるSPEC.md生成は必ずWrite/Editツールを通るため、正規フローで作成されたSPEC.mdは以降ドリフト検知が有効になる。この境界は§6 Risksに明記する。

**代替案と却下理由:**

| 案 | 却下理由 |
|---|---|
| mtime監視（`os.path.getmtime`） | ファイル内容を読まずに済み軽量だが、内容を変えない操作（`git checkout`・バックアップからのコピー等）でもmtimeが変化しうる一般的弱点があり、OS・ファイルシステム間の精度差リスクもある。「Bash経由の内容変更」を確実に捉えるという本チケットの目的（AC1）に対し、ハッシュより検出の正確性が劣る |
| `tickets/.metrics_state.json`への相乗り（キーを`__SPEC__`等の予約語にする） | 技術的には可能（ticket_id形式`{略称}-{3桁連番}`と衝突しない）だが、ticket_id前提のスキーマに異種レコードを混在させると`load_state`/`write_state`の呼び出し元すべてが暗黙に「ticket_id以外のキーもありうる」ことを意識する必要が生じ、保守性を損なう（D2で詳述） |
| `guard_spec_writes.is_spec`をそのままドリフト検知の判定にも流用（ネストしたSPEC.mdも対象） | ACの文言（「docs/SPEC.md」）を超えるスコープ拡張であり、単一サイドカーでは複数SPEC.mdの状態を区別できず設計が破綻する（D3で詳述） |

```python
def record_spec_state(path, cwd):
    """docs/SPEC.md（プロジェクト直下）への Write/Edit 後、内容の sha256 ハッシュ
    を docs/.spec_state.json へ記録する（KLK-016）。Write/Edit を経ない Bash
    改変とのドリフト検知（check_loop_integrity.py）の基準を提供する。
    fail-open: ファイルが読めない等の内部エラーでは何もしない。"""
    try:
        if not os.path.exists(path):
            return
        digest = lib.sha256_file(path)
        if digest is None:
            return
        state_path = lib.spec_state_path(cwd)
        if not state_path:
            return
        now = datetime.datetime.now().isoformat(timespec="seconds")
        write_state(state_path, {"hash": digest, "ts": now})
    except Exception:
        pass
```

### 4-2. `check_loop_integrity.py` の変更箇所

新設関数（`check_done_ticket_drift`の直後、`def main():`の直前に追加）:
```python
def check_spec_drift(cwd):
    """docs/SPEC.md（プロジェクト直下）のハッシュドリフトを検知する（KLK-016）。
    SPEC.md が存在しない、またはサイドカーに記録が無い場合は照合しない
    （fail-open。AC3）。"""
    spec_path = lib.spec_path_for(cwd)
    if not spec_path or not os.path.isfile(spec_path):
        return []
    record = lib.load_spec_state(cwd)
    if not isinstance(record, dict):
        return []
    observed = record.get("hash")
    if not observed:
        return []
    current = lib.sha256_file(spec_path)
    if current is None:
        return []
    if current != observed:
        return [
            "docs/SPEC.md: Write/Edit を経ない変更を検出しました"
            "（最後に検証されたハッシュと現在の内容が不一致）。"
            "正規経路（Write/Edit ツール・人間の diff 承認）で変更を"
            "再適用するか、意図しない変更なら元の内容へ戻してください"
            "（docs/.spec_state.json は直接編集しないこと）"
        ]
    return []
```

### 4-5. `tests/_util.py` の追加ヘルパー

```python
def write_spec(cwd, content="# SPEC\n\nテスト用SPEC本文\n"):
    """docs/SPEC.md をテスト用に書き出し、絶対パスを返す。"""
    target = os.path.join(cwd, "docs")
    os.makedirs(target, exist_ok=True)
    path = os.path.join(target, "SPEC.md")
    with open(path, "w", encoding="utf-8") as f:
        f.write(content)
    return path


def write_spec_state(cwd, record):
    """hook管理サイドカー docs/.spec_state.json をテスト用に書き出す。
    record: {"hash": ..., "ts": ...}"""
    docs = os.path.join(cwd, "docs")
    os.makedirs(docs, exist_ok=True)
    path = os.path.join(docs, ".spec_state.json")
    with open(path, "w", encoding="utf-8") as f:
        json.dump(record, f, ensure_ascii=False)
    return path


def spec_hash(content):
    """SPEC.md本文のsha256ハッシュ（テスト用。実装（sha256_file）を呼ばず
    独立に計算し、テストが実装のタウトロジーにならないようにする）。"""
    import hashlib
    return hashlib.sha256(content.encode("utf-8")).hexdigest()
```
