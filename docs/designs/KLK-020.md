## 3. 設計方針

**採用する方針:**

**D1（SPEC.md判定の一本化とスコープ）— 4箇所全てをcase-insensitive化する。** ACが名指しするのは `is_spec` と `_is_guarded_path` の2箇所だが、investigation.md B節により同型の欠陥が `_is_guarded_path_component`（sed/awk専用ゲート、KLK-029）と `is_project_spec`（KLK-016）にも独立に存在することが判明している。人間確定済み方針は「デプロイ先FSのcase-sensitivityに依存せず、**一律**case-insensitive化する」であり、「一律」という語と、チケットの「期待する動作」自体が掲げる非対称回避の原則（「片方だけ直すと新たな非対称を生む」）は、ACが名指しした2箇所に限定する理由にならない。2箇所のみ是正すると、残り2箇所が新たな取り残しとなり、AC自身の原則に反する。よって4箇所全てを是正範囲とする。
実装は `_ticket_lib.py` に共有ヘルパー `is_spec_basename(name)` を新設し、4箇所全てをこの単一の正規化ポイント経由にする（DRY化）。`guard_spec_writes.py`・`guard_bash_writes.py` はいずれも既に `import _ticket_lib as lib` 済みであり、新規importは不要。
`is_project_spec` はbasename部分のみcase-insensitiveにし、ディレクトリ部分（`docs`）とネスト除外（KLK-016 D3: `docs/foo/SPEC.md` 等は対象外）は現状のcase-sensitive比較のまま維持する。ディレクトリ名自体の大小区別（例: `Docs/SPEC.md`）は本チケットのAC・再現手順のいずれにも現れておらず、スコープ外として明示的に据え置く（Risks参照）。
なお `tickets/active` / `tickets/done` トークン自体の大小区別化は本チケットのAC・再現手順に含まれないため対象外とする。

**D2（`is_ticket` ↔ `is_guarded_token`/`_is_guarded_path`: 意図的な不統一を維持）—統一しない。** KLK-010 D2の根拠3点を再評価する（investigation.md D節）。
1. 目的（厳密判定 vs 再現率優先）: 現在も有効。`is_ticket` は状態機械検証（`validate_ticket_state.py`）・観測（`record_metrics.py`）・一覧（`scripts/list_tickets.py`・`scripts/batch_loop.py`）という**精密性が要求される用途**で使われ、誤って過剰検知すると任意ファイルへの正規のWrite/Editがチケット状態機械の検証対象として誤ってdenyされる（機能退行）。`_is_guarded_path`/`is_guarded_token` は「コマンド文字列の断片が保護対象に言及しているか」という**再現率優先の用途**であり、過剰検知の方向（deny/ask側）が安全側（P8）。両者を統一すると、いずれかの用途の安全性を壊す。
2. スコープ（`related_files`外・KLK-012と衝突）: KLK-012が2026-08-16に完了（`ffaf02b`）したことで**解消済み**。もはや不統一維持の根拠にならない。
3. 影響半径: KLK-010執筆当時の3件から現在4件（`validate_ticket_state.py`／`record_metrics.py`／`scripts/batch_loop.py`／`scripts/list_tickets.py`。M2対応）。KLK-012で `is_ticket` に相対パス対応が入ったことで、両者の乖離幅（`sub/tickets/active/...`・`x/../tickets/active/...` 等）は縮小した。しかし境界チェックなし部分文字列一致に起因する `mytickets/active/...`・`atickets/active/...` 等の過剰検知ギャップはKLK-012の変更範囲外で残存する（このギャップは `guard_bash_writes` 側の意図的な再現率優先設計そのものであり、バグではない）。
   結論: 根拠2は解消したが、根拠1（用途の相違）は現在も単独で不統一維持を正当化するのに十分であり、根拠3（影響半径縮小）はこの結論を補強する（統一の必要性がさらに下がった）。**よってKLK-010 D2の結論（統一しない）を維持する。**
   KLK-012からの申し送りM1（相対Writeの一部allow化）・R10（相対形でのfail-open、`tickets_dir_for`の制約）は必須入力として検討したが、いずれも `is_ticket` 単体の相対パス解決能力の限界であり、`is_ticket`↔`is_guarded_token` の統一/不統一という論点とは**直交**する。統一しても `is_guarded_token` は `tickets_dir_for` を使わないためM1/R10は解消されない。M1/R10自体のクローズ（`validate_ticket_state.py` でのcwd相対解決の実装、reviewerの提案）はAC4の範囲外（AC4は判定基準の統一/不統一の明示のみを要求）であり、本チケットでは実施しない。必要性が高いと判断されれば別チケットの候補とする。
   確定した決定を `is_ticket` のdocstringと `guard_bash_writes.py` モジュールdocstringの該当箇所（D1のD2該当節・上記old_string参照）に反映し、KLK-020を参照させる（`docs/designs/KLK-010.md` 自体は改訂しない）。**意図的な不統一を固定するpinningテスト**（`mytickets/active/...` 等の境界なし一致で `is_ticket` と `_is_guarded_path`/`is_guarded_token` の結論が食い違うことを明示するテスト）を新規追加し、将来「バグとして無自覚に修正される」ことを防ぐ。

**D3（README「ルールを変更するとき」の適用範囲）— 対象外を明示するaddendumを追記する。** 同節は `_ticket_lib.py` の状態機械定数（`VALID_STATUS`等）専用であり、パス判定関数（`is_spec`/`_is_guarded_path`/`_is_guarded_path_component`/`is_ticket`/`is_project_spec`）の変更を想定していない（investigation.md E節）。新セクションを丸ごと新設するのは過剰なため、既存の3ステップ末尾に短い注記を追記し、(1)本節は状態機械定数専用でありパス判定関数には適用されないこと、(2)パス判定関数を変更するときは同型の判定が他に独立実装されていないか棚卸しし共有できるものは`_ticket_lib.py`へ集約すること（本チケットの `is_spec_basename` が前例）、(3)変更・非変更の両方についてテストを追加し全件パスを確認すること、の3点を明示する。

**代替案と却下理由:**
| 案 | 却下理由 |
|---|---|
| SPEC.md大小区別をAC名指しの2箇所（`is_spec`/`_is_guarded_path`）のみ是正し、`_is_guarded_path_component`/`is_project_spec`はスコープ外とする | ACの「期待する動作」自身が掲げる非対称回避の原則に反し、2箇所を残すことが新たな取り残しになる。人間確定済み方針「一律」とも整合しない |
| 4箇所を各自個別にcase-insensitive化し、共有ヘルパーを作らない | DRY化しないと「4箇所が独立実装で少しずつ異なる」という本チケットの根本原因（再発パターン）をそのまま残す。将来また1箇所だけ変更漏れが起きるリスクが高い |
| `is_ticket` の境界判定を `_is_guarded_path` 側にも採用して統一する（厳密化） | `guard_bash_writes` の再現率優先という設計意図（KLK-010で複数版にわたりハードニングした前提）を壊し、埋め込まれた/難読化されたパスの見落としを増やす回帰リスクがある |
| `_is_guarded_path` の部分文字列一致を `is_ticket` 側にも採用して統一する（緩和） | `is_ticket` の呼び出し元（状態機械検証等）が過剰検知し、`mytickets/...`等の非チケットファイルへの正規のWrite/Editを誤ってブロックする機能退行を招く |
| README.mdに「パス判定関数を変更するとき」という新セクションを丸ごと新設する | 既存節への短い注記追記で目的（適用範囲の明確化・再発防止の手がかり）を十分達成でき、過剰な文書追加を避ける |

**新設する共有ヘルパー（`_ticket_lib.py`、`is_project_spec` の近傍に配置）:**
```python
def is_spec_basename(name):
    """basename が大小を区別せず 'SPEC.md' と一致するか（KLK-020: is_spec /
    _is_guarded_path / _is_guarded_path_component / is_project_spec の
    SPEC.md 判定を一本化する単一の正規化ポイント）。"""
    return isinstance(name, str) and name.upper() == "SPEC.MD"
```

**各箇所の変更（old_string → 方針）:**
- `guard_spec_writes.is_spec`: `return n.rsplit("/", 1)[-1] == "SPEC.md"` → `return lib.is_spec_basename(n.rsplit("/", 1)[-1])`
- `guard_bash_writes._is_guarded_path`: `return os.path.basename(path) == "SPEC.md"` → `return lib.is_spec_basename(os.path.basename(path))`
- `guard_bash_writes._is_guarded_path_component`: `return "SPEC.md" in path.split("/")` → `return any(lib.is_spec_basename(seg) for seg in path.split("/"))`
- `_ticket_lib.is_project_spec`: `return n == _normalize_path(target) or n == "docs/SPEC.md"` → ディレクトリ部分は現状維持・basename部分のみ `is_spec_basename` 経由にする補助関数を挟む（例: `n_dir, _, n_base = n.rpartition("/")` で分解し、対象側も同様に分解して `n_dir == target_dir and is_spec_basename(n_base) and is_spec_basename(target_base)` の形にする）。ネスト除外（KLK-016 D3）を壊さないこと。実装の最終形はimplementerの裁量とするが、**ディレクトリ部分の比較は大小を区別したまま**にすること（D1のスコープ限定）。

## 7. マイグレーション戦略

データ・スキーマの移行は不要。全ての変更はSPEC.md判定・チケット判定の「一致範囲が広がる」方向のみの変更であり（`spec.md`等が新たにTrue判定される）、既存の判定結果（True→False の後退）は発生しない。`docs/.spec_state.json`はhookが自動生成するサイドカーであり、手動移行は不要（次回Write/Edit時に新しい判定範囲で自然に追随する）。Phase間に強い依存関係はなく、Phase 1→2→3の順に実装することを推奨するが、Phase 2（設計判断の記録）はPhase 1のコード変更と独立して先に固めてもよい。

## 8. ロールバック戦略

コード変更（Phase 1・2）とドキュメント変更（README addendum・docstring、Phase 2・3）は可能な限り別コミットに分離する。問題発生時は該当Phaseのコミットのみを個別に取り消せる。

```bash
# 特定Phaseのみを取り消す場合
git revert {Phase該当コミットハッシュ}

# 全体を取り消す場合（依存が薄いため一括でも安全）
git revert {Phase3コミットハッシュ} {Phase2コミットハッシュ} {Phase1コミットハッシュ}
```

サイドカー（`docs/.spec_state.json`）はhook自動生成のため、revert後の次回Write/Editで旧判定範囲に自然に戻り、手動のデータクリーンアップは不要。
