# [KLK-001] batch-loopの1チケット1セッション外部駆動化 設計

> このファイルはarchitectが生成・更新するチケット単位の設計書です。
> チケット KLK-001 に対応します。implementer・tester・reviewerが参照します。
> spec_version は「n/a」: 本チケットは docs/SPEC.md を持たないKit自身の改善であり、
> 人間承認により Kit自身のドキュメント（docs/batch-loop.md・.claude/commands/batch-loop.md・
> .claude/commands/start-loop.md・.claude/agents/orchestrator.md）を要件の正とする
> （KLK-001 ログ 2026-07-19 の承認記録を参照）。REQ/SCR/IF-ID の参照は該当なし。

## 1. 目的

現行の `/batch-loop` は単一メインスレッドが全チケットのサブエージェントレポートを蓄積したまま連続実行するため、後続チケットほどトークン消費が累積する。本Kitは状態をチケットファイルへ外部化済みであることを活かし、チケットごとに `claude -p "/start-loop {ID}"` を新規セッションでヘッドレス起動する外部駆動スクリプト方式へ変更し、コンテキスト累積を解消する。その際、docs/batch-loop.md の事前承認セマンティクス（正常完了時のみ前進・異常系で停止・人間の確認機会の保全）を新方式へ写像して維持する。

要件の正: docs/batch-loop.md（事前承認セマンティクス）・.claude/commands/batch-loop.md（手順）・.claude/commands/start-loop.md（起動時チェックリスト）・.claude/agents/orchestrator.md（委譲・Never規則）。

## 2. 現状

**現在のフロー:**
```
人間: /batch-loop APP-001 APP-002
  → メインスレッド（1セッション）が:
     1. ID列検証（active/存在・cancelled/blocked除外）
     2. バッチ事前承認の確認（done到達時は要約報告のみで停止せず次へ / 最終IDで停止 /
        差し戻し・リトライ上限超過・blocked で即停止）
     3. 起動時チェックリスト（Autoモード・14日blockedトリアージ・in_progress上限・done/件数）
     4. 同一セッション内で APP-001 → APP-002 を連続ループ
  → 各チケットの investigator〜reviewer のサブエージェントレポートが
     メインスレッドのコンテキストに累積し、後続チケットほどトークン消費が増える
```

**関連する既存ファイル（investigator調査メモより）:**
- `docs/batch-loop.md`: 事前承認セマンティクスの正。(1) done到達時の要約報告は省略せず「待たない」だけ、(2) 最終チケットで停止、(3) 承認は列挙ID間の遷移1回ずつのみ、(4) 差し戻し・リトライ上限超過・blocked発生で即停止
- `.claude/commands/batch-loop.md`: コマンド手順（ID列検証→事前承認→起動時チェック→連続実行）
- `.claude/commands/start-loop.md`: 起動時チェックリスト4点（Autoモード確認・14日トリアージ・in_progress上限・done/件数）に人間対話が含まれ、ヘッドレスでは袋小路になる
- `.claude/agents/orchestrator.md`: done後の継続は人間判断（Never: `Start improvement loop without human instruction` / `Skip reporting to human after reviewer approval`）。従来のバッチはこの判断の事前承認で成立していた
- `.claude/hooks/_ticket_lib.py`: frontmatterパーサ・`VALID_STATUS`・`IN_PROGRESS_STATUSES`/`IN_PROGRESS_LIMIT`・`RETRY_CAPS`（stdlibのみ）
- `.claude/settings.json`: `permissions.defaultMode: "auto"` はCLI v2.1.142以降プロジェクトsettingsからは無視される（investigator実測）。Bash allowリストはループが使うコマンド群（git・python3・mv等）をカバー済み
- `scripts/` は存在しない（新設）。リポジトリ内シェルスクリプト0件・既存スクリプトは全てPython（stdlibのみ）
- `docs/worktree-policy.md`: チケット書き込みはメインworktreeに一本化

## 3. 設計方針

**採用する方針:**

1. **駆動スクリプトは Python（stdlibのみ）で `scripts/batch_loop.py` として新設する**
   - 既存スクリプト群（hooks・metrics）とのスタック統一。`_ticket_lib.py` の frontmatterパーサ・status定数を `sys.path` 経由でimportして再利用し、判定ロジックの単一の真実を維持する
   - `tests/` のunittest＋CI（test.yml）にそのまま載せられる（bashでは判定ロジックのテスト整備コストが高い）
   - ファイル名はチケットAC例の `batch-loop.sh` ではなく `batch_loop.py` とする（Pythonのimport可能名にしないとテストから参照できない。ACの「例:」は拘束しないと解釈し、reviewer向けにここに明記する）
   - **fail-closed**: hooksのfail-open規約とは逆に、駆動スクリプトは内部エラー・判定不能時に停止する。hooksは「ループを止めない」ことが要件だが、本スクリプトは人間がターミナルで実行する監督ツールであり「疑わしければ止まって見せる」が安全側

2. **`--permission-mode acceptEdits` を既定とし、明示的に渡す**
   - `defaultMode: "auto"` は現行CLIでプロジェクトsettingsから無視されるため明示必須（investigator実測）
   - `acceptEdits` はファイル編集を自動承認しつつ、Bashはsettings.jsonのallow/denyリストとPreToolUse hook（deny/ask）を通常どおり通す。ループに必要なBashコマンドはallowリストでカバー済み
   - `bypassPermissions` は既定にしない: guard_spec_writes等のask系ゲートを貫通し（hooks README「--dangerously-skip-permissions は貫通」と同系）、機械強制の前提を壊す
   - ヘッドレスで応答不能なask/承認プロンプトはツール実行拒否に落ちる想定（検証タスクV-1）。拒否によりチケットがdoneへ到達しなければ駆動側が停止するため、想定が外れても安全側に倒れる
   - `--permission-mode` フラグで上書き可能とする（bypassPermissionsを選ぶのは人間の明示判断）

3. **完了判定はファイル状態を正とし、終了コードは異常検出の補助に留める**（人間の決定事項）
   - 成功 = チケットが `tickets/done/` に存在し frontmatter `status: done`。`active/` に `status: done` のまま残る中間状態（Edit→mv間の中断）は異常として停止する
   - リトライ上限超過は独立statusを持たず blocked に包含される（調査メモ）ため、blocked検出時はブロッカーセクション本文を表示して停止する
   - `claude -p` の終了コード非0は内容にかかわらず異常終了として停止する（doneに到達していても停止して報告。網羅仕様が未文書化のため安全側）

4. **事前承認セマンティクスの写像: 「差し戻しで即停止」は「セッション境界停止」に写像する（既定ON）**
   - 1チケット=1セッションの新モデルでは、セッション内の差し戻し（tester fail / reviewer reject）は /start-loop 単体実行と同じ自律実装ループの正常動作であり、セッション中に外部から即停止させる手段はない
   - 代わりに駆動スクリプトが各チケット開始前に `retry_counts` をスナップショットし、セッション終了後に増分を検出したら **done到達済みでも次チケットへ進まず停止して報告する**。これにより現行セマンティクスの意図（差し戻しが発生したバッチを人間の確認なしに進めない）を、観測可能な最も早いタイミングで維持する
   - AC2の停止条件列挙（blocked・リトライ上限超過・異常終了）に対し本設計は上位互換（停止条件の追加）であり、AC2括弧書きの「docs/batch-loop.md の事前承認セマンティクスを維持」に寄せた。緩和ではないためACの弱体化に当たらない
   - `--continue-on-rework` フラグで人間がバッチ開始時に明示的に緩和できる（事前承認の範囲を人間が広げる操作として整合。既定は安全側）
   - ヘッドレスではリトライ予算リセット（ask）は承認不能＝発生しないため、増分検出は単調増加前提で成立する（検証タスクV-1で確認）

5. **done後の同一セッション内自走の抑止は「事前承認を与えないこと」を一次防衛とする**
   - orchestratorのNever（人間指示なしの改善ループ開始・reviewer承認後の報告スキップ禁止）により、事前承認が無ければdone後に次チケットへ進む根拠がそもそも無い。駆動プロンプトには従来の「バッチ事前承認」を**含めない**
   - 二次防衛として駆動プロンプトに「このセッションで処理するのは {ID} 1件のみ」を明記（検証タスクV-4）、三次防衛として `--max-turns` と「境界検査で他バッチ対象チケットのstatus変化を検出したら停止」を置く

6. **`/batch-loop` スラッシュコマンドは「検証と案内」へ役割変更する（実行はしない）**
   - セッション内から `claude -p` をネスト起動しない（既存ポリシーと整合。調査メモ）。コマンドは `--dry-run` でプリフライトを代行実行し、人間がターミナルで実行すべきコマンドラインを提示して終了する
   - バッチ事前承認の実体は、スクリプトが実行前に表示する承認サマリへの人間のy/N応答に移る（人間がセッション外で物理的に起動・承認する形になり、従来より人間の関与はむしろ強まる）

**代替案と却下理由:**
| 案 | 却下理由 |
|---|---|
| bashスクリプト（scripts/batch-loop.sh） | frontmatter解析・判定ロジックの再実装とテスト整備が高コスト。既存資産（_ticket_lib.py・unittest CI）を再利用できない。リポジトリ内シェルスクリプト0件の慣行にも反する |
| `--permission-mode bypassPermissions` を既定 | ask系hook（SPECゲート・リトライリセット・in_progress上限）を貫通し機械強制を無効化する。フラグでの明示上書きのみ許す |
| 差し戻し停止条件を撤廃しAC2の文言列挙に限定 | docs/batch-loop.md の事前承認セマンティクス（差し戻し発生バッチを人間確認なしに進めない）の緩和になる。AC2括弧書きと矛盾 |
| セッション内プロンプト注入で差し戻し時に即セッション終了させる | /start-loop 単体の自律実装ループ規約と矛盾し、チケットを中間statusで放置する。差し戻しの扱いがバッチ時だけ変わる二重規範になる |
| /batch-loop コマンド自身が Bashで claude -p を起動 | セッションのネスト起動。トークン累積の解消にもならず（親セッションが待機・出力を吸う）、既存の禁止事項に反する |
| 完了判定に .metrics.jsonl / .metrics_state.json を第一義で使う | サイドカーはgitignore対象・hook管理の観測用であり、欠損時の駆動不能を招く。frontmatterが正（読み取りのみなら併用可だが依存しない） |
| 駆動スクリプトがチケットへバッチ実行ログを書き込む | チケット書き込みはorchestrator専任（単一ライター原則）。駆動スクリプトは読み取りのみとし、書き込みは一切しない |
| `--output-format json` で session_id / cost を取得 | 実行中の進捗が人間に見えなくなる。v1は標準入出力を継承したtext表示（ライブ監視）を優先。コスト観測は将来課題（メトリクスはhookが記録済み） |

**ファイル構成（変更・追加）:**

```
└── batch_loop.py            ← 新設。外部駆動スクリプト（stdlibのみ・fail-closed）
tests/
└── test_batch_loop.py       ← 新設。プリフライト・境界判定のunitテスト（claude起動はモック）
docs/
└── batch-loop.md            ← 全面改訂（外部駆動ガイド化）
.claude/commands/
├── batch-loop.md            ← 全面改訂（検証・案内コマンド化）
├── start-loop.md            ← 33行目の誘導文を微修正
└── plan-tickets.md          ← 64行目の誘導文を微修正
.claude/commands/setup.md    ← 72行目（診断表）の誘導文を微修正
CLAUDE.md                    ← スラッシュコマンド一覧の/batch-loop行・ポリシー表「バッチ連続実行の事前承認」行
README.md                    ← ディレクトリツリー（scripts/追加）・コマンド表・使用例
CHANGELOG.md                 ← [Unreleased] に Added / Changed を追記
```

**主要なインターフェース:**
```
python3 scripts/batch_loop.py [オプション] ID [ID ...]

引数:
  ID ...                     実行順のチケットID（1件以上。重複不可）
オプション:
  --dry-run                  プリフライトのみ実行して終了（/batch-loopコマンドが利用）
  --yes                      実行前の承認プロンプト（y/N）をスキップ
  --permission-mode MODE     claudeへ渡す権限モード（既定: acceptEdits）
  --max-turns N              セッションあたりのターン上限（既定: 200。0で無効）
  --max-budget-usd X         セッションあたりの費用上限（既定: なし）
  --timeout-min N            セッションあたりの実時間上限（既定: なし）
  --continue-on-rework       差し戻し検知（retry_counts増分）でも次チケットへ進む（既定: 停止）
  --allow-missing-spec       docs/SPEC.md不在を人間承認済みとしてSPEC免除前提をプロンプトに付す
  --claude-cmd PATH          claude CLIのパス（既定: claude）

終了コード: 0=全チケットdone到達 / 2=プリフライト・引数エラー / 3=停止条件による中断 /
            1=想定外の内部エラー / 130=SIGINT（子プロセスをterminateして中断）
```

- リポジトリルートは `Path(__file__).resolve().parents[1]` で解決し、`claude` は cwd=リポジトリルートで起動する（人間がどこから実行しても同じ挙動）
- `_ticket_lib.py` は `sys.path.insert(0, <root>/.claude/hooks)` でimportする。import失敗時は停止（fail-closed）
- 引数はチケットIDのみを受け付け、チケットの**パスを引数に取らない**（/batch-loopが `--dry-run` をBash実行する際、guard_bash_writes.py のパス言及検査に掛からない構造を維持する。将来パス引数を追加する場合は READONLY_SCRIPTS への登録が必要になる）

**プリフライト（現行 .claude/commands/batch-loop.md 手順2と起動時チェックリストの機械化。全件チェックして違反を一括表示し、1件でもあれば開始しない）:**

| # | 検査 | 失敗時 |
|---|---|---|
| P1 | リポジトリルートに `tickets/active/` が存在。git利用可能なら `git rev-parse --git-dir` と `--git-common-dir` を比較し、linked worktreeなら停止（チケット書き込みのメインworktree一本化。docs/worktree-policy.md） | 停止 |
| P2 | 各IDが `tickets/active/{ID}_*.md` に一意に存在（0件・複数件マッチはエラー）。引数内のID重複もエラー | 停止 |
| P3 | 各チケットのstatusが `cancelled` / `blocked` / `done` のいずれでもない（VALID_STATUS外・frontmatter解析不能もエラー。todo〜test_passed の中間statusからの再開は許可） | 停止 |
| P4 | in_progress件数（IN_PROGRESS_STATUSES該当）が IN_PROGRESS_LIMIT(3) 未満（ヘッドレスで着手時のask hookを踏ませない。人間の決定事項） | 停止（チケット整理を案内） |
| P5 | `status: blocked` かつ updated から14日超のチケットが active/ に存在しない（起動時チェックリストのトリアージ対話がヘッドレスで袋小路になるため事前排除） | 停止（/triage を案内） |
| P6 | `docs/SPEC.md` が存在する。不在時は `--allow-missing-spec` 指定が必須（SPEC免除の人間承認をフラグで明示させる。人間の決定事項） | 停止（フラグを案内） |
| P7 | `claude --version` が実行可能（バージョン文字列を実行ログに表示。CLI挙動変化の切り分け材料） | 停止 |
| P8 | 全対象チケットの status / retry_counts をスナップショット（境界判定の基準） | - |
| P9 | `tickets/done/` が20件超なら警告表示（/archive 提案。開始は妨げない） | 警告のみ |

プリフライト通過後、承認サマリ（対象ID・タイトル・現status・実行順・停止条件・権限モード・ガード値）を表示し、y/N確認を取ってから開始する（`--yes` でスキップ可）。**このy/N応答が従来のバッチ事前承認の実体**となる。

**駆動プロンプト（チケットごとに組み立てて `claude -p` へ渡す）:**
```
/start-loop {ID}

【外部バッチ駆動の前提（scripts/batch_loop.py が起動したヘッドレスセッション）】
- このセッションで処理するのはチケット {ID} の1件のみ。done到達（reviewer承認・done/へ移動・
  完了ログ追記まで）または blocked 化の時点で、要約を報告してセッションを終了すること。
  他のチケットへは着手しない。次チケットへの継続判断は駆動スクリプトと人間が行う
- 権限モードは駆動側が --permission-mode {MODE} で明示済み。起動時チェックリストの
  「Autoモード確認」は充足として扱ってよい。14日blocked・in_progress上限は駆動側の
  プリフライトで確認済み。done/件数超過があれば報告のみ行い停止しない
- 人間の応答が必要な場面（AskUserQuestion・リトライ予算のリセット・改善ループ判断・
  破壊的操作の確認）では待機せず、チケットをblocked化（ブロッカーセクションへ理由を記録）
  して報告・終了すること
（--allow-missing-spec 指定時のみ以下を追記）
- docs/SPEC.md が無い/対象外であることは人間が承認済み（チケットのログを参照）。
  SPECゲートで停止せず、チケットに記載された要件の正に従うこと
```

**claude起動（チケットごと・逐次）:**
```
claude -p "<駆動プロンプト>" --permission-mode {MODE} [--max-turns N] [--max-budget-usd X]
```
- 標準入出力は継承（人間がターミナルでライブ監視できる）。`--timeout-min` 指定時はPython側でタイムアウト管理し、超過時は子プロセスをterminate→異常終了扱い
- `--bare` は付けない（hooks・CLAUDE.mdがロードされなくなる。investigator実測）

**境界判定（セッション終了ごと。上から順に評価し、最初に該当した停止条件で報告・中断する）:**
```
1. exit_code != 0                       → 停止「異常終了」（doneに到達していても停止・両事実を報告）
2. チケットがactive/にstatus: doneで残存 → 停止「完了手続き不完全」（done/へ未移動。/start-loop再開を案内）
3. status == blocked                    → 停止「blocked」（ブロッカーセクション本文を表示。
                                           リトライ上限超過もここに包含される）
4. status != done                       → 停止「未完了」（中間statusのまま終了。再開コマンドを案内）
5. 他のバッチ対象チケットのstatusが     → 停止「範囲外変更の検知」（1セッション1チケットの
   スナップショットから変化              前提が破れた疑い）
6. retry_counts がスナップショットから  → --continue-on-rework 無し: 停止「差し戻し発生
   増加                                    （done到達済み）」／有り: 報告して次へ進む
7. 上記いずれでもない（done/にdone）    → 完了報告して次チケットへ。最終チケットなら
                                           バッチサマリを表示して終了（exit 0）
```
- 判定は毎回チケットファイルを再読取（状態の外部化。スクリプトのメモリに依存するのはスナップショットのみ）
- 各境界で1行サマリ（ID・所要時間・status遷移・retry増分・exit code）を表示し、最後に全体サマリを出す

## 7. マイグレーション戦略

- 追加中心の変更であり、データ・チケット・hookの移行はなし

## 8. ロールバック戦略

スクリプトは状態を持たず（tickets/へ書き込まない・サイドカーにも触れない）、revertのみで完結する。

```bash
# 本チケットのコミット群を逆順にrevert（scripts/・tests/・docs改訂が対象）
git revert {Phase3コミット} {Phase2コミット} {Phase1コミット}
# バッチ実行中に問題が出た場合の即時停止は Ctrl-C（子プロセスterminate・チケットは中間statusで外部化済み）
# 中断チケットの再開: /start-loop {ID}（対話セッション）
```

旧 docs/batch-loop.md・.claude/commands/batch-loop.md はGitヒストリから復元可能。hooks・チケットに変更がないためロールバックの副作用はない。
