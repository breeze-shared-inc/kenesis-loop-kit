## 3. 設計方針

### 3-1. 採用する方針: 責務を3レイヤに分離する

現行コードの破綻は「1つの正規表現／分割がシェル構文・パス判定・書き込み判定を兼ねている」ことに起因する。次の3レイヤへ分離し、**各レイヤは自分の責務だけを解決する**。

| レイヤ | 責務 | 実現手段 | 解決するケース |
|---|---|---|---|
| **L1 字句** | クォート境界を尊重して「演算子」と「語」を分ける。コマンド置換の抽出 | 自前の走査（クォート状態のみ追跡）＋ 語チャンクは **`shlex.split`** でクォート解除 | A-1・A-3b・A-3c・B-4c・B-6a |
| **L2 パス** | 任意のテキストから保護対象パスを検出する | パス様候補の抽出 → `os.path.normpath` → 除外 → 分類 | B-5・B-6b |
| **L3 構文** | ステートメント／パイプ／リダイレクトの単位で書き込みベクタを判定する | L1のトークン列に対する規則適用 | A-2・A-3a・B-4a/b |

**AC1（shlex化）への対応の分離を明示する。** investigator の実測どおり `shlex.split` は演算子（`&&` `||` `;` `|` `>` `>>`）を特別扱いしない。そこで:
- **演算子の切り出し**は L1 の自前走査が担う（クォート状態を追跡し、**クォート外の演算子だけ**を切り出す）
- **語のクォート解除**は `shlex.split(chunk, comments=False, posix=True)` が担う（`-i''` → `-i` の正規化、`-F'|'` → `-F|` の連結、`"..."` 内の `'...'` の保持）

`shlex.shlex(..., punctuation_chars=True)` を採らない理由は §3-7 の代替案表に示す（**posix=True では「クォートされた `>`」と「演算子の `>`」がトークン文字列として区別できず、AC1 が明示的に要求する「クォート内の `>` で特殊構文判定をしない」を満たせない**ため）。

### 3-2. L1: 字句レイヤ（クォート走査 + shlex.split）

1. **前処理**: `\`+改行（行継続）を空白へ畳み、残る改行を `;` へ置換する。改行はステートメント区切りとして `;` と等価であり、クォート内の改行が `;` に変わってもL2の候補抽出（`;` も改行も候補の境界）に影響しない。行継続の畳み込みは「継続行の先頭がコマンド名と誤認される」既存の誤denyも同時に消す。
2. **走査**: 文字列を1文字ずつ進めながら、状態（通常／`'` 内／`"` 内）を追跡する。
   - `'` 内: 次の `'` まで全て literal（演算子・置換・エスケープを一切解釈しない）
   - `"` 内: `\` エスケープを消費し、`$(` とバッククォートのみ解釈する
   - 通常: `\` エスケープを消費、`'`/`"` で引用開始、`$(` / `` ` `` / `<(` / `>(` を置換として抽出、**演算子文字 `;&|<>` を最長一致で切り出す**
   - 抽出した置換は内側テキストを記録し、その位置には語のプレースホルダ `__KLK_SUBST__` を置く（引用の釣り合いを壊さない）
3. **語チャンクの解決**: 演算子で区切られた語チャンクを `shlex.split` に渡し、クォート解除済みトークンへ展開する。
4. **失敗時**: 未閉じクォート・未閉じ括弧・末尾の孤立エスケープでは `ValueError` を送出し、**degraded mode（§3-5）へ落とす**。

### 3-3. L2: パスレイヤ（候補抽出 → 正規化 → 除外 → 分類）

現行の「トークン全体を1つのパスとみなす」判定をやめ、**任意テキストからパス様の連続（`[A-Za-z0-9_.\-/]+`）を候補として取り出し、候補ごとに判定する**。

**適用順序（B-5 と B-6b を同時に解決するための要）:**

```
① 候補抽出   PATHISH_RE.findall(text)        ← トークン境界に依存しない（AC5）
② 正規化     os.path.normpath(候補)          ← ".." を解決（AC4: B-6b）
③ 除外       正規化後のパス成分に ".claude" があれば対象外
④ 分類       tickets/active|done → Templates・_index.md を除いて保護対象
             それ以外は basename == "SPEC.md" なら保護対象
```

- **③を②の後に行うこと**が B-6b の修正の本体である。`./tickets/active/../../.claude/../tickets/active/X.md` は正規化で `tickets/active/X.md` となり `.claude` 成分が消えるため、除外されず保護対象と判定される。
- **①が B-5 の修正の本体である。** `python3 -c "open('docs/SPEC.md','w')..."` は shlex 解除後に `open(docs/SPEC.md,w).write(x)` という1トークンになるが、候補抽出は `docs/SPEC.md` を切り出せる。**「SPEC.md の部分文字列包含」ではなく「パス候補の basename 完全一致」で判定する**ため、`MYSPEC.md` や `SPEC.md.bak` は保護対象にならず、誤deny再発を招かない。
- ③はパス「成分」の一致（`".claude" in p.split("/")`）で行う。現行の `".claude/" in t` は `foo.claude/` のような無関係な名前も除外してしまう（＝すり抜け方向の穴）ため、成分一致の方が厳密で安全側。
- tickets の検出は現行と同じ部分文字列（`"tickets/active" in p`）を維持する（**判定を狭めないため**。`/Templates/`・`_index.md` の除外も現行のまま）。

### 3-4. L3: 構文レイヤ（ステートメント／パイプ／リダイレクト）

**「証拠があるときだけ deny する」を原則とする。**

1. **リダイレクト（出力）** — ステートメント単位で判定する（現行のコマンド全体走査を廃止 ＝ A-3c の修正）。リダイレクト先が
   - 保護対象パスに言及していれば **deny**
   - **このコマンド内で保護対象パスを代入された変数**を参照していれば **deny**
   - それ以外（未知の変数・置換結果）は **allow**
   
   現行は「コマンドのどこかが保護対象に言及していれば、`$` を含むリダイレクト先を一律 deny」しており、これが A-3c（`cat tickets/... && echo x > "$TMP"`）の巻き添えを生んでいる。一方で既存テスト `test_redirect_to_variable_deny`（`f=tickets/active/APP-001.md; cat x > "$f"`）は維持しなければならない。**両者を区別する唯一の構造的な差は「その変数が同一コマンド内で保護対象を代入されているか」**であり、変数代入の追跡でこれを実現する。この絞り込みは A-3c が明示的に要求する変更であって、AC6 が守る既存 deny 対象（リテラル先・代入済み変数先）は保持される。
2. **heredoc** — クォート外の `<<` / `<<<` 演算子が、保護対象に言及するステートメントに現れた場合に deny（現行の `"<<" in command` を演算子判定へ置換 ＝ A-3b の修正）。
3. **パイプライン** — ステートメントをパイプ演算子で分割し、**どこかの区間が保護対象に言及していれば全区間の先頭コマンドを検査する**（現行の方針を維持。`find tickets/... | xargs rm` を止めるため）。
4. **セグメント** — 先頭コマンド（環境変数代入・先頭 `(` を剥がす）が `ALLOWED_HEADS` にあるかを見て、`sed` / `find` / `git` / `awk` の追加規則を適用する。
5. **コマンド置換・プロセス置換** — L1 が抽出した内側テキストを **同じ判定へ再帰**させる（B-6a）。深さ上限 `MAX_SUBST_DEPTH = 3`。上限到達時は「内側が保護対象に言及していれば deny」という保守側の打ち切りにする（単純に無視すると `$($($(rm ...)))` が抜け道になるため）。無限ループ防止は「走査インデックスが常に前進する」ことと深さ上限の2点で担保し、総処理量は O(深さ × コマンド長) に収まる。

**判定順序（ステートメント単位）:** ① 出力リダイレクト（証拠ベース・ゲートなし） → ② heredoc（言及ゲートあり） → ③ 言及ゲート → ④ パイプ区間ごとのセグメント検査。①を先に置くことで `check_spec_structure.py ... > docs/SPEC.md`（`READONLY_SCRIPTS` 例外を持つセグメント）が引き続き deny される（AC6）。

### 3-5. degraded mode（fail-open 方針との整合）

L1 が `ValueError` を返す入力（未閉じクォート等）は、**多くの場合シェル自身も実行できない**。しかし `ls tickets/active # don't` のように **bash ではコメントとして成立し、shlex では未閉じクォートになる**入力が実在する。ここで単純に allow すると `rm tickets/active/X.md #'` が素通りする。

そこで `ValueError` は **allow ではなく「簡易判定へのフォールバック」**とし、簡易判定は `command.split()` による素朴なトークン列に対して L2 の言及判定・`segment_violation`・旧 `REDIRECT_RE`（リテラル先のみ）を適用する。**内部例外（`ValueError` 以外）は従来どおり allow**（README の fail-open 方針）。この二段構えは「解析できない入力では現行相当の保守的判定に戻る」という意味であり、fail-open 方針（＝内部エラーでループを止めない）と矛盾しない。誤deny が起きうるのは「シェルとしても曖昧な入力」に限られる。

**`#` の扱い:** クォート内・クォート外を問わず `#` を特別扱いしない（`shlex.split` は `comments=False` で呼ぶ）。AC1 が要求する「クォート内の `#` で特殊構文判定をしない」は自動的に満たされる。クォート外のコメント除去は行わない（テキストを捨てない＝安全側）。副作用としてコメント中に `;` と書き込みコマンドがある場合に保守的な deny が起きうるが、これは既存挙動と同方向であり許容する。

### 3-6. 設計判断（D1〜D3）

#### D1: awk の内蔵リダイレクトは **本チケットのスコープに含める**（別チケットへ切り出さない）

- **理由1（自ら開ける穴は塞ぐ）:** 現行の `REDIRECT_RE` 全体走査は `awk '{print > "path"}'` を偶然 deny できている（investigator 実測）。AC1・AC2 に従って L1/L3 を導入し、AC3 に従って `awk` を `ALLOWED_HEADS` へ加えると、**この経路は本チケットの変更が原因で新規の false negative になる**。「既存の穴を塞がない」ことと「自分で穴を開ける」ことは別問題であり、後者は許容できない。
- **理由2（SPEC.md にバックストップが無い）:** `awk '{print > "docs/SPEC.md"}'` は Stop hook のドリフト検知でも捕捉されない（検知対象は `tickets/active|done/*.md` のみ）。無防備な経路を新設することになる。
- **理由3（コストが小さい）:** 後述の規則は1行で表現でき、A-3a（`awk -F'|' '{print $1}' tickets/...`）を誤denyしない。

**規則（awk）:** 先頭コマンドが `awk` のセグメントで、**保護対象に言及するトークンが `>` または `|` を含む**なら deny。正常な読み取りでは保護対象は「素のパス引数」として現れる（`>`・`|` を含まない）のに対し、内蔵書き込みは必ずプログラム文字列の中に `>`（`print > "p"` / `printf ... >> "p"`）または `|`（`print | "cmd"`）と同居する。`-F'|'` のトークンは `|` を含むが保護対象に言及しないため無害。

**一般化（sed）:** 同種の「スクリプト引数に埋め込まれた書き込み」は `sed` の `w` コマンド（`s/a/b/w FILE`・`/re/w FILE`）にも存在する。`sed` は既に `ALLOWED_HEADS` にあり、同じ関数を触るため、**`sed` にも同型の規則を入れる**（保護対象に言及するトークンが `w`＋空白＋非空白のパターンを含むなら deny）。これは AC の要求を超える追加の deny だが、(i) 既存 AC を弱めず、(ii) 誤検知面は「保護対象パスと `w ` を同時に含む sed スクリプト」に限られ極めて小さく、(iii) 同じ関数へ後日また手を入れる方が総コストが高い。**`perl` / `python3` / `gawk` / `mawk` は `ALLOWED_HEADS` に無く元から deny されるため、一般化の対象外**（＝この方針は「ホワイトリストに載るスクリプト実行系」にのみ適用する）。

#### D2: `_ticket_lib.is_ticket` との判定基準は **統一しない**（`guard_bash_writes.py` 内で完結させる）

- **目的が違う:** `is_ticket(path)` は「Write/Edit の対象ファイルが状態検証対象の実チケットか」を判定するもので、絶対パス・`/tickets/active/` 前後スラッシュ・`.md` 拡張子を要求する**厳密判定**である。本hookが必要とするのは「コマンド文字列の断片が保護対象に言及しているか」という**再現率優先の判定**で、相対パス・ディレクトリ指定（`tickets/active/`）・`SPEC.md`・引用符やコードの中に埋もれたパスまで拾う必要がある。統一すると `ls tickets/active/` や `docs/SPEC.md` を取りこぼす。
- **スコープと衝突:** 本チケットの related_files に `_ticket_lib.py` は含まれない。同ファイルのパス判定は **KLK-012（相対パス素通りの堅牢化・status todo）の対象**であり、並行チケットが同一シンボルを書き換えるとマージ競合と相互の回帰リスクを招く。
- **影響半径:** `is_ticket` は `validate_ticket_state.py` / `check_loop_integrity.py` / `record_metrics.py` から使われており、意味を変えると3hook＋そのテストへ波及する。本チケットの回帰基準線（スイート293件）の外へ出る。
- **対応:** 統一しない代わりに、**両者が意図的に別基準であること**を `guard_bash_writes.py` のモジュール docstring に明記し、将来「不統一だから直そう」という誤った修正を防ぐ。統一が望ましいと判断される場合は KLK-012 完了後に別チケットで扱う（申し送り §10）。

#### D3: 回帰確認スコープは **スイート全体293件 + 追加分**

### 4-2. L1: `lex(command)`

```python
def lex(command):
    """コマンドを (tokens, substitutions) へ分解する。
    tokens: [("w", クォート解除済みの語), ("op", 演算子文字列), ...]
    substitutions: $(...) / `...` / <(...) / >(...) の内側テキストのリスト
    未閉じクォート・未閉じ括弧・孤立エスケープでは ValueError を送出する。"""
    command = command.replace("\\\n", " ").replace("\n", ";")
    tokens, substs, buf = [], [], []

    def flush():
        chunk = "".join(buf)
        del buf[:]
        if chunk.strip():
            for t in shlex.split(chunk, comments=False, posix=True):
                tokens.append(("w", t))

    i, n, quote = 0, len(command), ""
    while i < n:
        c = command[i]
        if quote == "'":
            buf.append(c)
            if c == "'":
                quote = ""
            i += 1
            continue
        if quote == '"':
            if c == "\\" and i + 1 < n:
                buf.append(c); buf.append(command[i + 1]); i += 2; continue
            if c == "$" and i + 1 < n and command[i + 1] == "(":
                i = _take_subst(command, i + 2, ")", buf, substs); continue
            if c == "`":
                i = _take_backtick(command, i + 1, buf, substs); continue
            buf.append(c)
            if c == '"':
                quote = ""
            i += 1
            continue
        # 通常状態
        if c == "\\" and i + 1 < n:
            buf.append(c); buf.append(command[i + 1]); i += 2; continue
        if c in "'\"":
            buf.append(c); quote = c; i += 1; continue
        if c == "$" and i + 1 < n and command[i + 1] == "(":
            i = _take_subst(command, i + 2, ")", buf, substs); continue
        if c in "<>" and i + 1 < n and command[i + 1] == "(":      # プロセス置換
            i = _take_subst(command, i + 2, ")", buf, substs); continue
        if c == "`":
            i = _take_backtick(command, i + 1, buf, substs); continue
        if c in OPERATOR_CHARS:
            flush()
            op = next(o for o in OPERATORS if command.startswith(o, i))
            tokens.append(("op", op))
            i += len(op)
            continue
        buf.append(c); i += 1
    if quote:
        raise ValueError("no closing quotation")
    flush()
    return tokens, substs
```

補助関数（いずれも**インデックスを必ず前進させる**＝無限ループ防止）:
- `_take_subst(command, start, close, buf, substs)`: `start` から対応する `)` を探す（`(`/`)` の入れ子を数え、クォート内は数えない。`\` はエスケープとして2文字消費）。見つからなければ `ValueError`。内側テキストを `substs` へ追加し、`buf` へ `SUBST_PLACEHOLDER` を積み、`終端+1` を返す。
- `_take_backtick(command, start, buf, substs)`: 次の未エスケープのバッククォートまで。以下同様。

**注意点（implementer向け）:**
- `$((1+2))` は `(` の入れ子計数で正しく釣り合うため例外にはならない。内側 `(1+2)` が再帰評価されるが、保護対象に言及しないためゲートで素通りする。
- `OPERATORS` の最長一致により `2>&1` は `("w","2")`, `("op",">&")`, `("w","1")` になる。
- `find ... {} \;` の `\;` は通常状態のエスケープとして語チャンクに残り、`shlex.split` が `;` という語に解決する（演算子にはならない）。

### 4-3. L2: パス判定

```python
def _is_guarded_path(p):
    """正規化済みパス p が保護対象か。適用順序は §3-3 の③④。"""
    if ".claude" in p.split("/"):
        return False                      # スキル同梱のテンプレート等は対象外（正規化後に判定）
    if "tickets/active" in p or "tickets/done" in p:
        return "/Templates/" not in p and not p.endswith("_index.md")
    return os.path.basename(p) == "SPEC.md"


def guarded_paths(text):
    """任意テキストから保護対象パスを列挙する（トークン境界に依存しない）。"""
    out = []
    for cand in PATHISH_RE.findall(text):
        p = os.path.normpath(cand)
        if _is_guarded_path(p):
            out.append(p)
    return out


def is_guarded_token(text):
    """テキスト（トークン・コマンド断片のいずれでも可）が保護対象に言及するか。"""
    return bool(guarded_paths(text))


def mentions_guarded(values):
    """語の集合のいずれかが保護対象に言及するか。"""
    return any(is_guarded_token(v) for v in values)
```

### 4-4. L3: 構文判定

```python
def op_kind(op):
    if "<<" in op:            return "heredoc"     # << <<<
    if ">" in op:             return "redirect_out"  # > >> >& &> >| <>
    if "<" in op:             return "redirect_in"   # < <&
    if op in ("|", "|&"):     return "pipe"
    return "sep"                                     # ; ;; & && ||
```

**`find_violation(command, depth=0)`（既存名を維持・引数を追加）**
1. `tokens, substs = lex(command)`。`ValueError` なら `degraded_violation(command)` を返す。
2. 各 `substs` について: `depth >= MAX_SUBST_DEPTH` なら `is_guarded_token(inner)` が真のとき「深いコマンド置換内での保護対象への言及」で deny、偽なら無視。上限未満なら `find_violation(inner, depth + 1)` を再帰し、違反があればそれを返す。
3. `tokens` を `sep` 演算子でステートメントへ分割する。
4. ステートメントを先頭から順に処理し、各ステートメントについて **(a) 変数代入の記録 → (b) `statement_violation`** を実行する。最初の違反理由を返す。
5. 何も無ければ `None`。

**変数代入の記録:** ステートメント内の各パイプ区間について、先頭から連続する `NAME=VALUE` 形式の語（`ASSIGN_RE.match`）を取り、`is_guarded_token(VALUE)` が真なら `NAME` を `guarded_vars` へ追加する。`guarded_vars` はコマンド全体で1つ持ち、**左から右へ蓄積する**（`f=...; cat x > "$f"` の順序を再現するため）。

**`statement_violation(tokens, guarded_vars)`**
```
① 出力リダイレクト（ゲートなし・証拠ベース）
   op_kind(op) == "redirect_out" の各演算子について、直後の語トークンを target とする。
   - target が無い → 無視
   - op が ">&" / "&>" 等の fd 複製形で target が数字または "-" → 無視（2>&1）
   - is_guarded_token(target) → deny「リダイレクト（> {target}）による書き込み」
   - VAR_REF_RE で target 中の変数名を取り、guarded_vars に含まれれば deny（同上の理由文）
② heredoc
   op_kind(op) == "heredoc" が存在し、かつ ③の言及ゲートが真 → deny「ヒアドキュメントによる書き込みの可能性」
③ 言及ゲート
   ステートメント内の全語トークン（リダイレクト先を含む）に mentions_guarded を適用。
   偽なら None（このステートメントは検査対象外）
④ パイプ区間の検査
   "pipe" 演算子で語トークンを区間へ分割する。各区間の語リストからは
   「リダイレクト演算子の直後の語（＝リダイレクト先）」を除外する。
   各区間に segment_violation を適用し、最初の違反理由を返す。
```

## 7. マイグレーション戦略

データ・API・永続状態の移行は**なし**（hook は毎回プロセス起動で状態を持たない）。運用上の注意のみ:

1. **有効化タイミング:** `.claude/settings.json` が参照するのは `${CLAUDE_PROJECT_DIR}/.claude/hooks/guard_bash_writes.py` であり、**worktree 内の変更は develop へマージされるまで実行時の判定に反映されない**（作業セッション中に誤denyが消えることを期待しない）。マージ後の次回 Bash 実行から新判定になる。
2. **後方互換:** hook の入出力契約（PreToolUse の stdin JSON・`hookSpecificOutput.permissionDecision`・exit 0）と deny メッセージ本文は変更しない。呼び出し側（Claude Code・`tests/_util.py`）の変更は不要。
3. **段階的移行:** Phase 1 は「既存の許可・拒否の集合を変えずに解析基盤だけを差し替える」ことを狙う（`ALLOWED_HEADS` 据え置き）。判定集合が変わるのは Phase 2 のみで、変更点はすべて §4-6 のテストで表現される。

## 8. ロールバック戦略

単一ファイルの変更であり、Phase単位コミットのため Phase 粒度で戻せる。

```bash
# 個別Phaseの取り消し（worktree内。{hash}は該当Phaseのコミット）
cd ../kenesis-loop-kit.wt/KLK-010 && git revert --no-edit {hash}

# 未マージ段階での全体破棄（orchestratorが実施。develop は無傷）
git worktree remove ../kenesis-loop-kit.wt/KLK-010
git branch -D feature/KLK-010-{slug}

# develop へマージ後の取り消し
git revert -m 1 {マージコミットのhash}

# done化後に問題が発覚した場合
# /rollback KLK-010   （done → implementation_done）
```

**緊急時の即時回避:** hook 自体が誤denyでループを止める事態になった場合は、`.claude/settings.json` の `hooks.PreToolUse` から Bash マッチャのエントリを一時的に外す（README「注意」の既定手順）。その間チケット・SPEC.md への Bash 書き込みは Stop hook のドリフト検知のみが防衛線になるため、暫定措置に留め人間へ報告する。
