## 3. 設計方針

### 3-0. 人間の判断（委譲済み）Unknownsへの対応方針

investigatorが報告したUnknowns 4件は、委譲元の指示に従い次のように扱う。

| # | Unknown | 扱い |
|---|---|---|
| 1 | stream-json下のヘッドレス挙動がtext出力下の既存実測（KLK-001 V-1〜V-4）と同一か未検証 | **安全側構成＋検証タスク化**（VS-1、4節）。境界判定はstdout内容に一切依存しない既存設計のままであり、挙動が異なっていても境界判定4（未完了）等の既存の受け皿がそのまま機能する |
| 2 | `--forward-subagent-text`の実イベント列は未実測（Task単発実験からの類推のみ） | **安全側構成＋検証タスク化**（VS-2、4節）。レンダラー（`render_event`）は未知の`type`を例外なく無視する防御的パースとして設計し、実測結果は表示品質の校正にのみ使う（境界判定・合否には影響しない） |
| 3 | 旧方式＋worktree分離の組み合わせの実運用実績ゼロ | **構造的整合性の論証＋パイロット運用の注意書き**（3-3節）。worktree生成/削除はチケット単位イベントに紐づきセッション形態に依存しないため検証タスク化はせず、初回実運用を人間監視下のパイロットと位置づけるドキュメント注記で対応する（KLK-001 V-4と同じ考え方） |
| 4 | 改善ループ判断テーブル「実装ループ継続＝新チケット作成」と旧方式テンプレート「既存チケットへの前進」の意味論のずれ | **設計判断による解消**（3-1節）。人間から明示的に委譲されたため、Open Question化せず本設計で確定する |

### 3-1. 改善ループ判断テーブルとバッチ事前承認の関係を明示的に切り分ける

investigatorの指摘どおり、orchestrator.md「改善ループ（人間の判断後）」テーブルの
「実装ループ継続 → 新チケットを作成してtodoから再開」は、**`/start-loop`の単発実行**
（1チケット完了ごとに人間が確認する場合）を前提にした記述であり、バッチ実行（外部駆動・
セッション内いずれも）が「事前に列挙された既存チケットへ前進する」運用とは字面上噛み合わない。
この緩さは旧方式の初出（2026-06-17）から存在し、KLK-007が新たに生んだ問題ではない。

**採用する方針**: このテーブル自体は変更・再定義しない（「1チケット単発実行時の人間判断」という
意味論のまま維持する）。その直下に、バッチ実行時はこのテーブルの「個別チケット完了時の判断」を
**バッチ開始時の事前承認が代行し**、テーブルの判断がそのまま適用されるのは**バッチ終了後**
（次のバッチを新たに組む＝新チケット作成を要する新規実装として着手するか、改善ループへ入るか）
であることを明記する注記を追加する。

- 「明示的に解消する」か「別メカニズムとして切り分けて明記する」かの二択に対しては、**両方を
  部分的に採用する**: テーブルの文言自体はいじらず(再定義しない)、バッチが「テーブルの適用範囲外の
  別メカニズム」であることを明記する注記を1箇所（orchestrator.md、テーブル直下）に追加する。
  これは「別メカニズムとして切り分けて明記する」に相当する
- 注記は外部駆動`/batch-loop`にも同様に当てはまる内容であるため、`/batch-loop-inline`固有の
  対応ではなく既存の`/batch-loop`の文書上の欠落も同時に埋める（本チケットのついでに解消してよい
  範囲と判断した。docs/batch-loop.mdの「旧→新セマンティクスの写像表」がすでに実質的にこの
  意味論で運用されており、注記はその運用を明文化するだけで新しい挙動を導入しない）
- CLAUDE.md本体・README.mdのASCII図（「実装ループ継続 (新チケット作成)」の表記）は変更しない
  （architect制約「不要な書き換えを避ける」。図はテーブルを単純化した人間向けの概観であり、
  挙動の正はorchestrator.mdのテーブル＋注記であるため、図まで書き換える必要性は薄いと判断した）

### 3-2. stream-json化: 境界判定はstdout内容に依存させない（安全側構成の核）

**採用する方針:**

1. **`build_claude_command()`に4フラグを無条件付加する**: `--output-format stream-json
   --verbose --include-partial-messages --forward-subagent-text`。`--verbose`はinvestigator
   実測どおり`-p`+`stream-json`の必須前提のため必ず一緒に渡す
2. **`run_session()`を「stdout継承+ブロッキング待機」から「stdout PIPE化+専用リーダースレッド+
   queueベースのタイムアウト管理」へ置き換える**。理由: `readline()`はブロッキング呼び出しのため、
   メインスレッドで直接読みながら`--timeout-min`のデッドラインも管理するには、別スレッドで
   継続的にPIPEを読み進めてqueueへ渡し、メインスレッドは`queue.get(timeout=残り時間)`で
   タイムアウトとイベント処理の両方を扱う設計にする（PIPEを読み切らずに放置するとOSパイプ
   バッファ詰まりで子プロセスがブロックしうるため、専用スレッドでの継続的排出は安全性のためにも必須）
3. **stdout解析結果（`render_event`の戻り値）は表示にのみ使い、`judge_boundary`等の合否判定へは
   一切渡さない**（既存設計を維持）。JSONデコード失敗・未知の`type`・レンダラー内部例外は
   いずれも「その行の表示をスキップする」だけに留め、バッチの続行を妨げない（フェイルセーフ。
   hooksのfail-open規約とは別だが、「表示は失敗してよいが合否判定はfail-closedのまま」という
   役割分離をここで導入する）
4. **`run_session()`の外部契約（引数・戻り値`(exit_status, elapsed_sec)`）は変更しない**。
   既存の`test_timeout_terminates_child_and_stops`・`test_sigint_terminates_child_and_exits_130`
   がそのまま通ることを実装の受け入れ基準に含める（investigator指摘の「既存の振る舞い契約は
   維持が必要」に対応）
5. **stderr は従来どおり継承のまま変更しない**（claudeのエラー出力はターミナルへ直接流れる。
   stdout解析対象外とすることでパーサの複雑化を避ける）

**代替案と却下理由:**
| 案 | 却下理由 |
|---|---|
| `selectors`でstdout/stderr両方を多重化して読む | stderrは継承のままで十分（エラーは直接ターミナルに出る）。多重化はWindowsでの`select`のパイプ非対応等、移植性の懸念を増やすだけで得るものがない（stdlibのみ制約下でqueue+threadの方が単純） |
| `communicate()`で一括取得してから事後表示 | 「リアルタイムに表示する」というAC1の要求に反する（応答完了まで何も表示されない現状の課題をそのまま残す） |
| stream-json解析結果を境界判定に組み込む（例: assistantのエラーテキストを検知して停止） | 境界判定の正をチケットファイル状態に一元化してきた既存設計（KLK-001）を壊す。文字列マッチングによる停止条件は誤検知・見逃しのリスクが高く、fail-closedの原則にも反する |
| 未知の`type`をエラーとして扱い停止する | Unknown #2（実イベント列未実測）の下で採用すると、実測と異なるだけでバッチが動かなくなる。表示専用の防御的パースの方が安全側 |

### 3-3. 旧方式の復旧: 「即停止」ではなく「境界停止」で復旧する（互換性検証の結論）

AC2は「単純な過去バージョンの復元ではなく、互換性検証を経ること」を明示的に要求している。
docs/batch-loop.mdの「旧→新セマンティクスの写像表」（investigatorが8c10f84時点の内容から
書き起こしたもの）によれば、旧方式は「差し戻し（tester/reviewer）で**即停止**」だった。

**互換性検証の結論**: この「即停止」を文字通り復元すると、KLK-001以降に明文化・hook強制された
「実装ループ内の差し戻しはエージェント間で完結し人間は介在しない」という不変条件（CLAUDE.md
開発ループフロー、orchestrator.md Priorities）と衝突する。旧方式導入（2026-06-17）はauto
モード既定化・hookによる状態機械強制の**前**であり、当時の「即停止」は実装ループの自律性が
今ほど厳格に定義されていなかった時代の設計と解釈できる。したがって**文字通りの復元は現行ポリシーと
非互換であり、そのままでは復旧できない**。

**採用する方針**: 旧方式の意図（「差し戻しが発生したバッチを人間の確認なしに進めない」）は維持しつつ、
実現方法を外部駆動版と同じ**境界停止**（チケットがdoneに到達した時点でretry_countsの増分を検査し、
増分があれば次のチケットへ進まず停止・再承認を求める）に統一する。セッション内実行はプロセス境界が
無いぶん外部駆動版より観測は容易だが、「実装ループの自律性を尊重する」という現行ポリシーを優先し、
あえて外部駆動版と同じ粒度（チケット境界）に揃える。これにより:
- 実装ループ内の自律的な差し戻し処理（tester→implementer、reviewer→implementer）はバッチ実行有無に
  関わらず不変（人間非介在の原則を保つ）
- 「差し戻し発生バッチを無人で進めない」という旧方式の意図は、チケット境界での停止として維持される
- 外部駆動版・セッション内版で境界判定の考え方が統一され、二重規範にならない

**worktree分離ポリシーとの整合**: worktreeの作成（design_done→implementer委譲直前）・削除
（reviewer承認後）はチケット単位のイベントに紐づき、セッションが1チケットで終わるか複数チケットに
またがるかには依存しない。セッション内バッチはチケットを逐次処理する（並行しない）ため、ある時点で
アクティブなworktreeは常に高々1つであり、並行worktree上限3件（docs/worktree-policy.md）にも抵触
しない。対話セッションの`permissions.additionalDirectories`（`../{リポジトリ名}.wt/`）は
worktree-policy.mdで既に対話セッション向けに設定済みであり、追加の権限設定は不要。以上より
Unknown #3は構造的に整合すると判断し、検証タスク化はせず、初回実運用を人間監視下のパイロットと
位置づける注記のみをdocs/batch-loop-inline.mdに残す（KLK-001 V-4と同じ考え方の再利用）。

**KLK-002モデル割当との整合**: `model`frontmatterはサブエージェント起動（Task/Agentツール）の
たびに解決される割当であり、呼び出し元セッションが外部駆動ヘッドレスか対話セッションかに関係なく
同一に働く。セッション内バッチは`/start-loop`と同じ委譲ロジック（orchestrator.md Agent
Delegation Rules）をそのまま繰り返すだけなので、モデル割当について追加の調整は不要。

**採用する方針（コマンド構成）:**
1. 新コマンド`/batch-loop-inline`（`.claude/commands/batch-loop-inline.md`）を新設する。
   対話セッション内でorchestratorが直接、ID列検証→起動時チェックリスト（1回のみ）→事前承認
   テンプレートの提示→承認→チケット逐次処理、を行う。バッキングスクリプトは持たない
   （旧方式もPython化されたスクリプトは存在せず、コマンド定義だけで完結していたことと整合する。
   対話セッションでの人間対応はLLM自身が行うため、`scripts/batch_loop.py`のような機械的
   プリフライトスクリプトは不要）
2. `docs/batch-loop-inline.md`を新設し、セッション内バッチの詳細仕様・停止条件・使い分け指針・
   パイロット運用の注意を記載する（外部駆動版のdocs/batch-loop.mdと対をなす構成）
3. `docs/batch-loop.md`の末尾「## 旧方式（セッション内手動テンプレート）について」を、
   「`/batch-loop-inline`として復旧された」ことを示す短い案内へ差し替え、冒頭に外部駆動版と
   セッション内版の使い分け指針（比較表）を追加する
4. コマンド名は「`/batch-loop`＝既定・外部駆動」「`/batch-loop-inline`＝対話セッション内・旧方式」
   という対称性のある命名とする（`/batch-loop`という名称・意味論はKLK-001で確定済みであり
   変更しない。「別コマンドとして共存」という AC3 の要求を満たしつつ、既存コマンドの後方互換性
   を壊さない）

**代替案と却下理由:**
| 案 | 却下理由 |
|---|---|
| 旧方式の「即停止」をそのまま復元する | 「実装ループ内は人間非介在」という現行ポリシー（CLAUDE.md・orchestrator.md）と衝突する。AC2が求める「互換性検証」を経れば非互換と判定される |
| `/batch-loop`自体を拡張し、フラグで外部駆動/セッション内を切り替える | AC3が「別々のスラッシュコマンド」を明示的に要求している。1コマンドへの統合はACの再定義に当たる |
| セッション内バッチもPythonスクリプトで駆動する | 対話セッション内で`claude -p`をネスト起動することになり、既存の禁止事項（`.claude/commands/batch-loop.md` Never）と矛盾する。セッション内バッチの価値は「対話でAskUserQuestion等に人間が即応できること」であり、スクリプト駆動にする意味がない |
| 差し戻し検知を「チケット境界」ではなく「差し戻し発生の瞬間」で止める（旧方式によりの忠実な復元） | 実装ループの自律性原則と衝突する。仮に許容しても、implementer→tester→reviewerの自律ループを中断する実装が必要になり複雑度が増す割に、意図（無人でバッチを進めない）は境界停止でも同等に満たされる |

```python
def _brief(value, limit=200):
    """長い値を人間可読な範囲に切り詰める。"""
    text = value if isinstance(value, str) else repr(value)
    text = text.replace("\n", " ")
    return text if len(text) <= limit else text[:limit] + "…"


def render_event(evt):
    """stream-jsonの1行(dict)を人間可読な進捗表現へ変換する。
    戻り値: 通常行(str) / 継続出力用("TEXT", text)タプル / 表示不要(None)。
    未知のtype・構造は例外を出さずNoneを返す（防御的パース。境界判定はここに依存しない。
    実イベント列はUnknown#2のためVS-2で実測し、本関数はその結果で校正する）。"""
    etype = evt.get("type")

    if etype == "system":
        if evt.get("subtype") == "init":
            return "[session] 開始 (model=%s)" % evt.get("model", "?")
        return None

    if etype == "stream_event":
        delta = (evt.get("event") or {}).get("delta") or {}
        if delta.get("type") == "text_delta" and delta.get("text"):
            return ("TEXT", delta["text"])
        return None

    if etype in ("assistant", "user"):
        content = ((evt.get("message") or {}).get("content")) or []
        if not isinstance(content, list):
            return None
        lines = []
        for block in content:
            if not isinstance(block, dict):
                continue
            btype = block.get("type")
            if btype == "tool_use":
                lines.append("[tool] %s(%s)" % (
                    block.get("name", "?"), _brief(block.get("input", {}))))
            elif btype == "tool_result":
                lines.append("[result] %s" % _brief(block.get("content", "")))
        return "\n".join(lines) if lines else None

    if etype in ("task_started", "task_notification") or "parent_tool_use_id" in evt:
        text = evt.get("text") or evt.get("message") or ""
        label = evt.get("subagent_type") or evt.get("name") or "subagent"
        if text:
            return "[subagent:%s] %s" % (label, _brief(text))
        return "[subagent:%s] %s" % (label, etype)

    return None


def handle_stream_line(raw_line, state):
    """1行(str)をパースしてrender_eventへ渡し、必要なら表示する。
    JSONデコード失敗・レンダラー内部例外はいずれも無視して継続する。"""
    line = raw_line.strip()
    if not line:
        return
    try:
        evt = json.loads(line)
    except (ValueError, TypeError):
        return
    if not isinstance(evt, dict):
        return
    try:
        rendered = render_event(evt)
    except Exception:
        return
    if rendered is None:
        return
    if isinstance(rendered, tuple) and rendered[0] == "TEXT":
        sys.stdout.write(rendered[1])
        sys.stdout.flush()
        state["mid_line"] = True
        return
    if state.get("mid_line"):
        sys.stdout.write("\n")
        state["mid_line"] = False
    say(rendered)
```

**`run_session()`の置き換え（既存の引数・戻り値契約は不変）:**
```python
def _reader_thread(pipe, out_queue):
    try:
        for line in iter(pipe.readline, ""):
            out_queue.put(("line", line))
    finally:
        out_queue.put(("eof", None))


def run_session(cmd, root, timeout_min):
    """claude セッションを1つ実行し (exit_status, elapsed_sec) を返す。
    stdoutはパイプで受けてリアルタイムに進捗表示する（stderrは継承のまま）。
    exit_status はプロセス終了コード、タイムアウト時は文字列 "timeout"。"""
    start = time.monotonic()
    proc = subprocess.Popen(
        cmd, cwd=str(root), stdin=subprocess.DEVNULL,
        stdout=subprocess.PIPE, text=True, bufsize=1, errors="replace",
    )
    out_queue = queue.Queue()
    reader = threading.Thread(target=_reader_thread,
                              args=(proc.stdout, out_queue), daemon=True)
    reader.start()
    state = {"mid_line": False}
    deadline = start + timeout_min * 60 if timeout_min else None
    try:
        while True:
            if deadline is not None:
                remaining = deadline - time.monotonic()
                if remaining <= 0:
                    _terminate(proc)
                    return "timeout", time.monotonic() - start
            else:
                remaining = None
            try:
                kind, payload = out_queue.get(timeout=remaining)
            except queue.Empty:
                continue
            if kind == "eof":
                break
            handle_stream_line(payload, state)
        if state["mid_line"]:
            sys.stdout.write("\n")
            sys.stdout.flush()
        code = proc.wait()
    except KeyboardInterrupt:
        _terminate(proc)
        raise
    return code, time.monotonic() - start
```
- `queue.Queue.get(timeout=None)`は無期限ブロックする（`--timeout-min`未指定時は従来どおり
  無制限待機）。KeyboardInterrupt はブロッキング`get()`中でも配送されるため、SIGINT時の
  `_terminate`＋re-raiseという既存契約（`test_sigint_terminates_child_and_exits_130`）を
  変更なく満たす
- 専用スレッドが継続的にPIPEを排出するため、OSパイプバッファ詰まりによるデッドロックは発生しない
- `_terminate()`は既存実装のまま再利用する（変更不要）

`#!/usr/bin/env python3`は1行目に既存）。Gitは実行ビットを追跡するためコミットに含める

### 4-3. /batch-loop-inline コマンド仕様

**`.claude/commands/batch-loop-inline.md`（手順の骨子。確定文面は実装時にこの骨子から作成する）:**
1. `.claude/agents/orchestrator.md`を読み込み、orchestratorとして実行する。本コマンドは
   **対話セッション専用**（ヘッドレス実行は想定しない。ヘッドレス連続実行は`/batch-loop`を使う）
2. `$ARGUMENTS`からチケットID列を読み取る（記載順が実行順）。1件以下なら`/start-loop {ID}`を
   案内して終了する
3. ID列を検証する: 各IDが`tickets/active/{ID}_*.md`に一意存在し、statusが
   cancelled/blocked/doneでないこと（重複ID拒否）。違反があれば一覧提示して開始しない
4. `/start-loop`起動時チェックリスト（Autoモード確認・14日blockedトリアージ・in_progress上限・
   done/件数警告・残存worktree検出）を**バッチ開始前に1回だけ**実行する（1セッション内で
   状態は変わらない前提。チケットごとの再チェックはしない）
5. `docs/SPEC.md`が存在しない場合、SPEC免除が人間承認済みであることを人間に確認する
6. 事前承認テンプレート（下記）を人間へ提示し、明示的な承認を得る。**このテンプレートへの
   人間の承認が「バッチ連続実行の事前承認」の実体**（3-1節の注記が指す「代行」はこれを指す）
7. 承認後、対象チケットを先頭から順に処理する。各チケット開始前に`retry_counts`をスナップショット
8. 1チケットの処理は通常の実装ループ委譲ロジック（orchestrator.md Agent Delegation Rules）に
   そのまま従う。対話セッションのためAskUserQuestion等はそのまま人間に確認してよい
   （`/batch-loop`のヘッドレス制約は適用されない — これが対話セッション内実行を選ぶ理由の一つ）
9. チケットが`done`または`blocked`になるたびに次の判定を行う:
   - `blocked` → 停止して報告し、人間の指示を待つ
   - `done`かつ`retry_counts`増分あり → 要約報告して停止し、続行の再承認を求める
   - `done`かつ増分なしかつ残りチケットあり → 要約報告して次のチケットへ進む
   - `done`かつ残りチケットなし（最終チケット）→ 要約報告して停止し、通常の改善ループ判断
     （実装ループ継続/設計見直し/調査やり直し）を人間に確認する
10. チケットのstatus更新・ログ追記・done/への移動は通常どおりorchestratorが行う
    （本コマンド固有の書き込みルールはない。単一ライター原則・worktreeライフサイクル管理は
    orchestrator.md・docs/worktree-policy.mdのまま）

**事前承認テンプレート（`docs/batch-loop-inline.md`に正を置き、コマンド定義から参照する）:**
```
【バッチ連続実行の事前承認（セッション内・/batch-loop-inline）】
対象チケット（実行順）: {ID-1} {ID-2} ...

このセッション内で、各チケットに対して通常の実装ループ（investigator→architect→
implementer→tester→reviewer）を自律的に実行します。

前進の扱い:
- チケットがdoneに到達し、かつそのチケットの処理中にretry_countsの増分が
  一切なかった場合 → 完了を要約報告し、人間の確認を待たずに次のチケットへ進みます
- チケットの処理中にretry_countsが増分した場合（差し戻しが発生した場合）→
  そのチケットがdoneに到達しても次のチケットへは進まず、要約を報告して停止します
  （改めて人間の確認・再承認を待ちます）
- チケットがblockedになった場合（リトライ上限超過を含む）→ 直ちに停止し、
  ブロッカー内容を報告します
- 最終チケットの処理が終わったら、結果によらず必ず停止し、通常の改善ループ判断
  （実装ループ継続/設計見直し/調査やり直し）を人間に確認します

この事前承認は、チケット間の前進判断（本来は改善ループ判断テーブルが扱う）をバッチ内に
限り代行するものであり、実装ループ内の自律的な差し戻し処理そのものは変更しません
（人間非介在の原則は維持されます）。

実行してよろしいですか？
```

**Never（`.claude/commands/batch-loop-inline.md`に記載）:**
- ヘッドレス実行を想定しない（ask hook等ヘッドレス固有の配慮は不要。ヘッドレス連続実行が
  必要な場合は`/batch-loop`（外部駆動）を使う）
- 事前承認（手順6）を得ずにチケット間を自動前進しない
- `retry_counts`増分を検知したにもかかわらず人間の再承認なしに次のチケットへ進まない
- 大量件数・長時間の無人実行を目的として使わない（トークン累積のトレードオフを人間へ明示せずに
  実行しない）。多数件・無人実行が目的の場合は`/batch-loop`を案内する

### 4-4. 使い分け指針（比較表。docs/batch-loop.md冒頭と docs/batch-loop-inline.md双方に掲載）

| 判断基準 | `/batch-loop`（外部駆動） | `/batch-loop-inline`（セッション内・旧方式復旧） |
|---|---|---|
| バッチ件数 | 制限なし。多数件でも安全（セッション使い捨てでトークン累積なし） | 少数（目安2〜3件）を推奨。件数が増えるほど同一セッションにレポートが蓄積しコスト増 |
| トークン累積 | なし（チケットごとに新規セッション） | あり（セッション内に全チケットのサブエージェントレポートが蓄積） |
| 人間監視の要否 | 不要（無人実行可能。ヘッドレスでは`ask`は自動deny、応答不能な場面はチケットをblocked化して停止） | 必要（対話セッションが前提）。AskUserQuestion等の人間判断が必要になりそうなチケットに強い |
| 実行環境 | ターミナルでのPythonスクリプト実行が必要 | Claude Codeの対話セッション内で完結（追加のターミナル操作不要） |
| 進捗の可視性 | ターミナル標準出力でリアルタイム表示（本チケットでstream-json化） | セッションの通常の応答としてリアルタイムに見える |
| 差し戻し発生時の挙動 | チケット完了時に停止・報告。`--continue-on-rework`で緩和可 | チケット完了時に停止・報告し、再承認を待つ（対話でその場に確認できる） |
| 推奨用途 | 既定。多数件・長時間・無人実行したい場合 | 少数件をその場で見守りながら進めたい場合、対話的判断が挟まりそうな場合 |

## 6. リスク

| リスク | 深刻度 | 軽減策 |

## 7. マイグレーション戦略

- 追加中心の変更であり、データ・チケット・hookの移行はなし
- `scripts/batch_loop.py`の**出力形式**が「claudeの生text出力そのままの継承表示」から
  「パース済みの進捗行表示」へ変わる（非破壊的だが視覚的には変わる）。これは本チケットの
  目的そのもの（AC1）であり、CHANGELOGのChangedに明記する
- `/batch-loop`のCLI引数・終了コード・境界判定は無変更（後方互換）。既存の運用手順
  （`python3 scripts/batch_loop.py {ID...}`）はそのまま使える
- `/batch-loop-inline`は新規コマンドであり、既存の`/batch-loop`・`/start-loop`・
  `/improvement-loop`の挙動を変更しない（旧方式の復旧は加算のみ）
- `scripts/batch_loop.py`への実行権限付与はGitが実行ビットを追跡するため、コミット後は
  clone/pull した全環境に伝播する。`python3 scripts/batch_loop.py`表記は後方互換のまま維持する
- 実装はfeatureブランチ（worktree）で行い、設計書`docs/designs/KLK-007.md`はimplementerが
  featureブランチへ持ち込んでコミットする

## 8. ロールバック戦略

各Phaseはコミット単位で独立してrevert可能。スクリプト・コマンド定義・ドキュメントのみの変更で
状態を持たないため、revertのみで完結する。

```bash
# Phase単位でコミットする想定。問題発生時は該当Phaseのコミットを逆順にrevertする
git revert {Phase3コミット} {Phase2コミット} {Phase1コミット}

# stream-json化のみを切り戻したい場合（旧方式復旧は残す）
git revert {Phase1コミット}   # build_claude_command/run_session を戻す

# /batch-loop-inline のみを切り戻したい場合（stream-json化は残す）
git revert {Phase3コミット}   # 新規ファイル・CLAUDE.md表・orchestrator.md注記を戻す
```
旧`scripts/batch_loop.py`（stream-json化前）・削除前のドキュメントはGitヒストリから復元可能。
hooks・チケット状態機械に変更がないため、ロールバックの副作用はない。
