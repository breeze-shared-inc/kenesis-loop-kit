# [KLK-004] サブエージェントレポートの要約上限と詳細外部化 設計

> このファイルはarchitectが生成・更新するチケット単位の設計書です。
> チケット KLK-004 に対応します。implementer・tester・reviewerが参照します。

## 1. 目的

本チケットはKit自身の内部改善であり `docs/SPEC.md` は不使用（先行チケットKLK-001投稿時に人間承認済み）。要件の正はチケットKLK-004の受け入れ条件（AC1〜AC5、下記§9に転記）である。

サブエージェントのレポートは (a) orchestratorのメインスレッドにその場で積まれ、(b) さらにチケットログ・実装メモへ永続化されて以後の全ループ（`tickets/active/`の再読・`/metrics`・`/triage`等）で再読される、という二重のトークン消費構造を持つ。本設計は、各エージェントのRequired Output Formatに「各項目は要点5行以内・超過分は外部ファイルへ書き出しポインタのみ残す」規約を一律導入し、詳細ファイルの置き場を `docs/reports/{ID}/{phase}.md` に確定する。既にこのパターンを実践しているarchitect（`docs/designs/{ID}.md`）を雛形とし、Write/Editツールの有無に応じて「自筆」と「orchestrator代筆」を使い分けることで、investigator/reviewerの「読み取り専用」という既存の安全特性を変えずに(b)の再読コストを解消する。

## 2. 現状

**現在のフロー:**
```
1. サブエージェント（investigator/implementer/tester/reviewer）が調査・実装・テスト・レビューの
   全文レポートを返答として生成する
2. orchestratorがその全文をメインスレッドのコンテキストに受け取る（消費その1）
3. orchestratorが全文（またはその大部分）をチケットの実装メモ・ログへ追記する
4. 以後、当該チケットが再度処理される（差し戻し・改善ループ・トリアージ等）たびに、
   orchestratorや各種ツール（/metrics・/triage・check_loop_integrity.py等）が
   tickets/active|done/*.md を読み直し、蓄積された全文を毎回再読する（消費その2、恒常的）
```
唯一の例外がarchitectで、既に`docs/designs/{ID}.md`へ設計全文を外部化し、チケットには数行の要約＋ポインタのみを残す運用が確立済み（KLK-001: 35,977B、KLK-002: 23,451B、KLK-003: 29,663B。いずれもチケット本体56〜106行よりずっと大きい）。この運用を残り5エージェント（investigator/implementer/tester/reviewer/orchestrator）へ拡張することが本チケットの主題である。

**関連する既存ファイル:**
- `.claude/agents/{orchestrator,investigator,architect,implementer,tester,reviewer}.md` — 6ファイルともRequired Output Formatに行数上限・外部化規約が無い
- `docs/designs/README.md` — 「1チケット=1設計ファイル、改訂は上書き、過去版はGit履歴」という、本設計がそのまま踏襲する既存パターンの正
- `docs/worktree-policy.md` — 作業場所の境界表（メインツリー: orchestrator/investigator/architect、チケット専用worktree: implementer/tester/reviewer）
- `.claude/hooks/_ticket_lib.py`（`is_ticket()` 97-107行目）— `tickets/active|done/*.md` のみを実チケット扱いする。`docs/reports/{ID}/` はこの判定に一切含まれない（investigator確認済み）
- `.claude/hooks/validate_ticket_state.py` / `record_metrics.py` / `check_loop_integrity.py` / `guard_bash_writes.py` / `guard_spec_writes.py` — いずれも`docs/reports/`をパス判定条件に含まない
- `CLAUDE.md`（ドキュメント管理ルール表・ポリシー管理表）
- `tickets/Templates/ticket.md` / `ticket-bug.md` — `### 調査メモ (investigator)` / `### 設計メモ (architect)` / `### レビューメモ (reviewer)` の見出しはあるが、implementer・tester専用の見出しが無い

## 3. 設計方針

**採用する方針:**

1. **行数上限N=5を全6ファイル・Required Output Formatの各項目に一律適用する。** 役割ごとに数値を変えない。architectのPriority筆頭「システムの一貫性」を優先し、エージェントが役割ごとに異なる上限を覚える認知負荷を避ける。5行は「要点を箇条書きで示すが精査は詳細ファイルに委ねる」という規約の趣旨を満たす実務的な値であり、既存のarchitect設計サマリ運用（本タスクの依頼文でも「5〜8行程度」と指定されている）と同程度の規模感である。固定値ではなく、上限超過が恒常的でエージェントが要点の圧縮に恒常的に苦慮する運用実績が蓄積した場合は見直す。

2. **detail fileの書き手は既存のツール権限からそのまま導出する（新規のツール権限付与は行わない）。** Write/Editツールを既に持つエージェント（architect・implementer・tester）は各自が詳細ファイルを自ら作成・上書きする（architectは新規ファイルを作らず既存の`docs/designs/{ID}.md`をそのまま使う）。Write/Editツールを持たないエージェント（investigator・reviewer）については、orchestratorが受け取った全文レポートを`docs/reports/{ID}/{phase}.md`へ書き出し、チケットには要点＋ポインタのみを追記する。settings.jsonの`Edit(docs/**)`許可は既に存在するため追加設定は不要。

3. **detail fileの置き場は `docs/reports/{ID}/{phase}.md`（ロール単位で1ファイル）とし、Gitで追跡する（.gitignore対象にしない）。** phase名は `investigation`（investigator）・`implementation`（implementer、上限超過時のみ作成）・`test-report`（tester、上限超過時のみ作成）・`review`（reviewer、orchestratorが代筆）の4種。architectは対象外（既存の`docs/designs/{ID}.md`を継続使用）。Gitで追跡する理由: `docs/designs/{ID}.md`・`docs/wireframes/*.html`という「実体あるドキュメントは公開/非公開設定によらず追跡する」既存precedentに合わせるため。ループメトリクス（`tickets/.metrics*`）のような環境固有の生成物とは性質が異なり、意思決定の根拠を残す実質的なプロジェクト文書である。機密情報の記載禁止は既存の`docs/security-policy.md`がそのまま適用される。

4. **同一チケット・同一phaseのレポートは同一ファイルを上書きする。** 差し戻しで同じロールが再実行された場合（例: reviewer→investigator差し戻し後の再調査）、`docs/reports/{ID}/investigation.md`を上書きし、チケットログに「{phase}を再実施 - 理由」の1行を追記する。`docs/designs/{ID}.md`の改訂運用（「設計を改訂 - 理由」）と完全に同型であり、新しい概念を持ち込まない。

5. **tester/reviewerのdetail file配置は`docs/worktree-policy.md`の作業場所境界にそのまま従う。** testerは既存のGit Rulesどおりチケット専用worktree内で`docs/reports/{ID}/test-report.md`を作成・コミットする（実装コード・テストファイルと同じ扱い）。reviewerはWrite/Editツールを持たないため、orchestratorがメインworktree（既存の「チケット・メトリクスの書き込みはメインworktreeのみ」原則が適用される場）で`docs/reports/{ID}/review.md`を作成する。これによりreviewerの承認/差し戻しいずれの結果でもマージのタイミングに依存せず即座に参照可能になる。testerのレポートは、tester→reviewerの間は同一worktree内で参照できるが、他ツリーからはマージ完了まで見えない — これは実装コード自体も同じ制約を持つ既存のworktreeモデルの帰結であり、新たな非対称を生まない。

6. **detail fileにはYAML frontmatterを付けない。** 先頭は`# {ID} {phase}`の見出しと「生成: {ロール} / 最終更新: {日付}」の1行に留める。チケットのfrontmatter（`status`・`retry_counts`等、hookが検証する）と視覚的に混同されるのを避けるための意図的な選択。

7. **orchestrator自身のRequired Output Format・リトライ上限エスカレーション報告も同cap対象とするが、エスカレーション報告（リトライカウンタ管理節で規定される3項目）は例外として除外する。** エスカレーション内容はブロッカーセクションに一時的に記載され解消後に削除される前提であり、恒常的な再読コストが小さい一方、人間が1箇所で意思決定できることを優先する。

**代替案と却下理由:**

| 案 | 却下理由 |
|---|---|
| 役割ごとに異なる行数上限Nを設定する | 一貫性（Priority 1）を優先。エージェントが役割ごとに異なる数値を覚える必要が生じ、規約の実効性を下げる |
| investigator/reviewerにもWrite/Editツールを付与し自筆させる | 「読み取り専用」という明示された安全特性（description・Neverルール）を変更することになり、"Preserve public interfaces unless explicitly approved"に抵触する。orchestrator代筆でも将来ループの再読コスト（本チケットが解決すべき主要な消費）は同等に解消できるため、恩恵に対して安全特性を犠牲にするコストが見合わない |
| `docs/reports/`を`.gitignore`対象にする | detail fileの主目的（将来も参照可能な形で保存すること）と矛盾する。`docs/designs/`の既存precedentとも不整合になる |
| Required Output Format全体（複数項目通算）でN行上限にする | 項目ごとの箇条書き上限の方がエージェントにとって従いやすく、既存の見出し構造と自然に対応する |
| 1チケット1ファイルに全ロールの詳細を集約する（`docs/reports/{ID}.md`単一ファイル） | ロールごとの再実行タイミングが異なり（investigator/reviewerは通常1回、tester/implementerは複数Phase）、単一ファイルだと上書きのたびに他ロールの内容を消すリスクがある。ロール別分離ファイルの方が安全 |

**実装Phase:**

## 8. ロールバック戦略

全ての変更が追加的（新規ファイル・見出し追加・行追加）またはテキスト置換のみで、状態機械・hookロジックには一切触れない。問題発生時はコミット単位でrevertする。

```bash
# developへマージ済みの場合（orchestratorのworktreeライフサイクル管理の手順に従いマージされたコミット）
git revert <developへのマージコミットハッシュ>
```

Phase2（回帰テスト追加）のみを個別にrevertすると非衝突の証跡が失われるため、Phase1とセットでrevertすることを推奨する。
