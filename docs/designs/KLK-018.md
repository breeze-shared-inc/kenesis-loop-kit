# [KLK-018] シェル展開による保護対象パスの分断（ブレース展開・glob・パラメータ展開） 設計

> このファイルはarchitectが生成・更新するチケット単位の設計書です。
> チケット KLK-018 に対応します。implementer・tester・reviewerが参照します。

## 1. 目的

`.claude/hooks/guard_bash_writes.py` は `PATHISH_RE` が `{` `}` `,` `*` `?` `[` `]` を
含まないため、bash のブレース展開（`rm tickets/{active,done}/APP-001.md`）・分断 glob
（`rm tickets/acti*e/APP-001.md`）で初めて保護対象パスになる形を検出できない
（KLK-010 §3-9-2 SH-2 でスコープ外として `INVENTORY_CASES` の INV-SH-07・09 に
`allow` で登録済み）。本チケットはこの2次元を閉じる。パラメータ展開（引数側）は
原理的に PreToolUse では閉じられないため対象外とし、限界として明記したまま
維持する（本チケットに SPEC.md 上の REQ/SCR/IF は無い。要件の正はチケット
KLK-018 の受け入れ条件）。

## 2. 現状

**現在のフロー（`statement_violation` の言及ゲート）:**
```
lex() → 語（word）の並び → expand_all（$(...) 等のプレースホルダのみ解決）
  → mentions_guarded(expanded_words)  ※各語を is_guarded_token で判定
    → guarded_paths(word)  ※PATHISH_RE.findall → _is_guarded_path
      → PATHISH_RE = [A-Za-z0-9_.\-/]+ が { } , * ? [ ] を含まないため、
        "tickets/{active,done}/APP-001.md" は "tickets/" / "active" / "done" /
        "/APP-001.md" のような断片に割れ、どの断片も _is_guarded_path を
        満たさない → gate_hit=False → 非ホワイトリスト head（rm 等）でも allow
```

（sort -o／uniq第2引数／リダイレクト先の cwd 結合前判定）・degraded mode

## 3. 設計方針

**採用する方針:**

既存の `PATHISH_RE`／`guarded_paths`／`_is_guarded_path`／`is_guarded_token`／
`mentions_guarded` は**一切変更しない**。KLK-029（sed/awk プログラム本文ゲート
緩和）と同型の「専用の展開後判定関数を新設し、呼び出し箇所で OR 追加する」
方式を採る。これは investigator が Dependency Graph で提案した設計であり、
13箇所超の共有シンボルを直接改変した場合の全呼び出し経路への波及
（言及ゲート・リダイレクト先・変数代入値・sed/awk プログラム本文のすべてが
一度に変わり、影響範囲の切り分けが困難になる）を避けるための選択である。

新設する関数群（すべて `.claude/hooks/guard_bash_writes.py` へ追加）:

1. **`expand_braces(text)`** — bash のブレース展開を模した文字列展開。
   入れ子・直積（隣接する複数の `{...}`）に対応する。カンマを含まない
   `{word}` は bash も展開しないためリテラルのまま残す。
2. **`guarded_paths_after_shell_expansion(text)`** — ブレース展開後の各文字列に
   対し、①そのまま `_is_guarded_path` を満たすか、②満たさずかつ `*`／`?`／`[`
   が残る場合は「`/` 区切り成分ごとに `active`／`done`／`SPEC.md` のいずれかへ
   fnmatch し得るか」を判定し、し得るなら成分をその具体名へ置換して
   再評価する（分断 glob 対応）。
3. **`is_guarded_token_expanded(text)` / `mentions_guarded_expanded(values)`** —
   `is_guarded_token(text) or bool(guarded_paths_after_shell_expansion(text))`
   という OR 追加のみの関数（KLK-029 の `is_guarded_token_in_program` と同型の
   安全性主張）。

呼び出し箇所は、既存の `is_guarded_token`／`mentions_guarded` の呼び出しのうち
「bash 未展開の生語を判定している7箇所」を `_expanded` 版へ**置き換える**
（新しい呼び出しを追加するのではなく、既存呼び出しの対象を差し替えるだけ。
周辺の条件分岐・cwd結合ロジック・戻り値の扱いは一切変更しない）。詳細は
§4-2「呼び出し箇所の変更」を正とする。

**採用しない拡張（意図的にスコープ外とする）:**
- bash の**シーケンス形**ブレース展開（`{1..3}`・`{a..z}`）。数値・文字範囲の
  意味論（step・ゼロ埋め・逆順）の実装コストが本チケットの規模に見合わず、
  investigator の実機再現・チケットの再現手順もカンマ区切り形のみである。
  `INVENTORY_CASES` へ allow 固定ケースとして明示登録し、README／docstring の
  「既知の限界」へ追記する（§6 リスク参照）。
- 実際のファイルシステムに対する `glob.glob()` 実行（§3 代替案参照）。

**代替案と却下理由:**

| 案 | 却下理由 |
|---|---|
| `PATHISH_RE` 自体に `{},*?[]` を追加する（単純拡張） | KLK-010 §3-7 が却下した案。investigator調査で、この却下理由として引用される具体例 `_is_guarded_path("tickets/active/NR>1 {print}")` を机上で追跡した結果、これは **cwd を全語へ join する却下済み案（H2）**によってのみ再現する現象であり（`guarded_write_target` の cwd 結合分岐＝`_is_guarded_path(os.path.normpath(os.path.join(cwd, target)))`。この分岐は「構文的に書き込み先と確定したオペランド」にのみ適用され、awk のプログラム本文には到達しない）、**PATHISH_RE を widen しただけでは（cwd 結合を伴わない限り）再現しない**ことを確認した（§6 リスクに机上検証の詳細）。とはいえ `PATHISH_RE` は13箇所超から共有される最も基盤的なシンボルであり、変更した場合の影響範囲の切り分けコストが高い。専用関数の新設＋OR追加（KLK-029 と同型）の方が安全側かつ監査しやすいため、こちらを採る |
| 実ファイルシステムに対する `glob.glob()` 実行で分断 glob を判定する | **却下。** bash が実際に生成する argv と最も正確に一致する利点はあるが、(1) hook の判定がその瞬間の実ファイル配置に依存し非決定的になる（`tests/` の `INVENTORY_CASES` は純粋な文字列入力→期待値の対応表であり、実ファイルを用意しないと再現できないテストになる＝既存のテスト資産と非対称） (2) `cwd` の追跡が `next_cwd` のヒューリスティック（`cd $VAR` 等で追跡打ち切り）に依存しており、誤った cwd から `glob.glob()` すると誤判定の温床になる (3) 本 hook の既存設計原則（`_is_guarded_path` 等はすべて純粋な文字列操作で `os.path.exists` の類を一切使わない）から逸脱する。文字列ベースの保守的ヒューリスティック（fnmatch による「一致し得るか」判定）の方が既存文化と整合し、決定的でテスト容易性も保たれる |
| `record_assignments` の `is_guarded_token(value)` も `_expanded` 版へ置き換える | **却下（保護上の実益が無い）。** bash は変数の**値**に対してブレース展開を再適用しない（`f=tickets/{active,done}/X.md` の代入自体はブレース展開されず、`$f` はリテラル文字列 `tickets/{active,done}/X.md` のまま1語になる。実在しないファイル名を指すため書き込みとして成立しない）。変更しても防御が増えず、変更範囲を広げるだけになるため対象外とする |
| `mentions_guarded_in_program`／`guarded_paths_in_program`（KLK-029）へブレース/glob対応を統合する | **却下。** sed/awk 自身のプログラム構文（`{}`・`,`・`[]` を伴うアクションブロック・フィールド区切り等）と bash レベルのブレース/glob 展開は別レイヤであり、統合すると `awk '{print $1,$2}'` のような日常のプログラム本文が誤って展開・照合対象になるリスクが生じる。呼び出し元（`statement_violation` の `has_program_head` 分岐）で `mentions_guarded_in_program` と `mentions_guarded_expanded` を**別個に OR** で足すことで責務を分離したまま両方の言及を検出する |

## 4. 実装詳細

### 4-1. 新設するシンボル（`.claude/hooks/guard_bash_writes.py`）

**定数（`PATHISH_RE` の定義の直後に追加。命名は既存の `MAX_SUBST_DEPTH`・
KLK-029 の `_in_program` 系サフィックスに合わせる）:**

```python
# --- KLK-018: bash のブレース展開・分断 glob を考慮した言及判定 -------------
SHELL_EXPAND_PATHISH_RE = re.compile(r"[A-Za-z0-9_.\-/{},*?\[\]]+")
MAX_BRACE_DEPTH = 4          # MAX_SUBST_DEPTH(=3)に倣うネスト深さの上限
MAX_BRACE_COMBINATIONS = 512  # 直積展開の総数の上限（コスト爆発の防止）
MAX_BRACE_CHAR_COUNT = 50    # 隣接（非入れ子）ブレース群の個数に対する軽量な
                             # 事前上限（差し戻し対応で追加。詳細は本節末尾の
                             # 「RecursionError 安全性」を参照）
GUARDED_DIR_NAMES = ("active", "done")   # tickets/active・tickets/done の成分名
GUARDED_FILENAME = "SPEC.md"
GLOB_META_CHARS = frozenset("*?[")
```

**`expand_braces(text)`:**
- 入力の**最左**の `{` を見つけ、深さを数えながら対応する `}` を探す
  （`_skip_balanced` と同じ「ネストを数える」考え方を流用してよい。ただし
  クォート/バッククォートは意識不要——ここでの入力は bash が既にクォート解除
  した後の1語であるため）。
- 対応する `}` が見つからない（未閉じ）場合は bash も構文エラーになる形
  なので、展開せず `[text]` を返す。
- 見つかった場合、中身（body）を**トップレベルのカンマ**（ネストした `{}`
  の内側のカンマでは分割しない）で分割する。
  - 分割結果が2個未満（カンマ無し）なら bash はこの `{}` を展開しない。
    ただし body 自身に別の `{}` が含まれる可能性があるため、
    `prefix + "{" + b + "}" + s`（`b` は `expand_braces(body, depth+1)`、
    `s` は `expand_braces(suffix, depth+1)` の直積）という形でリテラルの
    `{`/`}` を残しつつ内側・後続だけ再帰展開する。
  - 分割結果が2個以上なら、各 part を再帰的に展開し、かつ suffix
    （`}` の次以降。隣接する別の `{...}` を含みうる＝直積のケース）も
    再帰的に展開して、`prefix + 各part展開 + 各suffix展開` の全組み合わせを
    返す（ネスト＝part の再帰展開／直積＝suffix の再帰展開、の両方を
    1つの再帰でカバーする）。
- **上限:** 深さが `MAX_BRACE_DEPTH` を超える、または直積の組み合わせ数が
  事前見積もりで `MAX_BRACE_COMBINATIONS` を超えると判明した場合は、
  full展開を行わず**その候補全体を「保護対象に一致し得る」ものとして
  扱う**（P8: 曖昧な位置では除去しない＝安全側。実装は組み合わせ数の
  事前見積もり関数を用意し、`expand_braces` 呼び出し前にガードするのが
  素直——`_brace_combination_count(text)` のような軽量ヘルパを新設してよい）。
  このフォールバックの結果、呼び出し元（`guarded_paths_after_shell_expansion`）
  は当該候補を無条件に「保護対象パスの候補」として扱い、以降の
  `_is_guarded_path` 判定を経由せず直接一致とみなしてよい。

**`guarded_paths_after_shell_expansion(text)`:**
```
1. SHELL_EXPAND_PATHISH_RE.findall(text) で候補（ブレース・globメタ文字を
   含みうる）を抽出する。
2. 各候補について expand_braces(candidate) を行い、展開結果それぞれに対し:
   a. os.path.normpath 後に _is_guarded_path を満たせば採用する。
   b. 満たさず、"/" 区切り成分のいずれかに GLOB_META_CHARS の文字が
      含まれる場合、その成分について fnmatch.fnmatchcase(literal, component)
      を GUARDED_DIR_NAMES の各要素（"active"/"done"）に対して試す。加えて
      その成分が候補の**最後の**区切り成分であれば GUARDED_FILENAME
      ("SPEC.md") に対しても試す。一致する literal が見つかったら、その
      成分だけを literal へ置換した文字列を再構成し、os.path.normpath 後に
      _is_guarded_path を満たすか再評価する（置換は情報を追加する操作であり
      既存の文字は変更しない＝置換前に一致しなかった判定が置換後に不一致へ
      戻ることはない）。
   c. 成分が複数 GLOB_META_CHARS を含む場合はそれぞれ独立に試し、一致した
      ものを採用する（1候補から複数の一致が見つかることもある）。
3. 見つかった保護対象パスをリストで返す（guarded_paths と同型の戻り値）。
```
安全性主張（KLK-029 の P8 型記法に合わせる）:
- **主張:** `guarded_paths_after_shell_expansion` が非空を返すのは、
  「ブレース展開後に文字通り保護対象パスになる」または「残存する glob
  メタ文字を含む区切り成分が `active`／`done`／`SPEC.md` のいずれかに
  fnmatch し得て、かつ置換後の文字列が `_is_guarded_path` を満たす」場合
  に限る。いずれも「`tickets/` という文字列が候補中に既に存在する」か
  「候補の basename 相当が `SPEC` と `.md` に一致する構造を持つ」ことを
  必要とするため、`tickets/` を一切含まない語（`awk` プログラム本文の
  `{print $1,$2}`・`cut -f1,2 -d,` 等）が誤って一致することは無い
  （§6 リスクに机上検証のトレースを列挙）。
- **破れる形（否定形）:** 本関数の呼び出し箇所を「素の `is_guarded_token`
  を置き換える」形で使った場合（OR ではなく置換にした場合）。
- **向き:** 誤りの向きは常に allow 方向（危険）。
- **検出器:** `tests/test_guard_bash_writes.py` の新規 `INV-SH-22` 以降
  （§4-3）と、誤deny予算の固定 allow ケース群（§9）。

**RecursionError 安全性（改訂: 差し戻し対応で追加。reviewer Critical Issue由来）:**
`_brace_combination_count`／`expand_braces` は入れ子（body）方向の再帰でのみ
`depth` を進め、直積・隣接（suffix）方向の再帰では進めない。そのため非入れ子で
隣接するブレース群が大量に連続する入力（例: `"a" + "{x,y}" * 2000 + "b"`）は
`MAX_BRACE_DEPTH` の早期リターンに到達せず、隣接数に比例して Python
コールスタックを消費し続け `RecursionError` になりうる（実測: 隣接997個・
`sys.getrecursionlimit()=1000`）。これを `guard_bash_writes.py` 内で捕捉しない
場合、`main()` の広域 `except Exception: allow()` により**deny方向ではなく
allow方向へフェイルオープン**する（P8原則違反。既存の明確な deny 対象さえ
同一コマンド中の大量隣接ブレースだけで丸ごと allow になりうる）。この欠陥は
reviewerの1回目の差し戻し（Critical Issue）で検出され、
`guarded_paths_after_shell_expansion` へ以下の2段防御を追加して修正した:
1. 候補中の `{` 出現数が `MAX_BRACE_CHAR_COUNT`（本節冒頭の定数）を超える
   場合、`_brace_combination_count`／`expand_braces` を一切呼ばず安全側
   フォールバック（候補全体を無条件に「保護対象パスの候補」とみなす）へ倒す
   （定数時間の事前チェック）。
2. ①をすり抜けた場合の防御第2層として、`_brace_combination_count`／
   `expand_braces` の呼び出しを個別に `try/except RecursionError` で囲み、
   例外発生時も同じ安全側フォールバックへ倒す。
いずれも `MAX_BRACE_COMBINATIONS` 超過時の既存フォールバックと同じ deny
方向の分岐へ合流するため新しい判定パスは増えない。**この安全側フォールバックは
`tickets/` 等の保護対象語を一切含まない候補にも作用しうる新しい deny 経路であり、
§9 AC4 の N1〜N4 閉列挙の文言を字面上満たさない。reviewerの判断（誤りの向きが
常にdeny=安全側であり非ブロッカー）に基づき、§9 AC4 へ N5 として明文化した**
（詳細は §9・`docs/reports/KLK-018/implementation.md` §7・
`docs/reports/KLK-018/review.md` を参照。実装の正は
`.claude/hooks/guard_bash_writes.py` の `guarded_paths_after_shell_expansion`）。

**`is_guarded_token_expanded(text)` / `mentions_guarded_expanded(values)`:**
```python
def is_guarded_token_expanded(text):
    return bool(is_guarded_token(text) or guarded_paths_after_shell_expansion(text))

def mentions_guarded_expanded(values):
    return any(is_guarded_token_expanded(v) for v in values)
```

### 4-2. 呼び出し箇所の変更（7箇所。すべて既存呼び出しの対象を置き換えるだけ）

いずれも「関数名を `is_guarded_token`/`mentions_guarded` → `is_guarded_token_expanded`/
`mentions_guarded_expanded` へ差し替える」1行変更であり、周辺の条件分岐・
cwd結合・戻り値の扱いは変更しない。implementer は Edit 前に該当行を
`grep -n` で確認し、引用文字列が一意であることを確認すること。

1. **`statement_violation`**（言及ゲート。has_program_head の両分岐）:
   ```python
   if has_program_head:
       gate_hit = (cwd_is_guarded(cwd) or
                   mentions_guarded_in_program(expanded_words))
   else:
       gate_hit = cwd_is_guarded(cwd) or mentions_guarded(expanded_words)
   ```
   を
   ```python
   if has_program_head:
       gate_hit = (cwd_is_guarded(cwd) or
                   mentions_guarded_in_program(expanded_words) or
                   mentions_guarded_expanded(expanded_words))

       gate_hit = cwd_is_guarded(cwd) or mentions_guarded_expanded(expanded_words)
   ```
   へ変更する（`mentions_guarded_expanded` は `mentions_guarded` を内包する
   ため、素の `mentions_guarded` 呼び出しは残さず置き換える）。
2. **`redirect_violation`**: `is_guarded_token(resolved)` →
   `is_guarded_token_expanded(resolved)`（一意な引用: `if (is_guarded_token(resolved) or`）。
3. **`guarded_write_target`**: `if is_guarded_token(target):` →
   `if is_guarded_token_expanded(target):`（この関数の**cwd結合分岐
   （`_is_guarded_path(os.path.normpath(os.path.join(cwd, target)))`）は
   変更しない**——変更するのは cwd結合より前の、target 単体の判定のみ）。

   `if not (cwd_is_guarded(cwd) or mentions_guarded(skeleton.split())):` →
   `mentions_guarded_expanded(skeleton.split())` へ。
5. **`degraded_violation`**（リテラルリダイレクト判定）:
   `if is_guarded_token(target):`（`LEGACY_REDIRECT_RE` ループ内。一意な
   引用: `if is_guarded_token(target):\n            return "リダイレクト（> %s）による書き込み" % target`）

6. **`degraded_violation`**（ステートメント単位ゲート）:
   `if cwd_is_guarded(stmt_cwd) or any(mentions_guarded(w) for w in words_list):` →

7. **`subst_violation`**（深追い打ち切り時）:
   `if is_guarded_token(inner) or cwd_is_guarded(cwd):` →
   `is_guarded_token_expanded(inner)` へ。

**変更しない箇所（意図的な除外。§3 代替案に理由を記載済み）:** `record_assignments`
