# [KLK-030] sed_strip_literalsのパス末尾s疑似境界探索の設計見直し 設計

**受け入れ条件の番号付け:** チケット本文のチェックボックスを出現順に **AC1〜AC4** と呼ぶ。

| 本設計書 | 要旨 |
|---|---|
| AC1 | パス文字列中に`s`/`y`が含まれる場合でも意図しない境界探索を起こさない、または起こしても危険文字の検出漏れに至らないことをテストで積極的に立証する |
| AC2 | 既存テストが全て通過する（KLK-015のINV-SED-01〜31を含む回帰なし） |

## 1. 目的

`sed_strip_literals`（`.claude/hooks/guard_bash_writes.py`）は、トップレベル走査で生の文字`s`/`y`の出現位置を構文的位置に関わらず無条件にs/yコマンド開始とみなすため、保護対象パス文字列（`tickets`・`docs`等、末尾または途中に`s`を含む）由来の疑似境界探索が発生する（KLK-015 tester再検証時の参考所見）。investigatorが実施した実機GNU sed 4.9との二方向照合3,345件（checker ALLOW ∧ 実機危険動作の組は0件）を踏まえ、本設計は**方針b（現状のコードは変更せず、危険文字検出漏れが構造的に起こり得ない理由を明文化し、代表的な回帰テストとして固定化する）**を採用する。対応するチケット受け入れ条件はAC1〜AC4（本書冒頭表）。

## 2. 現状

**現在のフロー:**
```
segment_violation(words, cwd, degraded)  # head == "sed" 分岐
  └─ sed_program_texts(variant)              # プログラム本文候補を抽出
       └─ sed_program_violation(text)         # ホワイトリスト判定
            └─ sed_strip_literals(text)       # s/y・正規表現リテラルの除去
                 - トップレベルで生の "s"/"y" 文字が現れた**位置**を
                   無条件にコマンド開始とみなす（構文的にコマンドが
                   開始しうる位置かどうかは一切見ない）
                 - 開始とみなした位置から次の1文字をデリミタとし、
                   未エスケープの再出現を2回探して閉じればスパンを
                   丸ごと除去、閉じなければ None（判定不能→deny）
            └─ stripped 全体を SED_SAFE_PROGRAM_CHARS と比較
                 （順序非依存。安全文字集合に無い文字が1つでもあれば deny）
```

**問題の所在（investigator報告・現行コードで再現確認済み）:**
- パス文字列内の`s`（例:`tickets`の末尾）が疑似的にs/yコマンドの開始とみなされ、後続のデリミタ探索・スパン除去が発生する（例: `1w tickets/active/sub/APP-001.md` → `active`/`sub`部分が誤って除去される）。
- ただし、この現象で実際に検出漏れ（allow化）に至った具体例は、investigatorの5種のアドバーサリアル入力および追加調査（境界文字×デリミタ23種×危険文字12種×境界位置13カテゴリ・計3,345件の実機GNU sed 4.9二方向照合）のいずれでも構築できなかった（confidence: high）。

**関連する既存ファイル:**
- `.claude/hooks/guard_bash_writes.py`: `sed_strip_literals`（本体。トップレベル走査。`if ch in ("s", "y"):`分岐が疑似境界探索の起点）・`sed_program_violation`（`stripped`全体を`SED_SAFE_PROGRAM_CHARS`と比較。`SED_SAFE_PROGRAM_CHARS = SED_SAFE_COMMANDS | SED_SAFE_STRUCTURAL_CHARS`で定義。順序非依存の判定）・`sed_program_texts`（プログラム本文候補の抽出。本件と無関係）
- `tests/test_guard_bash_writes.py`: `INVENTORY_CASES`のINV-SED-01〜31（末尾は一意な引用文字列`対照: |区切りは元々検出済み・回帰確認`の行）。この直後（`# --- シェル展開の次元（§3-9-2。`で始まるコメント）が新規ケース追加の挿入点
- `docs/reports/KLK-030/investigation.md`: Findings・Evidence・追加調査（3,345件照合）の詳細
- `docs/designs/KLK-015.md`: `sed_strip_literals`のP8型安全性主張（不変条件・破れる形・向き・検出器）の書き方の参考

## 3. 設計方針

**採用する方針: 方針b（現状のコードは変更せず、安全性主張を設計書として明文化し、代表的な回帰テストとして固定化する）**

**採用理由（投資対効果）:**
1. 実害（検出漏れ＝allow化）の具体例は、5種のアドバーサリアル入力に加え、境界文字×デリミタ23種×危険文字12種×境界位置13カテゴリの体系的brute-force・実機GNU sed 4.9二方向照合（計3,345件）でも1件も見つからなかった（confidence: high）。
2. 方針a（構文的位置への厳密化）を採る場合、investigatorのRisk Areasが指摘するとおり、境界判定の状態を持つ簡易FSMの追加が必要になり、`sed_strip_literals`のトップレベル走査全体の書き直しに及ぶ。これは`SED_SAFE_STRUCTURAL_CHARS`との整合・a/i/c・b/t/T/:を意図的に安全集合外としているKLK-015の設計（P8: 除去しない＝安全側）全体の再検証を要し、既存INV-SED-01〜31全件の回帰影響が大きい。
3. 誤deny予算（AC3）の観点で、方針aは境界判定を変えることで「w/rコマンドのファイル名部分が偶発的に除去される」ことで**たまたま**安全側に倒れているケース（INV-SED-09〜20相当）の除去範囲が変わり、新たな誤allow/誤denyを生まないか個別確認が必要になる（investigation.md Risk Areas）。方針bはコードを変更しないため、この観点のリスクがそもそも発生しない。
4. 残存Unknown（後述スコープ外）はいずれも「本プロジェクトの前提（GNU sed・非POSIXモード・単一トリガー）から外れる、または実害の可能性がさらに低い」とinvestigatorが評価しており、対応コストに見合わない。

**代替案と却下理由:**
| 案 | 却下理由 |
|---|---|
| 方針a: `sed_strip_literals`のトップレベル走査を「コマンド区切り文字・アドレス直後等、構文的にコマンドが開始しうる位置でのみs/yコマンドとみなす」よう厳密化する簡易FSMを追加する | 実害の具体例が3,345件のbrute-force照合でも見つかっていない一方、影響範囲（FSM追加・既存INV-SED-01〜31全体の回帰・誤deny予算への影響）が大きく、投資対効果が見合わない。将来、実害の具体例が見つかった場合に別チケットとして再検討する |
| 対応不要と判断するが設計書・テストへの明文化は行わない（現状維持のみ） | AC4が根拠の明文化とテストでの固定化を明示的に要求しており、チケットの受け入れ条件を満たさない |

**安全性主張の明文化（P8型。KLK-015の`sed_strip_literals`docstringの書き方に倣う）:**

- **主張:** `sed_strip_literals`のトップレベル走査がパス文字列由来の`s`/`y`を疑似的なコマンド開始と誤認しても、`sed_program_violation`が最終的にdenyへ倒れることが構造的に保証される。理由は次の2点の複合: (1) `sed_program_violation`の判定は`stripped`全体に対する「安全文字集合に無い文字が1つでもあるか」であり**順序非依存**（疑似トリガーより前に危険文字があれば、疑似トリガーの誤動作に関わらず既にdenyが確定している）。(2) 疑似トリガーより**後**に危険文字がある場合でも、危険文字（`w`/`W`/`r`/`R`/`e`/`a`/`i`/`c`/`b`/`t`/`T`/`:`）自体は`SED_SAFE_COMMANDS`に含まれないただの1文字であり、疑似トリガーの誤ったデリミタ探索が「閉じない」場合は`None`（判定不能→deny）に倒れ、「閉じる」場合も除去されるのはデリミタに挟まれた区間のみで、危険文字が区間の外（デリミタ自身の位置・区間より後）にあれば`out`へそのまま残り安全文字判定に引っかかる。境界文字×デリミタ23種×危険文字12種×境界位置13カテゴリの体系的brute-force実機照合（3,345件）で、この構造的保証に反する組（checker ALLOW ∧ 実機危険動作）は0件だった。
- **破れる形（否定形）:** 疑似トリガーの誤ったデリミタ探索が「閉じる」形で成立し、かつその除去区間が実際の危険文字の生文字表現を**内包**してしまう入力（すなわち、危険文字が疑似トリガー由来の除去スパンの内側に位置し、除去後の`stripped`から消える入力）が存在すれば、この主張は破れる。
- **向き:** `sed_strip_literals`の誤りは常に「除去し過ぎない方向（under-removal）」に倒れる限り安全側（P8）である。3,345件の照合は、パス由来の疑似トリガーに起因する「除去し過ぎ（over-removal）が危険文字を巻き込む」経路が実在するかを直接検証する目的で設計されており、そのような経路は見つからなかった。
- **検出器:** `tests/test_guard_bash_writes.py`の新規`INV-SED-32`以降（本設計§4-2）。既存INV-SED-09〜21は危険文字が疑似トリガーより**前**にある順序（Finding 3のパターン）のみを偶発的にカバーしており、本設計で追加する新規ケースが危険文字を疑似トリガーの**後**に置く逆順（Finding 4が指摘した未検証の順序）を明示的に固定する。
- **スコープ外（残存Unknown。investigator追加調査より）:** 以下は3,345件の照合に含まれておらず、確定不能として明示的にスコープ外とする。① 境界文字トリガーを複数個・デリミタを変えながら連鎖させた入力 ② `[.` `[=` `[:` 特殊照合要素を含む大きなブラケット式と危険文字の組合せの網羅 ③ GNU sed 4.9以外の実装（BSD sed等） ④ マルチバイト・ロケール依存文字をデリミタ／パス文字として使う入力 ⑤ `sed --posix`・`-s`・`-z`等のフラグが文法を変える場合。①②はSED-7の既存bracket/escaping前提と同型の一般問題、③〜⑤は本プロジェクトの前提（GNU sed・非POSIXモード）から外れるため、実害が生じる可能性は本調査のカテゴリよりさらに低いとinvestigatorは評価している。将来これらの経路で実害の具体例が見つかった場合は別チケットとして再調査する。

### 4-1. `sed_strip_literals`単体の固定化テスト（AC1・AC4）

チケットの再現手順そのもの（`sed_strip_literals`はモジュールレベル関数であり直接importしてテスト可能）を、**戻り値の厳密一致**で固定化する。目的は「疑似境界探索という現象自体」を明示的に検出器へ乗せること（Finding 4: 既存のINVENTORY_CASESはbucket＝deny/allowのみを見ており、この現象自体は固定化されていない）。

- 新規テスト関数（例: `test_sed_strip_literals_path_pseudo_boundary_documented`）で、`sed_strip_literals("1w tickets/active/sub/APP-001.md")`のような入力に対し、`tickets`中の`s`が疑似的なコマンド開始とみなされ`/active/sub/`相当の区間が除去されること（現状の既知の挙動）を`assertEqual`で固定する。**この挙動を「正しい」と主張するのではなく「既知の現象として凍結し、回帰があれば検知する」ことが目的**である旨をコメントで明記する。
- 併せて、`w`が疑似トリガーより**前**にあるため`stripped`に`w`が残り続けること（=deny判定に到達すること）を`sed_program_violation`経由でも確認する（`sed_program_violation("1w tickets/active/sub/APP-001.md")`が`None`ではない＝deny理由文字列を返すことを確認）。

### 4-2. `INVENTORY_CASES`への逆順ケース追加（AC1・AC2・AC3・AC4）

`tests/test_guard_bash_writes.py`のINV-SED-31（一意な引用文字列`対照: |区切りは元々検出済み・回帰確認`を含む行）の直後、`# --- シェル展開の次元（§3-9-2。`コメントの手前に、`INV-SED-32`以降として追加する。

**設計方針（implementerへの指示）:** investigation.mdの追加調査（境界文字×デリミタ23種×危険文字12種×境界位置13カテゴリ・計3,345件）の生の入力列挙はレポートに保存されていない（investigatorのセッション内生成のため）ため、全件をそのまま転記することはできない。代わりに、次の条件を満たす**代表的サブセット**を新規に構築し、`INV-SED-32`以降として追加する。実機GNU sedとの二方向照合はimplementerが`investigation.md`の「追加調査」節と同じ考え方（checkerの判定と実機の実際の書込/読取漏洩挙動を突き合わせる）で実施し、結果を実装ノートへ記録する（既存のINV-SED各行と同様、pytestでは checker の deny/allow バケットのみをアサートし、実機照合は実装ノートでの手動記録でよい。KLK-015のAC8がそうであったのと同じ運用）。

- **最低限のカバレッジ:** investigation.mdが列挙する13の境界位置カテゴリ（本編: 先頭境界・デリミタ自体への危険文字使用・閉じ後のフラグ位置・トリガー前後への危険文字配置・実パス構造の模倣・ブラケット式・カスタムデリミタアドレス・`/`トリガーの類似ケース／補完: アドレス前置き6種・`;`直後・`}`直後・危険文字を区切り無しでトリガー直前に接着）それぞれについて、**少なくとも1件**の新規ケースを追加する。
- **重点方向（Finding 4への直接対応）:** 追加するケースは、危険文字（`w`/`W`/`r`/`R`/`e`のうち少なくとも2種を含めること。優先度は書込`w`・情報開示`r`・任意実行`e`の順）を**疑似トリガー（パス文字列由来の`s`/`y`）の後**に配置する。既存INV-SED-09〜21（危険文字が疑似トリガーより前にある順序）と対をなす「逆順」を明示的に固定することが本追加の主眼である。
- **期待値:** 全て`deny`（安全性主張どおり、疑似境界探索の誤動作があってもdenyへ倒れることを立証するため）。もし実装時にいずれかのケースで`allow`になる組が見つかった場合は、AC1が要求する「検出漏れに至らないことの立証」に失敗したことを意味し、**設計を確定させず直ちにorchestratorへ報告してブロッカー化する**（方針bの前提=investigatorの3,345件照合結果が覆ることになるため、architectの設計判断自体を見直す必要がある）。
- **命名・記述形式:** 既存のINV-SED各行と同じ形式（`("INV-SED-NN", "説明（カテゴリ名を含める）", "コマンド文字列", "deny")`）に揃える。
